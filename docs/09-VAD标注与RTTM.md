# 09 用语音活动检测给训练音频加时间标注（RTTM）

这篇文档说清楚一件事：**怎么给说话人验证的训练语音，每条生成一份「哪段时间有说话声」的标注文件**，
以及为什么要做、做出来的文件长什么样、怎么跑、怎么确认跑完了。

用到的工具是 **FireRedVAD**（一个语音活动检测模型）的非流式离线模式。
这里的「语音活动检测」英文缩写是 VAD（Voice Activity Detection），
意思是判断一段音频里每一小段究竟是「有人在说话」还是「没有人在说话」。

## 2. RTTM 是什么

RTTM 是 NIST（美国国家标准与技术研究院）定的一种**纯文本**标注格式，
全称 Rich Transcription Time Marked。语音识别、说话人分割这些任务里，
大家用它来记录「什么时间、谁、说了多久」。

它每一行描述一段语音，一共 **10 列**，列与列之间用空格分开。我们生成的每一行长这样：

```text
SPEAKER 00001 1 0.440 1.380 <NA> <NA> <NA> <NA> <NA>
```

逐列说明（**时间是秒**，一律三位小数）：

| 第几列 | 内容 | 我们写什么 | 说明 |
|--------|------|-----------|------|
| 1 | 类型 | `SPEAKER` | 固定写这个，表示「说话人活动」 |
| 2 | 文件编号 | `00001` | 音频文件名去掉扩展名。见下面第 5 节 |
| 3 | 声道 | `1` | 模型看到的永远是单声道，所以固定是 1 |
| 4 | 起始时间 | `0.440` | 这段语音从音频的第 0.440 秒开始 |
| 5 | 持续时长 | `1.380` | 这段语音长 1.380 秒（即到第 1.820 秒结束） |
| 6 | 说话人类型 | `<NA>` | 我们不做说话人区分 |
| 7 | 说话人名字 | `<NA>` | 同上 |
| 8 | 置信度 | `<NA>` | 不用（格式规定这里本该是「是否可信」，我们不填） |
| 9 | 信号类型 | `<NA>` | 不用 |
| 10 | 其他 | `<NA>` | 不用 |

`<NA>` 是 RTTM 格式里表示「这一列没有内容」的写法，不是我们自己编的。

**一个音频可以有零行、一行或多行。** 行按时间先后排列，段与段之间不重叠。

> **我们的文件还多了几行以 `#` 开头的注释。**
> RTTM 规定 `#` 开头的行是注释，读的人应该跳过。我们在里面记了这条音频的来源、
> 采样率、声道数、原始时长、用的哪个模型等等，方便以后排查问题。
> **只会读标准 RTTM 的程序不受影响**，因为它们本来就该跳过 `#` 行。

## 3. 为什么要做这件事

现在的训练是把每条语音**固定切**成一样长的小段（比如都取 2 秒），
切片的位置和「哪里是真正一句话」没有任何关系。这带来两个问题：

1. **切到一半的字。** 一条语音里，第 2.00 秒可能正好在一句话的中间。
   切出来的片段既不是一个完整的字，也不是一个完整的词，模型学到的东西不干净。
2. **切到静音。** 片段里可能一大半是停顿或者背景声，有效信息很少。

有了 RTTM 之后，训练程序可以先读这份标注，知道「第 3.10 秒到第 5.00 秒是一整段有人说话的区间」，
然后**在这段区间内部**挑一个合适长度的片段。这样切出来的片段就是完整的字或词。

所以 RTTM 的作用是：**给训练程序一份「哪些时间可信」的清单**，让它不再闭着眼睛乱切。

## 5. 输出放在哪、文件叫什么

### 5.1 文件名

音频 `.../id00012/21Uxsk56VDQ/00001.wav` 对应的标注是：

```text
.../id00012/21Uxsk56VDQ/00001.wav.rttm
```

也就是**在音频文件名后面直接加 `.rttm`**。这样做的原因：训练程序手上只有音频路径，
不做任何查表就能算出标注在哪。后缀可以用 `--rttm-suffix` 改。

除了 RTTM，旁边还有一个以点开头的隐藏小文件：

```text
.../id00012/21Uxsk56VDQ/.00001.wav.rttm.json
```

它里面记了这条音频**当时的大小和修改时间**。下次续跑时，靠这两个数字就能判断
「这份标注还是最新的」还是「音频后来被换过、标注过期了」。

### 5.2 两种摆放方式

| 方式 | 什么时候用 | 参数 |
|------|-----------|------|
| 放在音频旁边 | 音频目录可以写 | 不传 `--output-root`（本机脚本默认不用） |
| 镜像树 | 音频目录只读（云端常见） | 传 `--output-root`（云端脚本默认用） |

**镜像树**的意思是：在输出目录下，按音频的路径搭出一样的目录结构。
但这里有一个**必须小心的坑**，我们实测撞到过：

样本清单里的三套语料，文件名重复得非常厉害。
仅混合清单的前 200 行里，`00001.wav` 这个名字就出现了 **31** 次（分属不同说话人）。

```text
.../voxceleb/vox2/wav/<说话人>/<视频>/00001.wav      ← VoxCeleb2
.../VoxBlink2/audio/<说话人>/<视频>/00001.wav        ← VoxBlink2
```

`VoxCeleb2` 和 `VoxBlink2` 的**音频文件名几乎完全一样**。
如果镜像树只保留文件名，这两条会写到同一个文件，后写的**悄悄盖掉**先写的，
最后结果少一批而且不会报错。

所以我们的做法是：**保留音频文件名，外加它上面两层目录名**。
上面那两条就变成了不同的路径：

```text
<输出目录>/id06536/kTOEfLNM3IY/00137.wav.rttm
<输出目录>/id122341/gUY2pdKeuDg/00003.wav.rttm
```

另外，如果传了 `--audio-root`，会先算出相对路径再取最后三层，
这样还能把语料本身的名字带进去，例如 CN-Celeb2 的会走 `data/<说话人>/xx.flac.rttm`。

**工具会在开跑前检查一遍**：把本进程要处理的音频都算一遍输出路径，
一旦发现有两条音频会撞到同一个路径，就**拒绝启动**并打印撞在一起的是哪几条。
这个检查的开关是 `--no-collision-check`（不建议关）。
层数用 `--root-depth` 调，默认 2。

### 5.3 文件编号（第 2 列）

我们用**音频文件名去掉最后一个扩展名**：

```text
00001.wav   -> 00001
a.flac      -> a
```

选这个的原因：它对同一条音频永远是同一个值，不随语料挂载在哪而变。
代价是**不同目录下的同名文件编号会一样**（比如 VoxCeleb2 和 VoxBlink2 都有 `00001`）。
这没有问题，因为 RTTM 是**一条音频一份**，文件编号只在这份文件内部使用，
训练程序是靠音频路径找到这份文件的，不靠文件编号。

### 5.4 没有检出语音时怎么办

**写一个只有注释、没有 `SPEAKER` 行的空文件，然后认为它是有效的。**

之所以不选「不写文件」，是因为训练程序必须能分开这两种情况：

- **有文件但是空的**：这条音频标注过了，模型认为里面没有语音。
  训练程序可以据此决定用兜底方案（比如退回固定切窗）。
- **没有文件**：这条音频**还没标注**，应该等标注跑完再来。

如果两种情况都表现为「没文件」，训练程序就没法区分了。
`--mode validate` 会把这种空文件算作通过，并在统计里单列一个 `empty_rttm` 计数。

## 6. 怎么保证跑得对

### 6.1 分片：多个进程怎么分活儿

样本清单是一个一行一条音频的文本文件。我们把任务这样分：

> 第 `r` 号进程，只做那些「从 0 开始数、行号 `i` 满足 `i % 进程总数 == r`」的行。

这样分有两个保证：

- **不会重复**：任意一个行号 `i` 除以进程总数只有一个余数，所以只属于一个进程。
- **不会遗漏**：0 到 N-1 每个整数都有一个余数，所以每一行都被某个进程拿走了。

各进程的条数最多差 1 条（除不尽的时候）。
因为每个进程是**独立的**、各写各的文件、互相不通信，
所以不存在「为了对齐必须凑一样多」这种要求，也就不会出现
「某些样本被重复处理来填满一个批次」的情况。

**开跑前脚本会真的算一遍**（`--mode shard-plan`），断言重复 0 条、遗漏 0 条，
把结果写进 `.runtime/shard_plan.json`，对不上就拒绝启动。

### 6.2 批量推理的数值对照

为了跑得快，我们把多条音频摞成一个批次一起算。
摞的时候短的补零到和最长的一样长，补零的位置用掩码盖掉。

问题是：**这样做出来的结果，和一条一条单独算，会不会不一样？**

所以有一个 `--mode oracle` 模式专门验证这件事：同一批音频，
先用批次方式算一遍，再逐条单独算一遍（单独这条路走的就是官方原本的 `vad_model.forward`），然后比对：

- 每一帧的语音概率，最大绝对误差必须小于 `1e-5`；
- 切出来的语音段时间戳，必须**逐个完全相同**。

本机实测（32 条真实音频）：

```text
oracle_items=32
maximum_absolute_probability_error=7.2e-07
segment_timestamps_identical=true
status=passed
```

启动脚本默认会先跑这个对照，不通过就不往下走。

### 6.3 续跑：怎么知道哪些已经做完了

一份 RTTM 只有在**下面每一条都满足**的时候，才会被当成「已完成」而跳过：

1. 文件存在，且能按 RTTM 的十列格式解析出来（不行就重算）；
2. 每段时长是正数、起点不为负，段与段之间按时间排好、不重叠，且不超出音频长度；
3. 文件里记的**音频大小和修改时间**，和现在磁盘上的一致（不一致说明音频换了，标注过期）；
4. 文件里记的**推理标识**和本次运行一致。
   推理标识是把「模型校验和 + FireRedVAD 代码版本 + 所有 VAD 参数 + 输出命名方式」
   一起算出来的一个短字符串。任何一样变了，标识就变了，旧标注就不会被误用。

任一条不满足，就重算并原子地覆盖（先写临时文件再改名，读到的一半文件不可能出现）。

### 6.4 复查模式

`--mode validate` 会把每一条音频的标注**重新读出来检查一遍**，
不做任何修改，最后给出一份汇总：

```json
{
  "processed": 20000, "valid": 20000, "invalid": 0,
  "empty_rttm": 120,
  "segments_total": 34094,
  "speech_seconds": 121028.9, "audio_seconds": 124774.9,
  "speech_ratio": 0.969978,
  "source_sample_rate_counts": {"16000": 20000},
  "source_channel_counts": {"1": 20000}
}
```

启动脚本跑完会自动做这一步，并把各进程的数字加起来，核对总数是否等于样本清单的行数。

### 6.5 单个文件出问题不影响整体

下面这些情况都会被记下来并跳过，不会让整轮任务挂掉：

| 情况 | 处理 |
|------|------|
| 文件不存在 | 记进 `failures.<rank>.jsonl`，继续下一条 |
| 0 字节 / 文件损坏 | 同上 |
| 采样率不是 16 kHz | **自动重采样到 16 kHz**，原始采样率记进 RTTM 注释 |
| 多声道 | **先按浮点求平均下混成单声道**，原始声道数记进注释 |
| 超长音频 | 按 300 秒切成块分别推理再拼起来（`--chunk-max-frame`） |
| 一条语音都没有 | 写一个空 RTTM（见 5.4），算有效 |
| 音频太短（不足一帧） | 特征帧数为 0，写空 RTTM |

语音段按时间顺序正确拼接。

### 7.5 分片正确性

用 200 条真实音频，跑 `--rank 0 --world-size 2 --limit 100` 两个进程，然后独立验证：

```text
rank0 条数 100，rank1 条数 100
并集条数 200，唯一条数 200
并集 == 0..199 : True
rank0/rank1 交集（必须为空）: []
两个 rank 的预期输出路径交集（必须为空）: set()
磁盘上 RTTM 数: 200
磁盘集合 == 预期并集 : True
清单前 200 行里找不到 RTTM 的: 0
文件编号与音频名不一致的: 0
```

### 7.6 续跑

用 20000 条真实音频跑起来，写出 277 个 RTTM 时**强杀进程**，然后重跑同一条命令：

```text
selected=20000, skipped_valid=276, written=19724, failed=0
```

`276 + 19724 = 20000`，说明**跳过 + 新做 = 全部**，没有重复劳动。

杀之前那 277 个文件，逐个算 sha256 重跑后再比一次：**277 个全部字节一致**，没有被改写。

重跑后再全量复查：

```text
processed=20000  valid=20000  invalid=0  empty_rttm=120
```

强杀会在输出目录留下 7 个没写完的临时文件（名字以 `.` 开头、以 `.tmp` 结尾）。
它们不会被当成结果（读的时候只认 `.rttm`），也不影响正确性，可以手动删掉。

### 7.7 出错路径

故意造了 9 种问题文件，结果：

| 文件 | 结果 |
|------|------|
| `zero_byte.wav`（0 字节） | 失败，记进 failures，**不影响其他文件** |
| `corrupt.wav`（内容不是音频） | 失败，记进 failures |
| 清单里有、磁盘上没有 | 失败，记进 failures |
| `silence_only.wav`（纯静音） | 写空 RTTM，算有效 |

| 各种采样率/声道 | 全部正常处理 |

## 8. 实测速度

> **先看这一条：这一节原来的数字是错的，已经换掉。**
> 早先这里写着"2 卡 2 进程 = 995 文件/秒、全量约 3.2 小时"。
> 后来有人按真实启动脚本在两种机器负载下复测，都远远达不到那个数。
> 排期请以本节的数字为准，并按"可能还要慢一些"留余量。

测的是**真实 VoxCeleb2 音频**，通过真实启动脚本端到端计时（含模型加载、
分片检查与最后的复查），机器负载见下面"为什么要留余量"。

| 配置 | 端到端（含启动） | 扣掉启动后的稳态 |
|------|-----------------|-----------------|
| 1 卡 × 1 进程，600 条 | 31.9 文件/秒 | 约 **47 文件/秒** |
| 2 卡 × 2 进程，600 条 | 19.7 文件/秒 | 约 **110 文件/秒** |
| 1 卡 × 1 进程，200 条 | 12.1 文件/秒 | —（样本太小，启动占比过大）|

注意 200 条那一行：**样本越小时启动开销占比越大**，所以不能拿它当稳态速度。
早先那些偏高的数字很可能就是没扣掉启动、或者机器当时比较空。

### 瓶颈在哪（这一条是对的，可以信）

把流水线拆开单进程测：

```text
读音频 + 重采样        约 1,000 文件/秒
整条 detect 端到端     约   49 文件/秒
```

也就是说**瓶颈在 CPU 上的特征提取，不在 GPU，也不在磁盘**。
在空闲机器上，单进程端到端能到约 49 文件/秒，
而真实启动脚本里每个进程还有并行读取、写文件等开销，实测稳态约 47。

**所以加显卡不会线性加速。** 从 1 进程加到 4 进程（跨 2 卡）
只从约 47 涨到约 110 文件/秒（2.3 倍），不是 4 倍——
因为大家抢的是同一批 CPU 核。

### 全量要多久（按上面的实测外推）

11,521,178 条，按 **2 卡 2 进程约 110 文件/秒**算：

```text
11,521,178 ÷ 110 ÷ 3600 ≈ 29 小时
```

按 1 卡 1 进程约 47 文件/秒算则约 68 小时。
**所以排期建议按"一天到三天"量级，不要按几小时。**

### 八卡外推（说明假设）

八卡按每卡 2 进程，也就是 16 个进程。不能简单乘 4 倍，
因为瓶颈是 CPU 不是 GPU，进程越多单进程越慢。给三档：

| 情形 | 假设吞吐 | 全量耗时 |
|------|---------|---------|
| 悲观（CPU 核不够） | 200 文件/秒 | 约 16 小时 |
| 中性（比当前 2 卡好 2 倍） | 220 文件/秒 | 约 15 小时 |
| 乐观（CPU 核充足、接近线性） | 440 文件/秒 | 约 7 小时 |

**这个外推的假设很粗，请以实际跑出来的数字为准。** 具体地：

1. 云端机器的 CPU 核数与磁盘读取速度与本机相当（本机 128 核）。
   **云端 CPU 核少的话，8 卡不会有这个速度** —— 瓶颈就在 CPU。
2. 没有把 8 卡跑满过（本机只有 2 块卡），只能按上面三档估。
3. 上面所有数字都在一台**有别的任务在跑**的机器上测的
   （测的时候负载 4～33，忙的时候到过 240 以上）。
   机器空的时候会更快，忙的时候会更慢。

**建议**：先在云上按第 4.4 节跑一次冒烟（`LIMIT_PER_RANK=100`），
看真实的文件/秒，再决定正式任务的时间窗。不要直接用本节的数字排期。

## 10. 常见问题

**问：为什么有的音频一条语音段都没有？**
答：模型认为整条音频都没有说话声。抽查中占比不高（20000 条约 0.6%）。
这种会写一个空的 RTTM（第 5.4 节），训练程序可以据此走兜底方案。

**问：为什么 `00001.wav` 和 `00001.flac` 的标注文件名不同？**
答：因为 RTTM 名字是「音频名 + `.rttm`」，音频名本身不同（一个 `.wav` 一个 `.flac`），
所以 `00001.wav.rttm` 和 `00001.flac.rttm` 是两个文件，不会互相覆盖。

**问：RTTM 里的时间是相对于什么？**
答：相对于音频文件自己的开头，第 0 秒就是音频的第一个采样点。
如果源音频不是 16 kHz，时间是按**重采样之后**的 16 kHz 信号算的，
但因为重采样保持时长不变，所以也等于原始音频里的时间。

**问：改了 VAD 参数（比如 `--speech-threshold`）会怎样？**
答：推理标识会变，之前所有 RTTM 都会被判定为「不是本次设置做的」而重算。
这是有意设计的，避免新旧参数的结果混在一起。

**问：跑的时候能不能同时做别的事？**
答：可以。任务本身很轻，但会把 CPU 吃满（特征提取是瓶颈）。
如果同时还有别的任务要跑，用 `PROCESSES_PER_GPU=1` 或者调小 `--num-workers`。
