## 3. 接下来一周该盯什么

按“会先出问题”的顺序排，每条都写了看什么、什么算不正常：

1. **标注能不能守住现在的速率。** 45,000—50,000 源/小时是目前稳态；连续两小时低于 35,000 就要查 worker 是否掉到 8 个以下、租约是否被单个大分片卡住。速率只用来算工期，不能用它证明标签质量。
2. **失败与隔离会不会出现。** `failure.json` 出现说明有分片彻底失败，`quarantine.json` 出现说明有分片被移出候选。两者都不等于停跑，但都要看内容，以及它们是否集中在同一来源或同一类音频上。
3. **侧车全量验收的口径还没定。** 坏源产回执那条修复让分片可以提交，但全量侧车验收会要求“每个已提交源都有侧车”，这类源没有。要么单独记账，要么补空侧车；这是一个决定，不是修 bug，落地前全量验收的结论不能算数。
4. **SITW 要不要补。** 卡在数据集授权（SRI 邮件申请或 Hugging Face `confit/sitw-full`，约 19.9 GB）。拿到 trials 后代码侧大约 1 小时能接上（推断）；没有授权，六列就是上限，报告里要写明缺这一列。
5. **LM 回执 `ok:false` 要不要修。** 源码已改成两份日志都读，但 r3 冻结包没有重打，那份回执不会自己变对。重打是发新版本，不是热修，要按 9.2 的四个哈希一起更新。

已经不用再做的：六列与 8 秒口径都测过了，重跑只会得到同一批数字；剩九百多万条的工期估算也不需要重新起任务，看板会自己更新。

3. **进度看板**：`docs/ANNOTATION-PROGRESS.md`，或现算一份：

   ```bash
   /root/miniforge3/envs/USE/bin/python tools/annotation_progress.py --out /tmp/progress.md
   ```

   服务器默认 `python3` 是 3.8.10，直接跑会报 `TypeError: unsupported operand type(s) for |`（实测）；用 3.10 以上的解释器。网页版是 `tools/annotation_dashboard_server.py --port 8899`，同样要 3.10 以上。
