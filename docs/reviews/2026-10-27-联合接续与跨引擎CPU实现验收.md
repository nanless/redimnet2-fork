# 联合接续、跨引擎对照与最小适配的 CPU 检查

本轮将此前规划中的三项工作实现为仓库代码：旧结果与新剩余输入的联合核验和唯一读取、独立跨引擎对照协议、官方 Qwen 接口的 vLLM 最小适配及转写阶段恢复。用户明确要求先不做 GPU 测试，因此本轮只使用本机 CPU 和合成来源，没有连接训练服务器、调用模型或音频 API、提交或切换云任务，也没有修改主训练阶段（PTN）的运行文件、冻结清单、队列和检查点。

软件行为已经过分工实现、交叉源码审阅、反例修复和复验。实际新旧任务交接、真实千万条终验、真实 vLLM/CUDA 兼容、吞吐、显存、远程文件系统事务以及文字和完整字准确性均没有在本轮得到证明。现有标注结果仍属于原生产者，机器候选仍不能自动进入训练或正式评测。

## 一、现在具体实现了什么

| 工作 | 维护入口 | 实际行为 | 仍不代表什么 |
|---|---|---|---|
| 保留旧结果并准备真正剩余输入 | `prepare_speed_continuation.py` | 默认只读预估；最终模式在旧父锁和终态材料约束下核未封账及未领取片的已发布结果，将其排除，只复制缺失来源 | 不是运行中热切换，也不授新任务启动资格 |
| 全库联合检查 | `union_coverage.py`、`cloud_gate.py --union-mode` | 原全集、旧已保留结果、新剩余来源逐源比对；完整模式再重开新旧侧车、提交记录和完成槽 | 不是资源、真实模型或人工质量验收 |
| 唯一读取 | `union_consumer.py` | 只读固定消费数据库，按原顺序和已声明生产者返回原记录及摘要 | 不按修改时间选版本，不复制旧结果为新生产者 |
| 跨引擎对照 | `engine_protocol.py`、`audit_engine_comparison.py` | 同一输入和控制条件下，分别核文字、语言、结束证据、可比字界、新计算及恢复 | 不是只比较成功子集，也不认证真实 GPU 速度 |
| vLLM 最小桥接 | `vllm_backend.py` | 延迟真实依赖导入，使用官方提示及解析接口，显式固定生成条件，按原生请求 ID 映射输出 | 尚未证明本机实际依赖组合能运行 |
| 新转写阶段库 | `asr_stage_store.py` | 一次预约整批，一次事务保存完整原生结果，持久化后才逐来源消费 | 不改旧缓存键，也不是八卡资源控制器 |

详细文件格式及命令见[联合覆盖与唯一读取](../../tools/open_annotation/联合覆盖与唯一读取.md)、[跨引擎对照协议](../../tools/open_annotation/跨引擎对照协议.md)和[vLLM最小适配与阶段恢复](../../tools/open_annotation/vLLM最小适配与阶段恢复.md)。公开测试提供可执行合成示例，实际运行必须另给原件、合同及各自摘要。

## 二、联合接续怎样保证不重跑旧结果

正式范围仍为 VoxCeleb2 1,092,009 条、VoxBlink2 9,904,382 条、CN-Celeb2 524,787 条，合计 **11,521,178 个独立来源**。这批是三个训练域的原主训练或大间隔微调引用；同一来源不因两种用途重复计数。不能拿剩余数量替代这个原分母，也不加入 MUSAN、额外业务诊断或其他语料。

`annotation-union-coverage/v1` 显式绑定原全量索引、最终准备报告、旧新合同、各自队列与侧车树，以及真正剩余索引。验证不是只做两个数量相加：原全量逐源记录摘要、原分片位置、来源 ID、用途和输出相对路径都进入独立 SQLite；重复、来源记录变化、重叠、漏项、多列均拒绝。

保留结果包括三种情况：旧完成片、已领取但未封账片中的完整侧车，以及尚未领取片中预先发布的完整侧车。最后一种容易遗漏，本轮审阅发现原准备器不能完整处理它，已补扫描与独立保留账本。只有侧车和逐源提交记录均存在、身份及摘要正确时才保留；孤儿、损坏或报告漏列的旧结果一律保留证据并拒绝，不悄悄重算。

`plan` 核原全集和旧新分工，要求一小时内的外部旧任务终态观察、既有父锁独占及 broker 稳定。`complete` 进一步核新剩余生产者已完成且无租约，重开全部选中旧新结果。终验可以发生在旧任务结束多天之后，因此不强迫把真实历史终态伪刷新为今日；当前旧锁、broker 和所有固定原件仍要核。终态 JSON 由外部实际观察提供，工具本身不认证平台账号或当前平台状态。

真实合同必须有非空 runtime 及转写/定位模型身份，逐条侧车还核合同版本、模型和 runtime。只提供一个正确合同 SHA，却在侧车写另一模型或策略，会被拒绝。合同在打开时按 SHA 读取，消费时不反复哈希同一合同；原来源分片缓存至多四片，每次仍核选中结果与提交摘要。

完整模式可将独立消费数据库发布到一个新外部路径，报告给出数据库 SHA。消费端只接受与描述精确绑定的完整索引，按记录选择 old 或 new；输出仍保留原生产者、原侧车和原摘要。没有最终结果的 plan 索引不能供正式消费。全部来源已由旧结果保留时无需后继任务，不制造空任务。

六条合成来源的文件级流程实际验证了两种分配：旧三条加新三条，以及在未领取片预置一条旧结果后的旧四条加新两条。后一条从最终准备、联合入口、新剩余发布、完整终验到唯一读取均实际串联，旧字节和修改时间保持原样。它验证的是小样本软件行为，不能写成真实千万条已核完。

最终准备与联合检查都会产生全域文本、旧结果读取及数据库磁盘开销，不能频繁用于正在运行的任务。本轮没有执行真实全库扫描，也没有解码或重新哈希原音。运行进度仍使用轻量 `readonly_progress.py`。

## 三、跨引擎怎样比较才不会得出假提速或假质量

新协议独立于旧单窗算子对照；旧工具同源码、单窗及资源限制没有放宽。模型权重、音频预处理、窗口和原钟、提示与语言、生成上限及非采样条件、质量规则、定位身份固定；只有显式列出的引擎、源码、精度和批量可以改变。生产者摘要与整个冻结包摘要分别保存，最终侧车须匹配实际包、合同和模型来源。

vLLM 轨必须引用真实适配描述文件，核其模型、版本、源码、生成上限、seed、精度、批上限、语言、窗口、规范化及 EOS 声明；不能只填一个形式正确的散列。每个新执行窗口的原生结果都要绑定稳定请求身份、来源和 PCM、实际生产者、原生请求 ID、批次摘要、token 与结束证据，以及最终侧车的文字、语言和状态。原生 unknown、truncated 或 failed 不能在最终侧车变成 completed。请求 ID 与批次摘要的形状检查不等于已验证真实 GPU 或该数据库的整批内容。

所有计划来源都计账，失败和无窗口来源也不能删除。固定文字的定位对照与各自转写的端到端对照分别进行；文字或词序不同就不强配字界，返回空值和不可比原因，不记零毫秒误差。原生时间、库内 FIX 及最终单位分别保留。这里给出的是方法间差异，没有人工金标时不能报告完整字准确率。

新计算、阶段缓存、完整结果复用和未执行分开统计。只有完整非合成新执行且无缓存复用时，才计算已保存记录的墙钟比例；`GPU_runtime_verified=false`，`validated_GPU_speedup=null` 始终保留。一个时间 JSON 不能自认证显卡运行。恢复对照单独固定既有已发布文件的字节与摘要，不强迫跨引擎尚未提交的计算逐位一致。

## 四、最小适配与断点恢复的实际范围

适配器通过 `enqueue()` 获取每条原生请求 ID，再从 `wait_for_completion()` 结果按 ID 查回来源，允许乱序但拒绝重复、缺失或陌生 ID。不会根据数字猜来源或按返回位置误配音频。公开接口依据已经复核：[官方 Qwen 源码](https://github.com/QwenLM/Qwen3-ASR/blob/main/qwen_asr/inference/qwen3_asr.py)和[vLLM 文档](https://docs.vllm.ai/en/stable/api/vllm/index.html)。网页说明只是接口参考，后续真实环境必须按实际依赖版本、导入源码和模型摘要重新验收。

结束证据保留 finished、finish_reason、stop_reason 和实际 token。token 中观察到 EOS 与引擎声明以 EOS 停止分别记录；只看到 stop 不自动算正常，矛盾或未知结束证据保留 unknown，达到上限记 truncated，异常中止记 failed。中间出现 EOS 或多次 EOS 的矛盾情况已补反例，不能通过伪造终止证据变成正常文字。

新阶段库使用本机 SQLite 事务和文件锁。完整批次在原生结果保存后才返回逐源内容；模拟该时间点中断后，只提供已存身份元数据即可恢复，实际新模型调用为零。未提交批次需要完整原输入组合，有界重做但保留完整失败输出和异常。已完成请求混入后续新请求时仍保留它原来的批次身份。缓存命中时若仍提供音频，也核实际数组，不接受旧摘要配新 PCM。缺少原数据库时拒绝，不能偷偷创建空库并重新计算。

普通模块导入和命令帮助不导入 torch、qwen_asr 或 vllm。真实工厂仅在显式 execute、pilot 用途、离线环境、固定依赖和关键源码、完整实际权重/处理器输入均核实后构造；配置文件摘要不能代替权重身份。普通对象注入不能记录成真实工厂已经运行。当前用户要求下没有调用真实工厂。

## 五、审阅修复与实际测试

本轮交叉审阅修复了：旧完成片集合只核计数的不足、未领取片已有结果未纳入最终保留、新生产目录已存在却身份错误、合同版本/模型/runtime 与侧车未完全对应、阶段数据库缺失可能被重建、真实模型摘要只覆盖配置、关键解析源码未绑定、注入对象误报真实构造、矛盾 EOS，以及跨引擎原生请求/状态/配置/包身份和字段形状不足。

整仓首轮 **796 项单元测试全部通过且无跳过**。补齐原生请求和批次形状的两项测试后，最终 **798 项单元测试全部通过且无跳过**。后一轮的文档静态组因当时尚未创建本报告的链接未通过；该失败原件保留。文档补齐后已单独复跑静态，**442 个文件检查通过、零错误**，含227份Python、12份Shell、28份JSON和75份Markdown；skill格式校验也通过。最终检查与提交摘要保存在本机收据中，未修改原失败汇总冒充成功。

实际文件级集成还串联了假 vLLM、整批持久化、原生结果文件、完整侧车和提交、跨引擎审计，再执行只带元数据的恢复：无新引擎调用，既有发布字节不变。它不是 mock 一句返回值后宣称生产恢复成功。真实模型、GPU、远程存储和人工质量边界仍如上所述未测。

## 六、接下来仍要做什么

1. 用户允许真实 GPU 后，先固定实际离线依赖、模型与资源控制器，验证真实 Qwen/vLLM 公共 API、PCM、语言、原生 token 和终止信息。当前不启动，也不共享不明进程的显存。
2. 在有限的三个训练域代表样本上，对照完整来源的速度与质量；同时做固定文字定位和各自文字端到端比较，并保留困难例逐条听审、波形频谱、削首/削尾/邻字证据。机器审核不冒充人工金标。
3. 实测加载/稳态峰值、模型执行和完整流程吞吐、异常与恢复、资源归还和远程文件系统行为，再决定批上限和每卡结构。不能套旧单实例显存直接推 vLLM 容量，也不能预报一个已实现的提速倍数。
4. 新旧 writer 交接需要真实旧终态、互斥资源和实际质量证明。正式交接时运行联合 plan，只将缺失来源交新生产者；结束时运行 complete 形成唯一消费索引。CPU 数据门不能替代原 W2、实际模型或八卡入口。
5. 保留所有候选与未知，按原因及域分层审核。通过人审和正式数据质量条件后，再进行官方模型的完整字自然变长微调与注册/测试长度交叉评测，分别记录自动标注、训练和评测资格。
