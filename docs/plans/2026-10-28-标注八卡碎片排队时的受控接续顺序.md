# 标注八卡因资源碎片排队时的受控接续顺序

本文件是操作准备，不提交、停止或重启任何任务。它修正此前文档中“必须先拿到新实例请求才能停旧标注”的过严顺序。用户已授权修复并恢复标注，同时明确不能影响PTN；不能把文档自行增加的限制当作平台或skill要求，使旧标注占满一台八卡、新八卡因此排队、却又必须等新实例才能释放旧节点的循环一直持续。

## 1. skill实际要求的先后顺序

`volcengine-ml-ddp-submit/SKILL.md`的操作原则要求：“创建后继实验时先提交新任务并取得唯一 ID、核对其详情。只有用户已授权停止精确旧任务时才执行停止”。其`references/platform-ddp-workflow.md`的“先创建新任务，再停止旧任务”段落，同样要求先有唯一新ID、核资源和挂载，再依已有停止授权处理精确旧任务；资源碎片不是重复提交的理由。

这里要求的是**新任务已经真实创建、取得唯一ID且配置正确**，没有要求新实例必须先分配。在资源足够时，先核新实例再停旧能减少中断；如果真实碎片证明旧标注占据可释放的整台八卡，可以先有新ID并核配置，再受控停止那个旧annotation，随后等新实例请求。

本轮授权只覆盖精确旧annotation。PTN、未知进程、其他人的任务、环境和冻结源码均不在停止或更改范围内。task名称相似不是归属证据，必须把旧task详情、实际入口和当前run相互对应。

## 2. 停旧标注前先固定这些材料

1. **候选通过。** 真实16源新协议的30/3000/512结果、全部逐差异质量、CPU/GPU证据、实际端到端速度和源码身份齐全；旧15源试验不授新16源正式运行。
2. **未来正式新八卡已真实提交。** 记录完整task ID、`zhounan_`名称、实际优先级6、单worker/八A800、区域/队列/AZ、镜像、原挂载、入口、固定蓝图SHA、代码bundle和新合同。仅准备表单、提交结果未知、或验证任务ID都不满足。
3. **新任务尚未写生产输出。** 新八卡入口是已审有限等待器，实例开始后也在完整实际终态、旧writer锁和新鲜平台材料通过前不创建GPU；新旧queue、labels和代码目录互不覆盖。
4. **碎片证据是新鲜平台事实。** 保存调度事件的原始原因与时间；区分单节点八卡不足、配额/镜像/权限/挂载错误和其他确定性问题。不能仅凭“总共有8张空闲卡”认为可放在一台worker上。
5. **释放旧annotation确实能贡献目标资源。** 核旧annotation占用同SKU/同队列/AZ的一整台八A800；节点仍健康、可调度，不是停后即下线或维护的节点。不能通过停PTN释放资源，也不能保证释放后调度器一定马上选择本任务。
6. **旧发布结果保全。** 固定当前runtime/合同/索引/queue/sidecar树、现有日志和异常位置；取小broker/完成槽元数据作为停止前进度下界，不重开全库侧车或来源。提前核后续最多8个在途片的处理入口和已有恢复路径，不在最后才发现路径或旧设备身份不匹配。

## 3. 可解除循环的实际操作顺序

**第一步：先提交并核唯一正式新八卡。** 任务即使仍Pending，只要完整ID、配置和入口已经回读正确，并已核碎片原因，就满足skill的“先新后旧”。提交失败、结果未知或配置错误时保留旧标注运行，先查重/修配置，不先停旧去试运气。

**第二步：仅对已核的旧annotation做受控停止。** 使用平台正式停止操作，保留操作者、事件时间和原始日志。允许原父进程现有退出清理完成，不向未知PID发信号，不修改旧worker或全局环境，不假定停止就是崩溃。此处可以发生在新实例分配之前。

**第三步：真实确认旧task和worker终态。** 平台状态、旧worker状态、共享锁和数据发布状态分开核。拿到旧writer锁以后才定稿快照。原子提交已经完成的侧车/commit不删除、不重算；停止瞬间未完成的源可能留下临时文件或孤儿，完整保留并逐条报告。现有严格工具若发现孤儿必须拒绝，不能补写假commit、删除异常或把它当完成来推进。

**第四步：等唯一新任务实际分配并建立请求。** 新节点自身生成task/hostname/PID/start/boot/nonce请求，实际八张空闲A800必须通过资源快照。没有实例时外层尚未运行，1800秒请求期限尚未开始；队列等待时间不能冒充GPU计算时间。

**第五步：在请求之后重新只读平台，发布新鲜观察。** 旧任务可以早已停止，但要在本次request创建后真实刷新平台，写当前“旧task和worker仍终态、无活跃writer/竞争后继”的观察。保留原停止事件时间；新写的是本次观察时间，不能改旧停止时间或拿旧观察改时间戳。随后发布最多8个部分片的最终薄索引和有限回复。

**第六步：原GPU入口再次严核再运行。** 父进程复核请求/回复、旧终态、原祖先锁及永久唯一声明，FD贯穿所有孩子和资源排空。保留3600秒平台观察时效、1800秒请求期限和全部原W2/挂载检查；不因调度困难放宽任何字节或质量证明。

新实例启动后仍要核实际八worker、首个整批、旧结果继承、新结果提交及异常；Pending、Running、请求或exec-intent都不证明推理已成功。

## 4. 为什么当前代码不用改就能表达这个顺序

`native_batch_queue_handoff.py`的`check`核固定配置时不要求旧task已终态；`wait`只在真正分配的新实例建立请求。`observation`要求本次平台观察时间不早于request，而不是要求旧停止事件发生在request之后。`publish`再用这个新鲜真实观察做最终有界准备。因此，先停旧再等请求时，只需请求到来后真实重读旧终态，仍可满足现有代码。

此前“操作者核新实例后才停旧”的文字是减少中断的一种操作选择，不是代码准入条件。不能伪造一个尚不存在的新实例请求、预先填nonce/PID、重写旧观察时间、重复提交新任务或热改冻结包来解除循环。

## 5. 失败、回退与观察预算

停止前把本轮允许的调度观察窗口、到时采取什么动作和旧profile恢复准备状态写进操作记录。这个窗口用于作出运维决定，不变成另一个永久代码门；不要因“必须实例先可读”的文字无限等待，也不要自动创建新的后台调度。

| 发生什么 | 保留与下一步 |
|---|---|
| 候选未通过或没有真实正式新ID | 旧标注继续；修候选/材料或完成一次真实提交。 |
| 新任务Pending，实际原因是权限、挂载、镜像、配额错误或旧节点不可调度 | 不把停止旧annotation当修复；先修确定性问题和准备后继，保持唯一性。 |
| 受控停旧后，新任务仍Pending | 到预定决策时刻只读刷新调度原因，保留唯一新任务及全部旧结果；选择继续等待或走已准备的旧profile恢复，不反复提交副本。释放节点不是即时排期承诺。 |
| 新实例请求后1800秒内材料不齐/有孤儿/源码不符 | 等待器保留失败并退出，不启动GPU。保留旧标签、终态与部分片异常；修独立新材料，不能覆盖原请求或降低规则。 |
| 新任务GPU前失败，尚无新producer完整发布 | 可以评估恢复旧profile；先核新任务真实终态/锁释放、旧全部输出不变，以及已有恢复入口实际支持已有run和跨节点身份。不能仅点“重试”就宣称安全。 |
| 新producer已经发布任何完整结果后失败 | 不能直接回到原旧queue重跑，否则会重复新已发结果。优先在同producer、同scope和独立attempt证据目录严格恢复；跨节点新结果身份或当前恢复入口不支持时，先准备并CPU审查有界继承方案，保留两代所有结果，不开全库审计。 |

旧profile回退也必须遵守先取得唯一后继ID并核配置、再按授权处理精确被替代任务的顺序，入口须在旧writer未退出前保持互斥等待。必须证明它支持现有queue与完整已发结果复用、实际原音身份和当前节点；原fresh-launch入口若只支持不存在的run，不得冒充恢复入口。没有这些实证时，应准确报告缺哪一项并继续准备，不能通过改旧冻结清单、删除新结果、重算全库或抢PTN资源来制造“恢复成功”。

本方案目前没有执行平台写入。真实操作后应把平台新旧完整ID、实际停止原因和时间、最终最多8片快照、原始异常、请求/回复及八worker实际运行证据写入本次记录。
