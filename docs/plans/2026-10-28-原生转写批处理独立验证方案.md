# 原生转写批处理：独立验证方案与实施边界

当前方案先继续完成已经启动的独立双卡三轨试验，再新增“转写合批、Ultra 逐窗”的明确试验分支。旧八卡标注和主训练不改；正在运行的冻结副本不更新。新分支必须产生自己的源码、合同、输入、批次和结果身份，CPU 检查不能当作真实提速或正式准入。

## 为什么继续研究合批

2026 年 10 月 28 日首批三训练域 30 条实测中，FP32/eager、FP32/SDPA、BF16/SDPA 均完成 34 个转写窗口、930 个生成 token；原始文字、语言、token ID、EOS、32 个可比较定位窗口和决定均相同。FP32/SDPA 的两工作进程转写累计用时为 26.38 秒，基线为 31.89 秒，约 1.21 倍。首批总墙钟约 1.47 倍，但基线模型加载明显更久，不能把这一数字直接外推千万来源。

这说明 SDPA 确实执行，却不能证明它已解决主要吞吐问题。下一步优先测试同一原生 Transformers 引擎在一次 `generate` 中处理 4 或 8 个窗口。它沿用单进程、单 CUDA 上下文、单份转写模型和单份 Ultra，避免另建多进程共享资源机制。真正的收益仍须实测，不能从 GPU 利用率或空余显存推算。

已经只读核实的官方 `qwen_asr/inference/qwen3_asr.py` 摘要为 `0b1770f8e907b6c5a0a1e9ebce037cb63f48555f3cd15eaf6ea2078e9df41a7b`。其中 `_infer_asr_transformers` 用 `max_inference_batch_size` 分组，以 `processor(..., padding=True)` 构造批次，再调用一次多行 `model.generate`。外层 `transcribe` 还会拆分并重新合并长音频，因此不能只凭返回列表长度猜测请求对应关系。

## 新分支的固定条件

新增试验策略名为 `asr_fixed_cohort_fa_single/v1`，默认限 `pilot_validation` 或显式 CPU 夹具。原 `silver_annotation` 缺少明确的新正式声明时继续拒绝新策略；新声明只是默认关闭的合同数据，运行仍须完整实测选型和经过认证的新接续入口。转写批次大小在新字段中明确声明，候选为 1、4、8；Ultra 的原 `max_batch=1`、FP32/eager、作者权重、无额外 head、原生/FIX 观察保持。

第一次比较只使用同一 FP32/SDPA 数值方式的批次 1、4、8，避免把精度变化与批次收益混合。三个候选使用同一新版源码、模型、三域输入、窗口、源时钟、归一化、语言策略、512 token 上限和质量规则。新版批次 1 还需与已完成的旧单窗轨做文字、token 和字界桥接对照；不能把修改后的代码自动视作旧 GPU 验收版本。

每个工作进程只持有自己领取的分片。批次按固定有限来源组及稳定的窗口长度/编号顺序构成，保存完整有序成员；不跨工作进程、UUID 或领取片凑批。尾批不足 4/8 时照实记录，不能把声明的上限当成每次实际批次大小。实际批次宽度分布、填充比例、长短音频分布和有效生成 token 分别计量。

## 必须观察真实模型调用

新增前的维护实现有三道明确单窗约束：合同读取最终要求 `max_batch=1`，生成钩子要求实际输入恰一行，Ultra 调用也要求恰一窗。仅把一个配置改成 4 会失败；本次新增窄的显式策略分支，保留旧策略的拒绝行为。

新增生成观察必须核：实际 `input_ids` 与 `attention_mask` 的批次维、每行未填充输入长度、填充方向、实际生成行数、有序成员、官方内部真实生成次数和输出数量。对于外层拆分/合并、重复或缺失输出、额外请求及无法证明映射的情况，应保存完整证据并停止该次试验，不按位置凑答案。

每行保留完整矩形生成 token，以及首个 EOS 位置、EOS 前有效 token 数、EOS 后填充长度和 token 上限。早结束的行可能因同批其他行尚未结束而出现后续填充，不能把这些填充计为真正生成工作量，也不能以填充中的值伪造 EOS。实际 attention 调用、Q/K/V 精度、eval 与 inference 状态继续核验。Ultra 每次实际调用仍必须为一行。

原现场 Hugging Face 曾报告临时将空缺的 `pad_token_id` 设置为首个 EOS。新试验在生成前显式固定同一规则：若模型原配置已有 pad 就保留，否则明确设置为首个已配置 EOS，并将原值、实际值和规则保存；1/4/8 三轨完全相同。分词器显式左填充，实际 mask 再核，不能在审计时看见尾部 token 后反猜 pad。实际生成的 token 上限必须等于合同，第二次隐藏 `generate`、缺行或映射不明均停止并保留已经捕获的原生结果。

## 整批持久化与恢复

已有 `ASRStageStore` 依赖 SQLite，用户已明确禁止本轮数据库路线，因此不能构造它，也不借新名称间接使用。复用的是其“完整批次持久化后才逐源消费”的语义，而非数据库实现。

新文件存储限定在每个领取片的独立新生产者目录内。先发布稳定批次计划和完整成员身份，再运行模型；完整原生输出和结果摘要全部写完并原子提交后，才允许逐窗定位、阶段缓存和完整侧车发布。计划、意图、完整结果、提交记录及所有异常按不覆盖方式保存，不建立全库来源索引。

恢复时先读取原固定计划。已有完整侧车保持原字节并跳过；已有完整批次结果零新 ASR 调用，缺少的定位或发布继续做。只有意图、尚无完整批次提交时，必须取得原批完整输入重做，不能因其中一条已发布或列表次序改变就把它从原批删掉。整批提交前禁止逐源正式发布，避免出现只能换批重算的半批结果。失败或显存不足完整保留，禁止自动降成批次 1、悄悄换精度或丢掉失败行。

## 与现有对照及接续的关系

`engine_protocol.py` 已能声明 Transformers 与固定批次的变量。应使用新的批处理协议分支，固定模型、窗口、前处理、语言、生成和定位条件，只允许明确的 ASR 批次变化；Ultra 批次不是可变项。

`audit_speed_comparison.py` 刻意只接受单窗，不应放宽它来容纳批处理。`audit_engine_comparison.py` 目前只对 vLLM 的独立原生请求引用执行完整适配校验；原生 Transformers 批次须有自己明确的请求/批次/原生结果校验，不能冒用 vLLM 声明或仅填一个 producer 摘要。

现正式有界接续准入也只承认已经验证的单窗计算条件。批处理即使 CPU 通过，仍不自动获得八卡或正式标签资格；需经新的实际质量、恢复和资源验收，并用明确的新准入版本接入。旧结果保留旧 producer/job/原件，旧生产者锁、祖先语义锁、GPU UUID 锁、唯一后继声明和排空顺序继续适用。

`freeze_contract.freeze(..., asr_batching=...)` 对合批只生成试验合同，绝不顺手生成可运行的正式合同。另有显式数据工厂 `make_native_formal_contract(pilot_path, pilot_sha, output, version)`：核固定试验合同和现行计算源码，仅修改用途、版本并增加 `native_formal` 声明。声明为 `annotation-native-formal-contract/v1`，要求 `annotation-native-selected-pilot-admission/v2`、`authenticated_bounded_runtime_v2` 且 `default_enabled=false`；输出收据明确没有 GPU、正式运行或标签资格。它不计算或伪造实际选型证据，不能拿一份合同 JSON 绕过父进程、子进程和工作进程的接续准入。

## 验证顺序与停止条件

1. CPU 检查合同隔离、真实生成包装的行数/映射、左填充和早 EOS、整批原子发布、完整恢复、半批发布反例、损坏或孤儿结果，以及禁止数据库构造。旧单窗及正式拒绝分支全部回归。
2. 在独立双卡资源上先用同一 30 条验证批次 1/4/8。每轨完成并排空归还后才启动下一轨。保留所有未知、空转写、截断和定位失败；不拿三十条宣称全库质量。
3. 有效候选再跑同一 3000 条及至少 512 条恢复，比较完整来源和窗口分母、文字/语言/token/EOS/截断、同文字原生/FIX 字界，以及实际新 ASR/FA 调用、峰值显存和分阶段吞吐。恢复要求已经发布的字节不变；未提交批次重算差异单列。
4. 新的文字或定位差异逐条复核，必要时按现有授权边界做原音听审、图和 API 辅助。机器一致不能证明完整字准确，API 也不能代替明确的人审边界原件。
5. 完整质量、恢复、资源和实际稳态收益均通过后，才准备唯一的八卡新任务。当前八卡继续标注，主训练完全排除；任何未知提交结果先查重，不直接再提一份。

这份方案记录实施要求；下面把有限实测和仍未完成的条件分开，不能用小样本结果
代替正式接续验收。

## 2026-10-28 的有限实测及新增检查

同一 30 来源、34 窗口的原生批宽 1/4/8 独立双卡试验已完成，各轨均完整读回
并归还资源。实际转写累计耗时为 27.885、17.466、14.199 秒，分别约为 B1 的
1、1.60、1.96 倍转写速度。这是固定小样本分阶段结果，不能直接换算全库天数；
首轮加载也影响任务墙钟时间。B4 有 1 个窗口文字变化，B8 有 2 个；同目标可比
字界保持相同，目标变化处不能用零端点差冒充准确率相同。两个实际差异原件均
保持原 unknown 资格。波形/频谱、原生/FIX 图和 API 辅助内容观察不产生人工金标。

旧 FP32/SDPA 单窗与新版 B1 还做了明确桥接：固定 30 来源的 34 窗口输入、
文字、原始及有效 token 均相同，32 个同目标可比窗口原生/FIX 端点差为零。
工具重核有限父摘要、worker 摘要/ready/ACK、完成槽、片段收据和逐源侧车/commit
摘要，而不是只看两份侧车能否自洽。两版软件和实际机器不同，桥接不计算速度比。
具体工具与证据边界见[两版单窗桥接与有限上下文复核](../../tools/open_annotation/两版单窗桥接与有限上下文复核.md)。

512 来源已经完整发布后的侧车命中恢复，和 ASR 整批刚提交、完整侧车还没有
发布的中途恢复，是两项不同要求。新增独立的固定 30 来源单分片探针，以同一
候选冻结代码先完整冷跑，再在另一新树观察首包并仅中止本次自有父进程，等原
清理及同 UUID 锁内真实 5 秒双空闲后，才启动同树 attempt2。首组 8 来源包含
两窗口长原件，至少 9 窗口，确保批宽 4/8 都有后续未提交 cohort。若错过中间
状态就明确无法完成本次检查，不能把全命中当成半批恢复；orphan/临时文件保留
并拒绝继续。见[原生转写中途恢复探针](../../tools/open_annotation/原生转写中途恢复探针.md)。

三千条稳态比较、512 来源恢复、真实中途恢复探针以及全部文字变化的质量处理
都各有独立证据要求。任一仍未通过时，正式八卡选型与接续继续关闭，不因本文
的小样本速度而放宽源时钟、定位、错误或现有任务保护规则。

## 后续发现：有效声学特征也必须以单条为基准

原批处理三千条报告随后显示：B4 有 110 窗标准化文字变化，B8 有 122 窗；
B4 的这 110 窗在 B8 中仍是同样变化，另有 12 窗新增。文字和零长定位问题
使旧候选不能直接接正式八卡。纯 CPU 合成实证查到官方 processor 的波形
合批会改变短源的有效特征帧/占位数，也可能通过 STFT 边界和每源内部的
频谱地板改变有效 mel，尽管 PCM 摘要、原帧数及非补齐 prompt 可能相同。

新增显式 `official_b1_features_then_pad/v1` 协议：每条先沿官方 B1 提取有效
mel/mask/prompt，再在特征层合批，并在真正 generate 入参核逐行 SHA、长度
和 dtype。新合同增加第 16 个计算语义源码和七个明确前处理来源绑定；旧
15 源结果保留历史用途，不给新协议质量资格。真实无 CUDA Tensor 与官方
AutoProcessor CPU 检查已经通过，新的 30→3000→512 GPU 对照仍需完整重做。
当前先不提交旧 B4 的中途恢复探针。具体根因、证据边界和实现见
[单条特征保真批处理](../../tools/open_annotation/单条特征保真批处理.md)。
