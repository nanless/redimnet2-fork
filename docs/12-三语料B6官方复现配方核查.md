## 3. 学习率按真实代码核算

`train.py` 固定写入 `scale_ratio = world_size * batch_size / 64`。本次明确保留 `scheduler_args.lr_scaling: legacy`，因此不能把 YAML 中的初始学习率当作实际峰值。

主训练倍率为 `8*96/64=12`，初始值 0.06，8 轮线性预热后实际峰值为 **0.72**。预热 8 轮加平台 45 轮，从完成第 53 轮的位置开始指数衰减，每 10 轮乘 0.5。完成 115 轮的位置约为 0.00979369，120 轮最后一步为 0.006925219。

`ExponentialDecayPlateauWithWarmup` 的旧版公式不读取 `final_lr` 来决定终点。本次显式写 `decay_to_final_lr: false`，保留作者公式，不擅自把终点调到 YAML 的 `1e-4`。

LM 倍率为 `8*48/64=6`。`ExponentialDecrease` 从第 0 步就随总进度指数衰减，同时在前 0.2 轮做线性预热。实际第 0 步为 0，第 2,615 步的峰值约 **0.00045471497**，最后一步为 **0.00015001590**。优化器初始字段 `lr: 0.1` 在第一个更新之前会被调度器覆盖，不应据此声称 LM 使用 0.1 学习率。

轻量审计结果存放在 `/root/codex_artifacts/redimnet2_repro_20261019/recipe/audit.json`，数值由当前调度器实际计算，不是手抄估算。文件中的 `probes_at_completed_epochs` 是已经完成多少轮的位置，不是从 1 开始的日志轮号。

## 5. 120 轮与第 115 轮如何处理

官方 PTN 的有效字段是 `num_epochs: 120`，目录名写 `100ep`，官方 LM 的有效字段却加载 `model_115.pt`。公开文件没有给出作者最终发布模型的训练记录，因此无法证明发布权重必然使用第 115 或 120 轮。

本次采用可以直接审核的选择：**PTN 完整训练 120 轮，保留第 115 和 120 轮权重；LM 明确从第 115 轮开始。**这保留了官方两份配置的有效字段。主任务入口需显式传入 PTN 的 `models/model_115.pt` 及同一目录的 `spk2id.json`，不采用按修改时间找到的最新权重。此选择是本次实验定义，不冒充作者未公开的历史事实。

训练输出目录必须独立且持久。`REPRO=1` 只选择配置文件，不自动保证输出目录隔离。PTN、LM 和短测各自使用独立目录，首次正式运行不得从短测目录恢复。短测若从较早轮权重启动 LM，应另写清楚，仅验证接口，不更改正式的第 115 轮选择。

## 8. 分类偏置与训练状态

三语料 LM 配方仍使用 SphereFace2，`do_lm:true` 不会将其改成 ArcMargin。PTN 的标量偏置 `projection.bias` 形状为 1×1，在第一次载入模型时与骨干一起载入；后续分类头重组只替换 `projection.weight`，不会漏掉该偏置。

原速类别位于 PTN 分类头前 119,274 行，因为速度扰动通过 `label + num_spks * speed_idx` 扩展类别。按名称重组的分支在真实官方基线 `c5bbe0b` 已经存在；直接切取前若干行只是没有映射文件时的退路。本次严格检查禁止走该退路。

本轮还修正了训练状态恢复：从 `model_ckpt` 初始化新的 LM 阶段，只载入模型参数，不继承 PTN 的骨干动量、分类头动量或混合精度缩放器状态。只有使用当前阶段的 `checkpoint` 恢复时，才载入其优化器与缩放器状态。原来只删除形状不符的分类头动量会留下 PTN 骨干动量，不能满足这个要求。

`tests/test_cold_start_state.py` 直接调用训练器实际使用的选择函数，使用真实 SGD 动量检查冷启动保持空状态、同阶段恢复保留动量和缩放器字典，以及旧裸权重没有训练状态的三种情况。3 项冷启动/恢复 CPU 回归检查通过，另用临时目录验证主进程 INFO 进度在根日志级别为 WARNING 时仍写入 train.log，共 4 项检查通过。日志在上述 `lm-init/cold_start_regression.log`。八卡 LM 短测还应出现 `cold start: model_ckpt loads model parameters only; optimizer/scaler start fresh`，并确认没有从 PTN 恢复优化器或缩放器的日志。


## 9. 第一次云端八卡短测失败与短测时钟修正

2026-10-19 的第一次八卡短测（任务 `t-20261019171759-mplrn`）通信检查通过，但 PTN 第 25 次更新的损失记录为 16.277，第 32 次更新记录为非数值，验收程序拒绝继续，正式训练没有提交。原源码、日志与检查点保留不改。第 25 次记录只代表计量器已采样的损失，不证明之前每一步前反向都有限。

发现的确定性短测设计问题是：把每轮样本数缩成 24,576 条之后，每轮只有 32 次更新，调度器仍以“8 轮预热”计时，于是原本 120,008 步的预热被压成 256 步。第 25 次更新学习率变为 0.0675，第 32 次为 0.0871875；正式完整数据在同样更新位置应分别为 0.00014399040064 和 0.00018598760083，前者比后者快了 468.78125 倍。这说明旧短测没有保留正式训练最初几十步的学习率，不能据此直接认定官方完整训练需要降低学习率。

v2 只为短测派生配置，不修改正式配方或调度器公式。程序是 `applications/speaker_rec/scripts/cloud/make_b6_smoke_recipe.py`，接口为：

```bash
python applications/speaker_rec/scripts/cloud/make_b6_smoke_recipe.py \
  --recipe applications/speaker_rec/examples/vb2_vox2_cnc2/recipes/redimnet2/b6/official_repro_ptn.yaml \
  --stage ptn --sample-num-per-epoch 24576 --num-gpus 8 \
  --output /本次独立短测目录/checks/smoke_recipes/ptn.yaml
```

LM 使用 `official_repro_lm.yaml`、`--stage lm` 和样本数 12,288，输出另外的 `lm.yaml`。程序拒绝覆盖已有文件，输出配方外还写同名 `.timing.json` 说明和数值证明，标准输出也是该 JSON。输入必须是完整原配方，短测每轮必须恰为 32 次更新。

PTN 的预热、平台期和半衰期均乘 `15001/32`，间隔的轮数阈值则按 `(原轮号-1)*15001/32+1` 换算。保留初始学习率、八卡批量倍率和 `decay_to_final_lr:false`。因此只把“轮”的单位换回同样数量的实际更新，前 64 次更新连续不变；第一段跑 1 轮、恢复后累计跑到第 2 轮，也不会在恢复点跳变。

LM 的预热轮数乘 `13075/32`，终点字段换成 `initial_lr * exp(log(full_final_lr/initial_lr) * 32/13075)`。这是因为 `ExponentialDecrease` 的指数分母是总更新次数；改变这个终点只用于让截短曲线保持正式训练的前 32 步，不是重新选择正式训练的学习率。LM 第 25/32 次更新分别为 0.000005492697468 与 0.000007089470583。

程序直接调用仓库实际调度器验证：PTN 正式 120 轮与短测 1/2 轮的前 64 步逐点最大差为 0；LM 前 32 步的最大差为 8.47e-22（浮点舍入范围）。间隔曲线也检查了短测前若干步及开始/固定阈值两侧，最大差为 0。证明保存在 `/root/codex_artifacts/verification/volcengine/redimnet2-b6mix-20261019/nan-diagnosis/v2/smoke-clock/`。

这个修正解决已证实的时钟压缩问题，尚不能单独证明损失非数值的首个算子。失败检查点的分类头参数仍有限，AMP 缩放器已降到 0.5；后继短测应逐步检查输入、说话人向量、损失和梯度，出现非有限值时统一停止并保存原因。只有新的八卡短测完成全部验收后，才可继续正式训练。


补充数值排查：单独把池化模块转成 FP16、在 CPU 上输入常数 300，确实能因平方溢出产生非数值；但这不是本次混合精度执行方式。随后在空闲 A800、PyTorch 2.4.0+cu124 上做了微小 CUDA 探针，真实 autocast 自动将平方、softmax 和加权方差计算提升为 FP32，同样输入的实际池化结果全部有限。因此不能依据前一个 CPU 现象修改正式模型。证据是 `nan-diagnosis/v2/astp_cuda_autocast_probe.json`，峰值张量显存为 45,056 字节，没有运行训练。
