## 自动标注怎样进入下一步

来源身份至少区分编码文件摘要、解码后原采样率多通道 PCM 摘要、模型实际单声道输入摘要和各自采样时钟。旧 FireRed 标注若只有路径、大小、时间与采样时钟绑定，就照实保存这种较弱身份，不能补写成旧原音 SHA 已核。

原始模型时间、库内修补时间和最终候选单位分别保存。新十进制原钟与 legacy 重建规则分版；撇号 A/B 仅作文字条件诊断，不涉及训练资格。运行中的旧标注包不热更新，当前仓库包导入修复也不代表旧 A/B 实测源码已变。零长、倒置、越界、超出支持语言、空转写、生成截断和未决读法都要完整计账；删除失败样本会改变分母，裁切、均分粗词或把修补后的正长度当成完整字正确同样会改变结论。

完整字消费工具默认只提出待核候选。工程格式导出也保留 `usable_for_training=false`、`usable_for_evaluation=false`、边界待审核状态、未核实说话人身份和独立的工程用途分组。正式训练和评测的默认输入检查会拒绝这些候选。显式请求导出而全部被拒绝时，命令返回失败；默认只做完整计账时，成功退出只表示检查完成。

## 恢复与发布怎样验收

标注任务的恢复需用同合同、同原音、同源码的完整基线进行逐源比较。统计复用的旧结果与实际新执行的结果要分开核对：旧文件字节和修改时间、缓存确实被消费、缺少阶段实际重新执行。若模型对批次组合敏感，恢复时就不能改变未绑定的批次组合；单窗执行只消除这一项隐含影响，不保证模型答案正确。

发布记录要绑定真实输出和对应输入，父进程退出码不足以证明发布成功。对并发代次、锁、计算进程和资源归还的检查有现场条件，合成 CPU 测试替代不了这部分。正式新任务若已经取得持久作业声明，后续失败应进入显式接续方案；删除声明或盲目重提来绕开去重会让现场证据失效。

## 历史证据与当前维护版本

历史两卡实测验证的是当时冻结源码、模型、输入和环境的组合。把文件迁入本仓库、泛化路径、移除私有名单或重构依赖后，源码身份已经改变。应先跑仓库内合成回归，再按需要绑定原件做模型和 GPU 回归，分别记录结果。本页不宣布新仓库提交已完成 GPU 验证。

外部证据留在受控存储。公开仓库只存工具、合成测试、非敏感示例和证据格式说明，不保存真实业务音频、完整日志、原始标注名单或凭据。部署时另存 Git 提交、程序文件摘要、配置、模型与输入摘要；不能改历史冻结文件或其清单来隐藏差异。

## 受控接续还需哪些实际证明

model47 受控接续保留原 189 来源，只允许新 executor 和故障取证 helper 形成独立 190 成员树，不重封原清单。先做完整模型/SGD/scaler 与映射的实际 CPU 恢复，再做双卡有限更新/精确状态重构及注入非有限的完整取证。双卡的具体成功范围以已核报告为准：同进程对象重构不等于操作系统进程重启，也不能代替正式八 rank 准入。

`st_dev` 的语义：device 由挂载命名空间决定，同一批侧车在 dev 节点读到 `57`，在八卡容器里记录为 `2097190`。因此 device 不能进“内容身份”等式：内容是否变过由 `inode/bytes/mtime_ns/ctime_ns`（以及已存的 `file_sha256`/`pcm_sha256`）判断，device 漂移只记录、不拒。同理，dev 节点读到的 device 不能推断云端容器的 device，要拿真值只能在目标容器里读。侧车只能记录 producer 侧 device，consumer 侧 device 只能落在回执与日志里。

LM 的两个执行门：`spk2id.json` 需要执行门，缺失时 `train.py` 会从“按名字重组分类头”退回“按索引切片”（357,822 → 前 115,362 行），形状合法且 `strict=False`，会静默训错；r3 已加“存在→sha→非空→整数编号→len==119,274→读 LM 标签重数 115,362→全覆盖”。`RECIPE` 要显式传包内 `resume.yaml` 并断言相等。首屏见 `LM_GATE_REFUSED` 或 `resumed optimizer state` 就停止排查；本次 LM 是冷启动（`model_ckpt loads model parameters only; optimizer/scaler start fresh`）。

### 标注 v2/v3/v4：三次失败的边界（2026-11-08 复核）

本节按现场原件分条写，不合成“11 月 7—8 日 v2/v3 两次失败”一段。三代的日期与失败形态不能互相代入：171 帧崩溃是 2026-11-01 的 v3 冻结包事故；11-07—08 是另一条 handoff 序列；v4 的失败和这两次都不同。

① 引擎死在 171 帧的短源上（2026-11-01，v3 冻结包 `37b1d5dd…`）。失败的直接原因是 CN-Celeb2 的 `id10052/live_broadcast-04-007.flac`：442 B、16 kHz、只有 171 帧（0.0107 秒）。窗口规划把它整段当一个窗口，而 `torch.stft`（`n_fft=400`、`center=True` 两侧各 pad 200）要求输入 ≥201 帧，于是 `RuntimeError: padding (200,200) at dimension 2 of input [1,1,171]`，worker 无法 ACK，任务在 11-01 13:14 终态失败。旧引擎没有处理这种短源的路径，所以“续跑既有生产者”必然复现同一崩溃。
复核：`grep -h "padding (200" <run-v1>/resources-attempt1/worker-7/worker.log`。

② device 预检不能当“内容变了”的门（11-07）。device 只是挂载命名空间的标签：同一个文件在开发节点读到 `57`，在集群 GPFS 命名空间记 `2097190`，在另一套容器挂载里又读成 `75`，而 inode/bytes/mtime/ctime 完全相同，内容并没有变。现在 `tools/open_annotation/device_preflight.py` 的语义是：device 不符只打印 `PREFLIGHT_DEVICE_MISMATCH`，回执里记 `device_mismatch_observed:true` / `device_relaxed:true`，然后继续；只有内容不符才打印 `PREFLIGHT_IDENTITY_MISMATCH` 并 `exit 21`。预检只 `stat` 加写 stdout，在 `gpu_launch.main()` 的 `run()` 之前调用，所以 `exit 21` 时没 claim 任何租约。放宽 device 与放宽内容身份是两件事，不能一起松。
复核：`grep -n "PREFLIGHT_DEVICE_MISMATCH\|PREFLIGHT_IDENTITY_MISMATCH" tools/open_annotation/device_preflight.py`。

> 一条不能当已核事实的旧说法：“11-07 的 v2 生产任务在 `PREFLIGHT_DEVICE_MISMATCH expected=2097190 actual=orphan_source:75,…` 处 `exit 21`”只出现在 `7d03d3c` 的提交说明和 `device_preflight.py` 的 docstring 里；本次没有找到该任务的日志或 `failure.json`，无法独立复核。另外 `admission-20261107/admission-attempt-v2-result.json` 是另一个“v2”，失败原因是 `ValueError: explicit input pin required`，与 exit 21 不是同一件事，引用时要把两个“v2”分开。

④ `bounded-speed-*.claim.json` 是“一链一生产者”的硬门，退役要留证据才算退役。生产声明写进 `.formal-parent-locks/bounded-speed-<sha>.claim.json` 后，就绑定该生产者的核心（`new_contract` / `new_bundle` / `new_run_root` / index / parent index 等）。换引擎后核心必然不同，`bounded_speed_runtime.py` 会抛 `another bounded producer was permanently claimed; inspect prior results, do not rerun`，这是护栏，不是故障。要换成新生产者，退役流程按顺序做：

1. 按字节归档原 `claim.json`（连同同名 `.sha256`）到证据目录，本次在 `/root/codex_artifacts/retired-claims-20261108/`；
2. 写清理由：原声明时间、声称的 `new_run_root`、任务终态与崩溃形态、为什么旧引擎不可能继续、为什么新引擎算不同生产者；
3. 写清回滚方法（复制回 `.formal-parent-locks/` 并删除新声明），最后才从原位置删除。

反过来做（先删再补理由）会毁掉“这个生产者真的跑过”的现场；用“再提一次试试”绕过 claim 同样不行。

> 归档目录里的 `.sha256` 是裸哈希，不是 `sha256sum -c` 能吃的格式：文件里只有 64 位哈希、没有文件名，`sha256sum -c` 会报 `no properly formatted SHA256 checksum lines found`。要机器校验得按 `hash  filename` 重新生成一行。另外别只看路径：原位置现在有一个同名、不同字节的新 claim（`created_utc` 更晚、`new_run_root` 指向 `handoff-v4r2-20261108-v4`）。只 `ls` 看到文件还在就判“没退役”会误判，只信“已退役”又看不到新声明，两种情况都要比字节。
> 复核：`cat /root/codex_artifacts/retired-claims-20261108/*.sha256`、`sha256sum <原地 claim> <归档 claim>`。

退役只解除阻塞，不证明新生产者已准入。“准入通过”也不等于“能跑”：admission v5 在 11-07 14:55 `passed:true`，一小时后 v4 生产在 worker 初始化/CUDA 分配阶段超时、`labels` 0 条。新包仍要自己的 pilot 与 admission，跑起来之后还要自己的首片证据。
