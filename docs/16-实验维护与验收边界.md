## 自动标注怎样进入下一步

来源身份至少区分编码文件摘要、解码后原采样率多通道 PCM 摘要、模型实际单声道输入摘要和各自采样时钟。旧 FireRed 标注若只有路径、大小、时间与采样时钟绑定，就照实保存这种较弱身份，不能补写成旧原音 SHA 已核。

原始模型时间、库内修补时间和最终候选单位分别保存。新十进制原钟与legacy重建规则分版；撇号A/B仅作文字条件诊断，不提训练资格。运行中的旧标注包不热更新，当前仓库包导入修复也不能冒充旧A/B实测源码。零长、倒置、越界、超出支持语言、空转写、生成截断和未决读法必须完整计账；不能删除失败样本来改善分母，也不能裁切、均分粗词或把修补后的正长度当成完整字正确。

完整字消费工具默认只提出待核候选。工程格式导出也必须保留 `usable_for_training=false`、`usable_for_evaluation=false`、边界待审核状态、未核实说话人身份和独立的工程用途分组。正式训练和评测的默认输入检查仍应拒绝这些候选。显式请求导出而全部被拒绝，命令必须返回失败；默认只做完整计账时，成功退出只表示检查完成。

## 恢复与发布怎样验收

标注任务的恢复需用同合同、同原音、同源码的完整基线进行逐源比较。统计复用的旧结果与实际新执行的结果，核对旧文件字节和修改时间、缓存确实被消费、缺少阶段实际重新执行。若模型对批次组合敏感，就不能在恢复时改变未绑定的批次组合；单窗执行只消除这一项隐含影响，不保证模型答案正确。

发布记录必须绑定真实输出和对应输入，不能仅相信父进程退出码。对并发代次、锁、计算进程和资源归还的检查有现场条件，不属于合成 CPU 测试可以替代的部分。正式新任务若已经取得持久作业声明，后续失败应进入显式接续方案；不要删除声明或盲目重提来绕开去重。

**自动标注的准入集合**：`worker.py` 在合同的 `engine_source_files`（16 项）里，而 `check_formal_bundle()` 对引擎源是无条件等式（第 214–215 行）。所以**改 `worker.py` 必须用新包重跑 native pilot 并出新 admission**；`REVIEWABLE_CONTROL` 的白名单只有 4 个 CPU helper（`native_batch_admission.py`、`native_batch_readback.py`、`native_batch_queue_handoff.py`、`bounded_speed_runtime.py`），且要引擎源全等之后才轮到它。pilot 的规模门在 `_full_check_native_selected_pilot()` 第 247–248 行：production 必须 **n≥3000 且 rc==512**，300 条不够。

**cohort 改名是必要条件，不是清理**。崩溃前各源组的 `plan.json` 已写盘并绑着旧 `store_identity`，未提交 cohort 缺少整批结果。不把 8 个在途分片的组目录移出 live 根，续跑会先撞 `stored fixed plan identity differs`（换了包），若身份恰好未变则撞 `no partial retry`（护栏少给一行）。改名同时保留了"崩在哪一组"的现场；删除则不可接受。

**`st_dev` 的语义**：device 由挂载命名空间决定——同一批侧车在 dev 节点读到 `57`，在八卡容器里记录为 `2097190`。因此 device **不能进"内容身份"等式**：内容是否变过由 `inode/bytes/mtime_ns/ctime_ns`（以及已存的 `file_sha256`/`pcm_sha256`）判断，device 漂移只记录、不拒。同理，**不能用 dev 节点读数推断云端容器**的 device；要拿真值只能在目标容器里读。侧车只能记录 producer 侧 device，consumer 侧 device 只能落在回执与日志里。

**LM 的两个执行门**：`spk2id.json` 必须有执行门——缺失时 `train.py` 会从"按名字重组分类头"退回"按索引切片"（357,822 → 前 115,362 行），形状合法且 `strict=False`，会**静默训错**；r3 已加"存在→sha→非空→整数编号→len==119,274→读 LM 标签重数 115,362→全覆盖"。`RECIPE` 必须显式传包内 `resume.yaml` 并断言相等。首屏见 `LM_GATE_REFUSED` 或 `resumed optimizer state` 即停——本次 LM 是冷启动（`model_ckpt loads model parameters only; optimizer/scaler start fresh`）。

### 11月7—8日：标注 v2/v3 两次失败留下的教训

**① device 预检不能当"内容变了"的门。** v2 生产任务（11-07）在 `PREFLIGHT_DEVICE_MISMATCH expected=2097190 actual=orphan_source:75,…` 处 `exit 21`，一个 cohort、一份租约都还没开就在 CUDA 之前停了。原因是 device 只是**挂载命名空间的标签**：同一个文件在开发节点读到 `57`，在集群 GPFS 命名空间记 `2097190`，在另一套容器挂载里又读成 `75`，而 inode/bytes/mtime/ctime 完全相同，内容并没有变。现在 `tools/open_annotation/device_preflight.py` 的语义是：device 不符只打印 `PREFLIGHT_DEVICE_MISMATCH`，回执里记 `device_mismatch_observed:true` / `device_relaxed:true`，**继续**；只有内容不符（inode/bytes，以及记录里给出的 mtime_ns/ctime_ns）才打印 `PREFLIGHT_IDENTITY_MISMATCH` 并 `exit 21`。预检只 `stat` 加写 stdout，在 `gpu_launch.main()` 的 `run()` 之前调用，所以 `exit 21` 时没 claim 任何租约。**放宽 device 不等于放宽内容身份**，这两件事不能一起松。

**② 引擎死在 171 帧的短源上，靠"接续旧生产者"救不回来。** v3 冻结包（`37b1d5dd…`）失败的直接原因是 CN-Celeb2 的 `id10052/live_broadcast-04-007.flac`：442 B、16 kHz、只有 171 帧（0.0107 秒）。窗口规划把它整段当一个窗口，而 `torch.stft`（`n_fft=400`、`center=True` 两侧各 pad 200）要求输入 ≥201 帧，于是 `RuntimeError: padding (200,200) at dimension 2 of input [1,1,171]`，worker 无法 ACK，任务在 11-01 13:14 终态失败。**旧引擎不可能完成这个源**，所以走"续跑既有生产者"必然复现同一崩溃；要修就得出新包、重跑 native pilot、拿新 admission（v4 系列就是这么做的），不能指望同一份冻结包下次能过。

**③ `bounded-speed-*.claim.json` 是"一链一生产者"的硬门，退役要留证据才算退役。** 生产声明写进 `.formal-parent-locks/bounded-speed-<sha>.claim.json` 后，就绑定该生产者的核心（`new_contract` / `new_bundle` / `new_run_root` / index / parent index 等）。换引擎后核心必然不同，`bounded_speed_runtime.py` 会抛 `another bounded producer was permanently claimed; inspect prior results, do not rerun`——这是护栏，不是故障。要换成新生产者，退役流程必须按顺序做：

1. **按字节归档**原 `claim.json`（连同同名 `.sha256`）到证据目录，本次在 `/root/codex_artifacts/retired-claims-20261108/`；
2. **写清理由**：原声明时间、声称的 `new_run_root`、任务终态与崩溃形态、为什么旧引擎不可能继续、为什么新引擎算不同生产者；
3. **写清回滚方法**（复制回 `.formal-parent-locks/` 并删除新声明），**最后**才从原位置删除。

反过来做（先删再补理由）等于毁掉"这个生产者真的跑过"的现场；用"再提一次试试"绕过 claim 更不允许。退役只解除阻塞，不证明新生产者已准入——新包仍要自己的 pilot 与 admission。
