## 1. 功能要解决的问题

原来的训练流程对每一句语音都截成同样长：配置里写 `num_frms: 200`，程序就固定取
200 帧（约 2 秒）的音频，短于这个长度的语句用自身的循环复制补足。这样一来：

- 每一批里的张量天然等长，不需要补零，但也永远看不到一句完整的语音；
- 长语句被切掉一大截，短语句被重复播放，模型学到的是"2 秒片段的平均音色"。

**变长训练**改成：每句语音按它自己的真实长度读出来（长句随机截到上限，不重复播放），
同一批里各句长度不同，用右侧补零凑成矩形，并把每句的真实采样点数（`lengths`）
一起交给模型。模型的注意力统计池化（ASTP）和前端会跳过补零帧，只统计真实语音。

**长度分桶**解决的是变长带来的副作用：同一批里如果既有 1 秒又有 8 秒的语音，
补齐到 8 秒就意味着大量算力花在零上。分桶把长度接近的语音放进同一批，
补零比例从约 1.74 降到约 1.07（下面第 5 节有实测数字）。

两件事是分开的：分桶只是"怎么组批"的策略，和模型无关，所以它是一个独立的配置块。

## 2. 怎么开启

在 `dataset_args` 下加两个块：

```yaml
dataset_args:
  varlen:
    enable: true          # 总开关，默认 false
    min_sec: 2.0          # 短于这个长度的语句直接丢掉
    max_sec: 6.0          # 长于这个长度的语句随机截到这个长度
    max_batch_sec: 900.0  # 可选：一批里真实音频秒数之和的上限
  bucketing:
    enable: true          # 分桶，默认 false
    bucket_count: 6       # 分几个长度桶
    bucket_width_sec: 1.0 # 每个桶的宽度（秒）
    shuffle_buckets: true # 随机挑下一个桶，让每批长度有变化
```

默认是关的。不写这两块（或 `enable: false`），训练流程和改动前逐位相同
（第 5.5 节给出了实测证据）。仓库里原有的 18 份固定长度配方一个字都没改。

### 数据去哪了

一批数据从磁盘到模型的顺序是：

```
data.list
  → DataList            （无限流，按 rank/worker 切分、逐轮重新打乱）
  → parse_raw_fast_varlen （读真实长度；关掉时走原来的 parse_raw_fast_and_filter）
  → shuffle             （本批内打乱）
  → spk_to_id           （说话人转编号）
  → resample / speed_perturb
  → random_chunk_range  （随机截到 min_sec..max_sec；关掉时走原来的 random_chunk）
                        （开了第 9 节的 vad_segments 时，这一步换成 vad_select_segment：
                          按语音段边界取完整的一段，而不是随机位置切）
  → 增广（可选）
  → BucketedLengthDataset（可选，把长度接近的攒成一批）
  → collate_varlen      （右侧补零 + lengths）
  → run_epoch → model(wav, lengths=lengths)
```

## 4. 三个容易踩的点

### 4.1 分桶需要 `batch_size=None`

分桶数据集自己攒够 `batch_size` 句才交付一批。如果 `DataLoader` 还带着配方里的
`batch_size`，它会把好几个"已经是一批"的组再摞成一批，结果是 `batch_size` 的平方
（默认 512 时就是 26 万句一批），而且桶被混在一起，分桶就失效了。
所以代码在开启分桶时会自动把 `DataLoader` 的 `batch_size` 设成 `None`，
同时去掉 `drop_last`（torch 不允许两者同时出现；这里也没意义，因为交出来的批本来就是整的）。

### 4.2 分桶路径下 `max_batch_sec` 仍然生效，但基本不会触发

`max_batch_sec` 由 `collate_varlen` 在组批之后按秒数截断。分桶路径下批次由
`BucketedLengthDataset` 先组好，`collate_varlen` 照样会跑，所以这条限制仍然生效
（不是被绕过）；只是因为同一桶内长度接近，"按秒数截断"很少真的触发。
要严格控制显存，调 `bucket_count` 和 `bucket_width_sec`。

### 4.3 变长批不等于逐句推理

右边补零再传 `lengths`，得到的说话人向量和"把这一句单独送进模型"得到的并不完全相等。
实测相对 L2 误差约 0.008（第 5.3 节），小模型上可以低到 1e-6，但不是 1.0 的余弦。
原因是卷积在边界处的取整：前端输出的帧数要截到时间降采样倍数的整数倍，
舍入方式在两种调用下可能差几帧。这是已知的、有意的取舍，不是 bug。

## 5. 实测数字

以下都在本机实测，命令见第 7 节。

### 5.1 补零比例（400 句合成语音，长度 1–10 秒均匀分布，批大小 8）

| 做法 | 平均补零比例 | 最大补零比例 |
|------|--------------|--------------|
| 不分组（按打乱后的顺序组批） | 1.7400 | 2.3773 |
| 长度分桶（6 桶 × 1 秒） | **1.0681** | **1.2492** |

补零比例 = 批内最长长度 ÷ 批内平均长度，1.0 表示完全没有补零。

### 5.2 批内长度是否真的不同、补零是否在右侧

用 8 个合成 wav（0.8 / 1.2 / 2.5 / 3.7 / 4.0 / 5.5 / 6.1 / 7.9 秒，
`min_sec=1.0, max_sec=6.0`）：

```
wav 形状      : (4, 1, 64000)
lengths       : [19200, 40000, 59200, 64000]   dtype=int64
右侧全是零     : True
每句真实前缀非空: True
批内长度不同    : True
```

并且把 `lengths` 和磁盘上文件的真实帧数逐条比对，四句全部相等
（19200 / 40000 / 59200 / 64000）。0.8 秒那句因为短于 `min_sec=1.0` 被丢掉。

### 5.3 传不传 `lengths` 的差别

小模型（能在 CPU 上跑通、比较数值），把 3 句长度 1/1.5/2.25 秒的语音补齐成一批：

| 调用方式 | 与逐句推理的相对 L2 误差 |
|----------|--------------------------|
| `model(wav, lengths=lengths)` | **0.000001** |
| `model(wav)`（补零但不告诉模型真实长度） | **0.331688** |

两者输出的最大绝对差 0.177，说明 `lengths` 确实传进去并起作用了。

用官方 b0 权重（`checkpoints/pretrained/b0-vox2-lm.pt`，731 个张量全部加载）在真实
VoxCeleb2 语音上重复：相对 L2 误差 **0.0083**（带 `lengths`）对 **0.265**（不带），
差距 32 倍。

> 关于余弦：任务里期望的"余弦 0.95–0.99"在本架构上测不出来。
> 原因有两个：小模型上两条路径本来就几乎完全一致（余弦 0.9985–1.0000）；
> 而官方 b0 权重输出近似正交的向量（任意两句余弦约 0.008，非对角均值 0.0001），
> 余弦在这个尺度上没有分辨力。所以上面用相对 L2 误差衡量，它不受向量尺度影响。
> 对外写"余弦等于 1.0"与上面的实测不符。

### 5.4 端到端训练

真实数据（`vox2_dev`，109 万句）单卡，`batch_size=8`、`sample_num_per_epoch=320`、
`num_epochs=1`、`log_batch_interval=1`：

| 配方 | 优化步数 | loss 范围 | NaN | Inf |
|------|----------|-----------|-----|-----|
| `b0/varlen_ptn.yaml`（变长 + 分桶） | 40 | 16.572 – 16.680 | 无 | 无 |
| `b0/ptn.yaml`（原来的固定长度） | 40 | 16.516 – 16.721 | 无 | 无 |

两条路径都跑完了一整个 epoch、存下 `model_1.pt`、并完成了 VoxCeleb1-O 验证。

> 日志里前 15 行的 loss 显示 `nan`，那是原有的取值节奏问题：
> `executor.py` 每 16 步才往 `loss_meter` 里放一次值，而打印是每

## 6. 关于分桶的实现与限制

做法：训练集是无限流（`DataList` 逐轮重新打乱），没有可以按长度排序的索引表。
所以 `BucketedLengthDataset` 为每个长度桶维护一个缓冲区，从流里取样本放进对应的桶，
某个桶攒够 `batch_size` 就交付一批。一批只从一个桶里取，这是分桶的意义所在。

限制：

1. 批次会跨桶边界。桶是 `bucket_width_sec` 宽的左闭右开区间，
   `bucket_width_sec: 1.0` 时 1.9 秒和 2.0 秒分属两桶，但 1.2 秒和 1.9 秒同桶，
   补零比例仍可能到约 1.25。想要更紧就减小桶宽、增加桶数。
2. 缓冲区有内存上限。看未来样本的数量有界（见 `__iter__` 里的
   `lookahead_limit`），所以当长度分布极端偏斜时，可能来不及给某个桶攒满，
   此时会交付一个较小的批次。正常长度分布下不会走到这条路。
3. 最后一批可能偏小。流被耗尽时会把剩下的样本交付出去，批次可能不满。
   真实训练用的是无限流，正常训练不会遇到；只有测试或很小的数据清单才会。
4. 每个 worker 各自分桶。`num_workers > 1` 时各 worker 独立攒桶、独立交付，
   worker 之间不共享桶，所以不同 worker 交付的批次长度可以不同。
   这在训练上没有问题（各 worker 本来就各自算梯度再同步），但因此只保证
   同一批内部来自同一个桶，跨 worker 之间不保证。

## 8. 本次顺带修掉的一个既有问题

`wespeaker_lite/utils/meters.py` 里定义了 `AverageValueMeter` 和 `ClassErrorMeter`
两个类，但 `utils/executor.py:204-205` 是写成 `tnt.meter.AverageValueMeter()` 调的，
而这个模块里没有 `meter` 这个名字。结果是任何训练一开始就报
`AttributeError: module 'wespeaker_lite.utils.meters' has no attribute 'meter'`，
一步都跑不下去。这个问题在改动前就存在，和变长功能无关，
但它挡住了端到端验证，所以 `meters.py` 现在通过替换模块类型把 `meter` 暴露成属性。
为什么不用模块级赋值 `meter = ...`：这个文件在训练进程里会被两条 `sys.path`
各加载一次，两份模块里的类对象不同，`isinstance` 判断会落空（`meters.py:121-176`
有实测记录）。属性形式按进程唯一，两条路径拿到同一个命名空间。

## 9. 按语音边界取样：`dataset_args.vad_segments`

前面几节讲的是"变长"和"分桶"。这一节讲的是怎么决定取哪一段。

默认的变长取样（`random_chunk_range`）是在音频里随机位置切一段。
问题是它会切在语音中间——半句话、半个字被切开，送进模型的是一个
不完整的音素。按语音活动的边界来切，可以让切点落在标注的语音段边界上，
不把一段连续语音从中间切断。这一节就是这个开关。

这里的「完整」只指不切断 VAD 标出的那一段语音，不是字边界：
VAD 段可能从字中间开始、也在字中间结束。真正的完整字要 ASR 文字、
字序、字时间与边界审核，那是 `word_ft` 那条线（见第 9.5 节末尾与 09 开头）。

### 9.1 前提：先给音频做语音标注

需要每条音频旁边有一份语音分段文件。默认约定是
**音频文件名后面再补一个 `.rttm`**：

```text
.../id00012/21Uxsk56VDQ/00001.wav        <- 音频
.../id00012/21Uxsk56VDQ/00001.wav.rttm   <- 它旁边这份就是分段文件
```

分段文件用标准 RTTM 格式，只写语音段。怎么批量生成见
[09 用语音活动检测给训练音频加时间标注](09-VAD标注与RTTM.md)。

### 9.2 怎么开启

在配方的 `dataset_args` 里加一段（不写就是关闭，行为与从前完全一样）：

```yaml
dataset_args:
  vad_segments:
    enable: true
    rttm_suffix: .rttm       # 分段文件名后缀：a.wav -> a.wav.rttm
    min_sec: 1.0             # 取出来的片段最短多长
    max_sec: 6.0             # 最长多长
    target_sec: 3.0          # 想要的长度，默认取 min 与 max 的中点
    pad_sec: 0.1             # 两端各留一点余量
    cut_policy: middle       # 单段太长只能切开时，取中段还是随机一段
```

**这个开关要求 `dataset_args.varlen.enable` 同时为 `true`。** 片段长度本来就是
变化的，只有走变长读取才拿得到真实长度、也只有变长那条汇总会补零并回传
`lengths`。只开 `vad_segments` 不开 `varlen` 会在建数据集时直接报错，
而不是悄悄按固定长度跑出一个长度不对的结果。

仓库里已经放了 6 份开好的配方：

| 文件 | 说明 |
|------|------|
| `examples/vox2/recipes/redimnet2/b0/vadseg_ptn.yaml` | 只练 VoxCeleb2，B0 主训练 |
| `examples/vox2/recipes/redimnet2/b0/vadseg_lm.yaml` | 同上，大间隔微调 |
| `examples/vox2/recipes/redimnet2/b3/vadseg_ptn.yaml` | B3 主训练 |
| `examples/vox2/recipes/redimnet2/b3/vadseg_lm.yaml` | 同上，大间隔微调 |
| `examples/vb2_vox2_cnc2/recipes/redimnet2/b3/vadseg_ptn.yaml` | 混合数据线 B3 主训练 |
| `examples/vb2_vox2_cnc2/recipes/redimnet2/b6/vadseg_ptn.yaml` | 混合数据线 B6 主训练 |

这 6 份是从对应的 `varlen_*.yaml` 复制后只加 `vad_segments` 一个块（再把
`exp_dir` 换个名字）得到的，其它训练设置完全一致——所以想比较"随机位置切"
和"按语音边界切"的效果，两份配方可以直接对照着跑。
原来那 18 份固定长度的配方、以及 6 份 `varlen_*.yaml` 一个字节都没有改。

### 9.3 全部配置项

| 配置项 | 默认值 | 意思 |
|--------|--------|------|
| `enable` | `false` | 总开关 |
| `rttm_suffix` | `.rttm` | 分段文件名后缀 |
| `rttm_root` | 不填 | 分段文件不在音频旁边时，改到这个根目录下按镜像结构找 |
| `rttm_root_depth` | `2` | 用 `rttm_root` 时，除文件名外再保留几层上级目录名 |
| `audio_root` | 不填 | 用 `rttm_root` 镜像时，音频路径的公共前缀（用来算相对路径） |
| `min_sec` / `max_sec` | 沿用 `varlen` 的同名项（默认 `1.0` / `8.0`；仓库配方里写的是 `6.0`） | 片段时长范围；不写就跟着变长那一套走，保证两处对"合法长度"的理解一致 |
| `target_sec` | 上下限中点 | 想要的时长 |
| `pad_sec` | `0.1` | 两端各留的余量。留一点是为了不正好切在语音的第一帧上——挑剔的分段器常把边界前的十几毫秒也标成静音 |
| `merge_gap_sec` | `None`（按 `0.0` 处理） | 相邻语音段间隔小于它就并成一段。**独立于 `pad_sec`**，理由见 9.4 末尾 |
| `min_speech_sec` | 等于 `min_sec` | 片段里真正语音的下限 |
| `cut_policy` | `middle` | 单段长于 `max_sec`、只能在段内部切开时：取中段还是随机一段 |
| `missing_policy` | `fallback` | **分段文件不在**或读不出可用段时：`fallback` 退回随机切，`drop` 丢掉这条样本 |
| `low_speech_policy` | `resample` | 选出的片段语音太少时：`resample` 换个起点重挑（最多 `low_speech_retries` 次），`keep` 照用，`drop` 丢掉 |
| `low_speech_retries` | `2` | `resample` 最多重试几次 |
| `fallback_min_sec` / `fallback_max_sec` | — | **配方里写了不生效**：这两个只在 `vad_select_segment` 里作为函数参数存在，不在配置白名单内，YAML 传进去会被丢掉 |
| `fallback_chunk_sec` | `3.0` | 拿不到音频真实长度时，随机切多长 |
| `read_fail_policy` | `fallback` | 选好的片段读失败时：退回随机切还是丢掉 |

### 9.4 挑选规则（这是本节的核心）

它按顺序做这几件事，每一步都具体到能对照日志：

1. 先把挨得很近的语音段并起来（间隔小于 `merge_gap_sec`）。合并后的区间
   就是"可选的整段"，片段的起点终点只能落在它们的边界上。
   `merge_gap_sec` 默认是 0，也就是只并真正重叠或首尾相接的段——
   它不跟着 `pad_sec` 走，原因见本节末尾那段说明。
2. 把连续的若干个整段并起来，凑到最接近 `target_sec` 的那个区间。
   这里会把"用 1 段""用 2 段""用 3 段"……所有可能都算一遍，
   取全局最接近目标的那个，而不是能用 1 段就停。
   两者差别很大：4 段语音各约 0.7～1.4 秒、目标 3.0 秒时，
   "能用 1 段就停"只给出 1.4 秒，而并两段能得到 2.6 或 3.4 秒。
   若有多个区间一样接近目标（比如四段各 1.2 秒、目标 1.2 秒），
   就在这些平手项里随机取一个，不会永远从第一条语音开始切。
3. 只有当单独一段就长于 `max_sec` 时，才不得不在这一段内部切开，
   按 `cut_policy` 取中段或随机一段。这是唯一会切到语音中间的情况，
   日志里会计入 `vad_cut_inside`。
4. 两端各加 `pad_sec` 的余量，再落到音频范围里：
   * 放得下就两头都加满，片段以语音段边界为中心；
   * 某一头放不下（片段贴着文件开头或末尾），就把整个片段平移，
     让放不下的那头贴住文件边缘。这一条会记成"未对齐"；
   * 平移之后，另一头的余量会被夹回 `pad_sec` 以内。也就是说
     不会出现"一头 0、另一头 2 倍余量"的情形 —— 宁可片段短一点，
     也不悄悄多塞静音。这一条也记成"未对齐"；
   * 只有片段比整条音频还长，才会缩得更多。

   > 为什么用"平移"而不是"两头各缩一半"：对称缩短会让片段变短，实测最短
   > 只剩 3.5 秒（比目标短一截），而且两个边界会同时离开语音段边界。
   >
   > 但只平移不夹余量是不够的，这里踩过一个坑：分段
   > `[(0.0,7.640),(7.890,9.984)]`、音频 9.984 秒、`pad_sec=0.2` 时，
   > 右端放不下、整段左移 0.200，于是左余量变成 0.400（请求的两倍）、
   > 右余量变成 0。实测 200 条真实音频里有 **19.5%** 的片段是这种双倍余量。
   > 现在平移之后会把多出来的那头夹回去，实测同一批数据超标 **0** 个。

> 为什么 `merge_gap_sec` 默认不跟着 `pad_sec` 走。余量是对称地往两头扩的，
> 所以它只覆盖片段两端以外的范围，不会把片段内部那条静音缝隙补上。
> 这里踩过一次坑：早先的写法让合并阈值等于 `pad_sec`，于是"扩完余量才连上"
> 的区间被并成了一段，随后又按"不许切段"的规则把起点放在合并区间的左端——
> 可它中间那条缝隙还在。实测 `id03722/.../00011.wav` 就选出 (2.060, 5.888)，
> 而那里的语音段是 (2.26, 3.36) 与 (3.68, 5.888)：区间正中躺着一整段
> 0.32 秒的静音，起点也不在任何语音段的边界上。现在合并阈值独立配置、
> 默认 0，这个情况不会再出现。

### 9.5 实测数字

这里检查的是取段端点与 FireRedVAD 标注边界的关系，不是人工完整字边界。用 30 条真实 VoxCeleb2 音频 + FireRedVAD
真实标注逐条检查，参数照抄仓库里 `vadseg_ptn.yaml` 的写法
（`min_sec: 1.0`、`max_sec: 6.0`、`target_sec: 3.5`、`pad_sec: 0.1`）：

| 情况 | 条数 |
|------|------|
| 端点正好落在语音段边界上 | 29（单段 25 + 并段 4） |
| 单段本身长于上限、只能段内切 | 1 |
| 除上面 1 条允许段内切的情况外，未按标注边界取段 | 0 |

"端点落在边界上"的口径说清楚：加余量之后，片段的起点等于
`某个语音段的起点 − pad_sec`，终点等于 `某个语音段的终点 + pad_sec`。
如果片段顶到了文件开头或末尾，余量放不下时片段整体平移，
此时一头贴住文件边缘、另一头的余量仍不超过 `pad_sec`——这也算对齐。
只有"单独一段就长于 `max_sec`"这一种情况允许切在语音中间。

片段里语音占多少：中位 96.5%，最低 81.1%。这里要把话说准，
因为很容易想当然：在没有触发段内切回退时，片段包住它选中的标注语音段，
但标注本身可能漏掉字首或字尾，片段内部也未必全是语音。两个来源：

* 并段时，被并起来的相邻语音段之间那点停顿会一起被包进来；
* 两端各留的 `pad_sec` 余量本身也不是语音。

同一批数据上实测"选中区间与语音段的重叠 ÷ 区间长度"：

| 模式 | 条数 | 最小 | 中位 |
|------|------|------|------|
| 单段 | 25 | 93.01% | 96.83% |
| 并段 | 4 | 81.08% | 88.58% |
| 段内切 | 1 | 100.00% | 100.00% |
| **合计** | 30 | **81.08%** | **96.46%** |

因此，这个检查只能说明：未触发段内切回退的片段按 VAD 标注段取样。
它既不能证明标注段把字切完整（字边界未截断），也不能证明"整段都是语音"。长段回退本身允许切在语音中间；
完整字微调实验（`word_ft` 线）还需要文字、发生序号、字词时间及边界审核，见 [实验维护与验收边界](16-实验维护与验收边界.md)。

用更大的样本复核过这个结论（跨说话人分层抽 150 条真实 VoxCeleb2，
每条抽 10 次，共 1500 个片段）：

| 模式 | 片段数 | 语音占比最小 | 中位 |
|------|--------|-------------|------|
| 单段 | 1140 | 100.00% | 100.00% |
| 并段 | 190 | **85.13%** | **95.15%** |
| 段内切 | 170 | 100.00% | 100.00% |

只有"并段"这一种的语音占比会低于 100%，原因就是被并起来的相邻语音段
之间那点停顿被一起包了进来；单段与段内切都是 100%（它们本来就落在语音里）。
所以"多段音频会被并段、并段会带进停顿"是这里唯一会损失语音占比的地方。

想要语音占比更高，最直接的办法是调小 `pad_sec`（余量本身不是语音）；
并段带来的那部分停顿只能靠"不并段"来避免，也就是把 `merge_gap_sec`
保持默认的 `0`——它已经只并真正重叠或首尾相接的段，没有更小的空间可调了。
另一个办法是把 `target_sec` 调小：目标越短，越容易只用一段就凑够，
上面那组数据里 `target_sec` 从 3.0 降到 2.0 时，并段的比例从 190/1500
降到 20/1500。

多久会走"段内切"那条路，主要看 `max_sec` 相对单段长度有多大。
一条音频如果只有一整段连续语音、而且比 `max_sec` 还长，就只能段内切。
上面这 30 条里最长单段的中位数是 3.88 秒、最大 12.32 秒，
其中只有 2 条的最长单段超过 6.0 秒。同一批数据换个上限，段内切的比例差很多：

| `max_sec` | 单段 | 并段 | 段内切 |
|-----------|------|------|--------|
| 6.0（配方用的值） | 25 | 4 | **1** |
| 4.0 | 22 | 2 | 6 |
| 3.0 | 17 | 3 | 10 |

跨说话人分层抽 120 条实测，**38% 只有一段、62% 有多段**
（段数中位 2、最多 7），最长单段中位 4.59 秒。
所以把 `max_sec` 调小到接近常见段长，段内切的比例会明显上升——
这是正常现象，不是算错了。反过来说，也不是每一条都严格对齐：
日志里 `vad_cut_inside` 的条数就是这个比例，跑之前看这个数即可判断。

和分桶一起用是合适的。400 条真实长度（取自上面这 30 条的片段长度分布）上
实测补齐比例（= 批内最长 ÷ 批内平均，1.0 表示一点零都没补）：

| 做法 | 平均补齐比例 | 最大 |
|------|------------|------|
| 只开 `vad_segments`（按流顺序组批） | 1.2462 | 1.4595 |
| 再开分桶（6 桶 × 1 秒） | **1.0737** | **1.1743** |

分桶后的 50 个批次全部只来自同一个长度桶（50/50），
说明两者叠在一起时"一批一个桶"没有被破坏。

### 9.6 怎么看它有没有在正常工作

启动时（数据集刚建好、还没开始训练）会打印一行实际生效的配置。
下面是一段真实输出：

```text
VAD_SEG : enabled, {'enable': True, 'rttm_suffix': '.rttm', 'rttm_root': None,
 'rttm_root_depth': 2, 'target_sec': 3.5, 'pad_sec': 0.1, 'min_speech_sec': 1.0,
 'merge_gap_sec': None, 'cut_policy': 'middle', 'missing_policy': 'fallback',
 'low_speech_policy': 'resample', 'low_speech_retries': 2,
 'read_fail_policy': 'fallback', 'fallback_chunk_sec': 3.0, 'audio_root': None,
 'min_sec': 1.0, 'max_sec': 6.0}
```

（真实输出是一整行，这里为方便阅读折了行。）
没开这个开关时不会打印这一行——所以看到它就说明配置读到并生效了。
变长和分桶两个开关一起开时，`VARLEN`、`BUCKETING`、`VAD_SEG` 三行都会打印。

跑完一个 epoch 会打一条汇总，长这样：

```text
[dataset] VAD 取样统计（本进程 / 本 worker）: cut_inside=1, fallback_random=5, merge=4, single=25
```

（这一行是实际日志。`single + merge + cut_inside` 等于本进程产出的
样本数：25 + 4 + 1 = 30，和上面第 9.5 节那张表的 30 条对得上。
早先这里写的是 `cut_inside=2`，加起来变成 36 —— 那是把段内切算了两遍的
旧代码留下的日志，代码已修，示例也一并改过来了。）

这条汇总只在 `num_workers: 0`（单进程读数据）时才看得到。
配方默认是 `num_workers: 16`，计数分散在各个 worker 进程里、不会汇总回来，
所以实际训练时看不到这条汇总，上面那个 `cut_inside` 比例也就无从得知。
要查看就临时把 `num_workers` 设成 0 跑一小段，或者看
`vad_cut_inside` 那几条带路径的明细。

各计数的意思：

| 日志里的名字 | 意思 |
|--------------|------|
| `single` | 一段语音就够长，片段就是那一段（正常，多数样本走这条） |
| `merge` | 连着并了好几段才凑够长度（正常） |
| `cut_inside` | 单段本身就长于 `max_sec`、只能段内切。**不是错误**，但想知道"多少比例没严格对齐"就看它 |
| `fallback_random` | 没找到分段文件，按 `missing_policy: fallback` 退回了随机切 |
| `vad_cut_inside` | 上面那个 `cut_inside` 的头几条明细（会打印路径和那一段的长度） |
| `vad_no_rttm` | 旁边没有分段文件、且 `missing_policy: drop`，样本被丢掉 |
| `vad_bad_rttm` | 分段文件在但读不出可用段 |
| `vad_low_speech` | 选出的片段语音太少 |

前几条明细会带路径打到 `stderr`，形如：

```text
[dataset][DROP:vad_cut_inside] .../id04155/XPMlzQgXKaE/00175.wav 单段语音长 9.216s，超过 max_sec=6.000s，只能在段内部切开（切出 3.700s）
```

`vad_cut_inside` 的措辞是说清"被切的那一整段有多长、切出来多长"，
而不是拿切完的长度去和 `max_sec` 比。

> 这些计数都是按进程的：开了 `num_workers` 之后每个 worker 各算各的，
> 主进程那条汇总通常看不到数——每个 worker 是独立进程，它自己的计数不会汇总回来。
> 想知道整体比例，要么用 `num_workers: 1` 跑一小段，要么直接统计一批 RTTM 文件。

### 9.8 已知限制

1. VoxCeleb2 这类"一整段连续语音"的音频本来就很难按边界取段。
   它们只有一段语音，只要这段比 `max_sec` 长，就只能段内切。
   想让这部分也严格对齐，要么把 `max_sec` 放大，
   要么用 `cut_policy: random` 至少保证切点位置随机。
2. `pad_sec` 加出来的余量不算语音。检查 `min_speech_sec` 时已经把
   余量排除在外了，所以调大 `pad_sec` 不会让"语音太少"的检查变松。
3. 计数是按进程的。开了 `num_workers` 之后每个 worker 是独立进程、
   各算各的，主进程那条汇总通常一条数都没有。这和 `processor.py` 里
   其他丢弃计数（`short_audio`、`read_failed` 等）是同一套机制。
4. `rttm_root` 镜像模式有重名风险：不同语料里都有
   `<说话人>/<视频>/00001.wav` 这种重名文件，所以默认保留两层上级目录名
   （`rttm_root_depth: 2`）。层数留少了会让不同音频的标注互相覆盖——
   生成标注那一步已经带了重名检查，训练侧这边只是按同样的规则去找。
