# 跨节点保留旧结果，并只准备真正缺失的来源

`portable_source_identity.py`为新的后继协议提供内容证明，`prepare_speed_continuation.py`增加显式入口。它们不修改旧producer、旧合同、冻结源码、队列、侧车、commit或阶段缓存；也不会删除设备号后伪称旧stat仍然相同。原来的严格读取和默认准备方式保持不变。

本轮的原因是共享原音在不同容器中可能具有不同device，但旧worker把完整stat作为复用条件。旧记录的device不能被修改，新节点的实际device也不能被伪造。本工具只允许这个明确差异，同时实际读取编码原音，证明其SHA256仍与旧发布记录一致。新后继使用独立版本、队列和标签，不调用旧worker去绕过旧stat检查。

## 固定的新协议

新描述schema为`annotation-portable-source-spec/v1`，内容身份模式为`portable_encoded_sha256/v1`。示例中的摘要是说明文字，不能直接执行：

```json
{
  "schema": "annotation-portable-source-spec/v1",
  "purpose": "production",
  "source_identity_mode": "portable_encoded_sha256/v1",
  "old_contract": {"path": "/absolute/original/silver.json", "sha256": "旧合同实际SHA256"},
  "full_index": {"path": "/absolute/original/index.json", "sha256": "原全集实际SHA256"},
  "old_queue_root": "/absolute/original/queue",
  "old_sidecar_tree": "/absolute/original/labels/original-version",
  "source_alias": {"alias_path": "/root/group-shared", "target_path": "/shared/group-shared"},
  "allowed_difference": ["device"],
  "encoded_hash_algorithm": "sha256",
  "model_API_calls_allowed": 0,
  "release_training_labels": false
}
```

正式模式只接受这对已明确的共享挂载别名。现场必须仍是同一软链接目标，别名以下不允许另有未声明软链或上级目录跳转。原source中的`audio_path`保持原文，只在实际读取时解析这个明确关系。`cpu_fixture`只用于小规模合成数据，不能替代正式三域总数或资源验收。

准备时将描述中的旧合同引用、原全集引用、旧队列及旧标签树与实际输入逐项比较；不能换一份合同或索引后继续使用旧描述。`allowed_difference`必须恰为`["device"]`，不能扩为inode、时间或字节数。正式原分母仍是11,521,178，剩余数量不能替代它。

## 每个保留来源怎样验证

只有当前部分片和未领取片中确实存在的旧发布结果需要新内容账本。工具先重开旧侧车和commit，验证完整source、旧合同、job key、提交的字节数与摘要、机器决定及资格未释放，再读取原音。

对`decoded_complete`记录，要求：

1. 旧`stat_before`与`stat_after`完整且相同，包括device、inode、bytes、mtime_ns和ctime_ns；旧编码SHA256存在。
2. 当前读取的完整stat与旧记录只可能在device不同，其他四项必须完全相同。任一其他差异直接拒绝，不能仅因SHA相同便忽略它。
3. 使用同一个只读文件描述符（FD）流式读取实际编码原件并计算SHA256；原件必须是普通文件。读取前后FD和路径的完整stat均相同，明确别名也必须仍指向原目标。
4. 实际编码摘要必须等于旧`source_identity.file_sha256`。只有目录、时间、inode或挂载关系相同，没有实际读内容，不能报告内容通过。

这里证明的是编码原件相同，没有重新解码脉冲编码调制（PCM）、转写或定位。账本保留旧source_identity整体摘要、旧PCM摘要及策略，固定`PCM_redecoded=false`；不能把旧PCM字段冒充本次新解码输出。

旧记录如果确实是解码失败且决定为failed，仍保留原失败、原producer及commit，不自动重算；账本状态明确为`historical_decode_failure_preserved_not_content_verified`，实际新hash/stat为空，内容通过为false。它不能计入本次内容验证成功数，更不能变成可训练数据。候选或unknown若原件成功解码，仍必须经过上述完整内容证明。

账本schema为`annotation-portable-source-evidence/v1`。每行绑定描述SHA、source ID及原记录摘要、旧侧车/commit摘要、旧合同、原路径及实际读取路径、旧编码SHA、实际编码SHA、完整新旧stat、实际读取字节数和观察时间。旧stat与实际stat分别保存，绝不覆盖。成功状态是`encoded_content_verified`，仍固定`training_or_evaluation_eligibility_released=false`。

## 避免对一千多万个缺失路径逐个查询共享盘

新portable final模式先在旧父锁内用`os.scandir`流式遍历旧版本树，将确实存在的侧车及commit目录项登记到新的SQLite数据库。目录项成对核对，软链接、未知临时残件、孤儿、缺少的完成片结果以及不属于原索引的额外路径均保留原件并拒绝。已知`.stage_cache`根明确跳过，并在报告中记为没有遍历、没有复用；不能借此宣称旧缓存已完整检查。

随后流式读取原索引的全部来源记录。缺失来源先查SQLite，不执行原路径的`exists`、stat或父目录软链查询；只有目录项命中才真正打开旧侧车和原音。已封账来源也仅用原来源文本登记目录项覆盖，完成片引用仍保留原摘要。数据库使用文件临时区和有限缓存，来源ID不整体塞进Python集合；账本逐行写出，不把所有保留来源收集到内存。

SQLite的`paths`表按原`sidecar_relpath`唯一，保存sidecar/commit标记、原source ID、completed/partial/unclaimed类型及是否被原索引匹配；全部旧目录项必须恰被原来源匹配。成功后发布目录项数据库SHA及扫描计数。清单说明一个受旧writer锁保护的观察快照，不能替代平台身份认证或后续互斥。

这个优化只在显式portable模式生效。旧strict准备仍沿原规则，不能悄悄把其stat检查换成可移植内容规则。

## 准备命令及输出

```bash
python3 -B tools/open_annotation/prepare_speed_continuation.py \
  --index /absolute/original/index.json --index-sha '<原全集SHA256>' \
  --queue-root /absolute/original/queue \
  --old-contract /absolute/original/silver.json --old-contract-sha '<旧合同SHA256>' \
  --old-sidecar-tree /absolute/original/labels/original-version \
  --output /absolute/new/preparation \
  --execute-final \
  --terminal-observation /absolute/private/terminal.json --terminal-sha '<真实终态原件SHA256>' \
  --old-task-id '<原任务ID>' \
  --portable-source-spec /absolute/private/portable-source-spec.json \
  --portable-source-spec-sha '<本描述实际SHA256>'
```

新模式必须同时给描述路径与摘要，并显式final；旧任务必须有真实终态原件和既有旧父锁独占。`--execute-final`表示执行CPU文件准备，不是启动GPU。所有输出和失败临时证据都写新外部目录，不能位于旧队列、标签、索引、合同或仓库内。

长准备在stdout明确记录目录扫描、来源分工及剩余分片写入的开始与结束；中间进度最多每30秒一条，分别报告目录/文件数、已检查来源数、无共享盘查询的missing数或已写分片数，不凭单个计数推算ETA。异常原文和当前扫描计数保存在新临时目录；旧strict模式不新增这套阶段输出。独立部署按真实仓库标记识别仓库根，不把脚本任意第三级祖先误当仓库，也不允许写进当前控制器或旧冻结包。

Python入口是`prepare(..., portable_spec_path=..., portable_spec_sha=...)`。不传这两个参数时严格默认不变。`prove_source_identity(...)`实际读原音生成证明；`validate_ledger_entry(entry,source,record,old_contract_sha,portable_spec,spec_sha=...)`只核已保存证据与原记录绑定，不会在审计时再读原音，也不认证一个JSON声明真的来自平台或受信执行。

final报告仍是`annotation-speed-continuation-plan/v1`，另外保存：

- `source_identity_mode`、`portable_source_spec_ref`及`portable_source_ledger_ref={path,sha256,count}`。
- `portable_source_evidence_counts`区分真实编码内容通过与保留历史解码失败。
- `portable_sidecar_inventory_ref={path,sha256}`和`portable_sidecar_inventory_summary`，记录完整原来源检查数、目录/文件计数、无PFS缺失查询数和stage cache范围。
- `fresh_media_scope="retained_partial_and_unclaimed_only"`。
- `completed_media_scope="original_completed_chunk_reference_not_media_rehashed"`、`completed_media_rehashed=false`、`source_PCM_redecoded=false`。

已有部分片结果、未领取片中的已有结果都从真正剩余输入排除；缺失者保留原source JSON记录和摘要。计数严格满足原全集等于旧保留与新剩余的互斥联合。孤儿、损坏、内容变化或目录项异常时保留新故障证据，不修旧文件，不重新标注旧结果。

## 完成片和完整终验的边界

本次准备不会重新读取已封账一百多万份媒体，也不会在目录扫描中打开其侧车内容。它们按原完成槽、分片/合同/全集摘要及目录项保留。不能把partial和预置旧结果的内容验证扩写成全库媒体已经重新验证。

后续联合数据门须显式选择同一portable模式并固定同一描述与账本；重开全部选中侧车、commit和完成片链，验证新旧分工及原总分母，再由独立消费者按确定producer读取。联合门只核已保存内容证据，不重新哈希媒体；完整终验报告应如实保留这个边界。它不授资源、八卡运行、人工完整字质量或训练/评测资格。

源和模型身份、旧13个推理模块、FP32/eager、单窗、原v1时钟及原窗口数值语义由新的后继合同及启动协议分别固定。本工具只负责来源内容与剩余输入，不能靠换成当前维护推理版本混入尚未验证的新窗口或新时钟。真实恢复还须独立核资源互斥、八个实际worker和封账增量。
