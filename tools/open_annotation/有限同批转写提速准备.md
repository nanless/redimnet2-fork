# 有限同批转写计算怎样准备与验收

`prepare_bounded_speed_validation.py`只准备明确小批输入的独立对照。它不执行GPU，不读取模型或原音，不领取当前生产分片，不重开旧标注，不创建数据库。实际推理仍由仓库现有`gpu_launch.py`、bootstrap、设备UUID锁、双快照和持续上下文守卫托管；不能为一次速度试验另写裸模型入口绕过这些检查。

本入口解决旧准备器强制同时提供30、3000、512三份索引的问题。可以先固定30或数百个三训练域来源筛选候选，再用同一接口做3000条左右代表性流程；每次必须是显式独立索引，来源数上限4096，不能拿它扫描千万来源。断点恢复仍用同合同完整输入及既有恢复比较，不以扩大试验时长代替恢复检查。

## 为什么先选现有单窗候选

当前生产每卡一个独立worker，转写和Ultra定位串行；原始策略为FP32、eager、单窗batch1。维护版本已经支持以下三个计算版本：

| 名字 | 转写计算 | 作用 |
|---|---|---|
| asr-fp32-eager | 显式FP32、eager | 同维护软件、显式原计算方式的基线，不冒称旧23文件字节一致 |
| asr-fp32-sdpa | FP32、SDPA | 先只比较注意力计算方式 |
| asr-bf16-sdpa | BF16、SDPA | 在相同注意力方式下再比较转写精度 |

Ultra始终FP32、eager、单窗，模型身份、质量规则和采样窗口不借机改变。三个版本均由同一次准备时的维护软件复制，使用相同的新源钟及文字规则。因此它们可作同软件计算方式对照；旧23文件生产包与维护版本不同，不能把这个显式FP32/eager基线轨包装成与正在跑的旧包逐字节同软件。

vLLM真实工厂此前因资源归还机制未验收而关闭。现有独占父进程旁新增CUDA上下文会触发原守卫；显存空余不能作为旁路试验许可。这个入口没有启用vLLM、多副本、数据库或共享GPU。

## 明确输入与命令

准备文件使用以下结构。所有路径和SHA必须来自本次核实的实际输入；示例没有真实模型和音频名单。

```json
{
  "schema": "annotation-bounded-speed-preparation/v1",
  "source_count": 30,
  "base_contract": {"path": "/absolute/old-code/contracts/base.json", "sha256": "实际SHA256"},
  "index": {"path": "/absolute/finite-inputs/index.json", "sha256": "实际SHA256"},
  "target_uuids": "auto2",
  "python": "/absolute/offline-env/bin/python3.10",
  "device_lock_root": "/absolute/shared-device-locks",
  "protected_roots": ["/absolute/current-annotation-run", "/absolute/current-PTN-run"],
  "profiles": ["asr-fp32-eager", "asr-fp32-sdpa", "asr-bf16-sdpa"],
  "max_runtime_seconds": 1800
}
```

索引必须只包含VoxCeleb2、VoxBlink2、CN-Celeb2三训练域，覆盖三个域；用途限train_ptn／train_lm，source_id与实际数据域和相对路径的稳定身份相等。不得掺入MUSAN或额外业务诊断来凑样本。该准备器核索引和有限分片字节，不证明其音频现场内容正确；现场原音／PCM仍由真实worker检查。

`target_uuids`可为两个明确GPU UUID数组、独立两卡pilot的`auto2`，或独立八卡pilot的`auto8`。`auto2`要求pilot_validation合同且实际NVML恰好看见两张物理卡；正式silver合同即使在两卡机器也拒绝auto2，且在读模型／取得GPU快照前拒绝。选出的UUID之后仍要核A800容量、协作锁、空闲双快照、上下文挑战与资源归还。`auto8`正式八卡的恰好八卡要求不变，不能据准备收据认定资源空闲。新的输出目录必须在仓库、旧模型代码、有限索引、明确保护的标注／PTN目录和锁根之外，软链及既有输出拒绝。

仓库根必须沿当前程序的实际祖先寻找，同时存在`AGENTS.md`文件和`redimnet2/`模型目录才能确认。部署副本没有这两个标记时，只将实际部署源码目录作为源码保护范围，继续保护合同、索引、既有任务和设备锁，允许在同一实验目录下新建兄弟输出。不能按固定目录层数猜仓库：2026年10月28日首次远程CPU准备曾把部署副本的两级祖先误作仓库，因而在任何GPU执行前拒绝了合法的兄弟输出；旧副本和失败保留，新源码另封版本。维护测试实际复制源码并在独立解释器中执行部署准备器，再生成三轨冻结副本，同时验证部署源码内和真实仓库内输出仍被拒绝；这些检查不运行模型或GPU。

```sh
python -B tools/open_annotation/prepare_bounded_speed_validation.py \
  --spec /absolute/bounded-speed-spec.json --spec-sha 实际SHA256 \
  --output /absolute/NEW-speed-validation
```

收据`prepared.json`给出每轨`argv`、`shell_command`、冻结源码和pilot合同摘要、`speed-track.json`及只读对照命令。所有命令都只是文本，不会自动执行。若只验证BF16候选，`profiles`可为`["asr-fp32-eager", "asr-bf16-sdpa"]`；不能省略基线、重复轨或填未知方式。真实云任务名另按用户要求以`zhounan_`开头。

## 运行和判定的顺序

1. 先完成实际资源交接。当前生产仍在使用目标卡时不执行任何轨；不在旁启动第二CUDA上下文，不松旧守卫，不改旧冻结包。PTN卡和进程完全排除。
2. 依次执行显式FP32-eager基线、FP32-SDPA、BF16-SDPA，沿同一批固定输入；每轨独立queue／labels／cache，资源归还双快照通过后才开始下一轨。首次小批用于发现配置兼容和文字差异，不拿几条样本宣称全库速度。
3. 首个成功转写调用记录真实参数dtype、逐attention forward、F.sdpa次数及Q/K/Vdtype。只看请求配置或顶层配置读回不能算实际兑现。当前观察是Python函数入口，不能称CUDA内核profiler。
4. 终态用生成的`audit_speed_comparison.py`命令核完整分母、侧车／commit、来源／PCM／窗口、语言、文字、原生token、EOS、截断、原生／FIX时间、实际模型调用与完整资源链。它最多比较有限试验，不产生数据库。失败、空文字和不支持语言不从分母删除。
5. 速度分别查看模型加载、ASR／生成、定位、读解码、缓存、发布和总墙钟。首窗追踪耗时包含真实推理，不全扣成观测开销；缓存复用不冒充冷推理提速。解码音频秒、来源条数和生成token分别统计，不能把更多短音频误当引擎更快。
6. 选中候选后再做代表性完整流程、同合同中断恢复和资源归还；已发布结果按原字节复用，未知和异常仍保留。不同目标文字的字界不强配为零误差；机器一致不代替人工完整字验收。

这个工具不自动选型、不提交八卡、不改变已有标注使用资格。正式接续由独立交接工具根据原任务真实状态与已发布结果推进，本工具不会重开旧全库审计或创建联合数据库。

## CPU检查的范围

维护测试覆盖：实际冻结三轨后的同工程／同Ultra／同模型及仅ASR差异、三域与来源身份、少量／全量误输入、明确两卡、pilot-only auto2与auto8、明确PTN保护、旧输入和锁目录重叠、软链、摘要置换、未知方式与重复轨。CPU检查不证明真实CUDA兼容、速度或文字／字界质量。
