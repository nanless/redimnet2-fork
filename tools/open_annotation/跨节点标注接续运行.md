# 跨节点标注接续的实际运行入口

本入口只恢复旧开源模型标注的相同计算方式，不测试vLLM，不改变PTN。先读[原音内容证明与剩余输入](跨节点原音内容证明与剩余输入.md)、[联合覆盖与唯一读取](联合覆盖与唯一读取.md)及[旧生产源码冻结](旧生产源码冻结与剩余接续.md)。旧的同输出严格恢复仍保留；它在跨节点device不同时应当拒绝，不能改旧stat或旧代码绕过。

## 数据准备与当前运行锁分别证明

真实CPU准备和联合检查可在开发机执行。准备器逐源核完整的原11,521,178条来源，把已发布的旧结果选为旧生产者，把真正缺失者写入新输入。内容证明只重新读取部分片和未领取片中已发布来源的原音；已完成片在准备阶段通过原完成槽和分片证据保留。运行描述现区分两条路线：`annotation-portable-successor-run/v1`要求完整联合plan报告及SQLite计划库；显式`annotation-portable-successor-run/v2`复用已经完成的准备与角色定稿收据。两者不能混作同一种证明。

新云容器不能把开发机当时的device号当作当前文件描述符（FD）身份，也不能在另一节点重跑要求同节点device的旧联合锁检查后删字段凑通过。`run_portable_successor.py`消费所选版本固定的真实证明，然后在当前云容器独立取得旧语义锁与旧队列父锁。历史锁的精确路径和inode仍须一致；当前FD与当前路径的device及inode必须一致，且不能在两项旧检查期间被替换。两组device分别保留在证据中。

v2的`preparation_attestation`固定`annotation-remaining-role-finalize/v1`完成收据及实际SHA。此前真实准备已经遍历原全集，排除旧目录库中的1,159,534条来源；角色定稿又实际检查10,361,644条剩余记录的父分片归属、与旧目录库互斥、数据域及角色总数，并重开816份部分片内容证明。v2核收据、原／新计划和索引的固定引用及允许的角色元数据差异，重核必要摘要和原队列，不重新打开115万份旧侧车，不重新逐条扫描全库来源，也不构建或消费联合计划数据库。它不把已停止审计的半成品或空报告当成功证明。

原23文件模型引擎直接消费剩余索引，不依赖联合数据库。v2移除的是维护者额外加入的启动前联合库要求，不改变v1严格分支、旧模型／stat规则或完整字资格。`union_spec`在v2仅复用固定的新旧生产者、来源及证明布局描述，不执行其中的联合审计。后续完整结果的联合消费和最终终验仍保留；v2准备证明不能冒充最终标签消费库。

以下两段仅适用于run/v1的联合计划库。计划库至少要求真实的九列来源表及单独source ID主键，原全集总量和旧/新生产者分区计数必须等于报告。旧行保存文本格式的64位来源/侧车/commit摘要及合法决定；新计划行的侧车、commit和决定仍为空。SQLite BLOB、复合主键、空表或只有metadata的伪数据库均拒绝。该检查不重新解码或转写旧原音，也不把外部JSON当作平台账号认证。

千万行数据库的两个生产者计数采用一次`COUNT(*)`与条件求和，不使用需要临时排序的`GROUP BY`。两组均须实际存在，逐组数量与报告精确相等，总数又必须等于两组之和；额外、未知、NULL或空组不能被忽略。比较显式使用`COLLATE BINARY`，不能让异常的大小写不敏感或去尾空格表结构把错误ID混入合法生产者。原默认BINARY正式表的计数语义保持，异常排序规则只会更严格。来源字段类型、文本摘要形状和新旧完成状态的独立检查继续执行。

## 固定的运行描述

schema显式选择`annotation-portable-successor-run/v1`或`annotation-portable-successor-run/v2`。共同字段及各自证明字段如下；两种证明字段不得同时出现：

| 字段 | 绑定内容 |
|---|---|
| `purpose` | 正式只能`production`；`cpu_fixture`不能调用真实执行器 |
| `task_name` | 必须以`zhounan_`开头；名称本身不证明平台创建成功 |
| `old_control` | 原v2严格恢复描述的路径和SHA；用于固定旧代码、合同、全量索引、声明、检查脚本和解释器，不执行其跨节点严格stat恢复 |
| `freeze_receipt` | 新版冻结收据；原23代码字节不变，合同仅version不同 |
| `union_spec` | 固定的新旧生产者、全集／剩余索引、内容账本与目录库布局；v2只复用描述，不执行联合审计 |
| `union_attestation`（仅run/v1） | 实际production联合plan输出报告及SHA，含最终发布的计划数据库引用；不能接受半成品 |
| `preparation_attestation`（仅run/v2） | 已完成准备的角色定稿收据及SHA，绑定原／新计划、剩余索引、父全集和旧目录库；不含联合计划库依赖 |
| `old_broker`、`old_completion_map`、`old_queue_identity` | 原队列三份文件及完整SHA；不得替换原分母或更改旧队列 |
| `current_platform_observation` | 实际平台终态与竞争任务观察原件及SHA，不能由工具伪造查询结果 |
| `new_run_root` | 原冻结ROOT之下的全新独立运行目录；新queue、labels和resources在其下，不能与旧输出或代码重叠 |
| `lineage_claim` | 原语义锁旁唯一的`.portable-successor-v1.claim.json`，一旦创建永久保留，无自动重试 |
| `evidence_root` | 与新旧运行和源码分开的全新执行证据目录 |
| `model_API_calls_allowed`、`release_training_labels` | 严格整数0和false |

`current_platform_observation`使用`annotation-portable-platform-observation/v1`，包含原`old_task_id`、同一`observed_utc`、标准`original_terminal`、`competing_successor_tasks=[]`、已核`prior_attempts`，以及`evidence_basis=platform_terminal_and_current_shared_locks`、`remote_proc_enumeration_performed=false`。标准终态绑定原task、queue和唯一`task-worker-0`，状态须为终态，`active_workers`严格整数0。原终态时间必须有时区且不在未来；本次运行观察须在一小时内。旧历史准备观察继续保留原时间，不改写成新鲜观察。

排队超过观察时效时，入口必须在GPU前拒绝，不能悄悄延长或伪造时间。维护者应查询实际平台和任务后取得新的真实观察，再按明确后继记录处理；不能因为有排队状态就重复提交多个写入者。已有永久声明时尤其要查实际任务和进程，不能删声明或锁文件重跑。

长时间排队可另用[排队后新鲜证明交接](排队后新鲜证明交接.md)外层：蓝图提前固定全部运行字段，实际新实例申请新鲜平台观察后只补这一项，再交给本入口。它不改所选版本的检查；run/v1须在提交前具备完整联合证明，run/v2须具备实际已完成的准备收据。实例已分配的CPU等待可能计费，1800秒单次截止及所有失败原件保留，不能将外层等待成功当GPU验收。

## 默认检查与执行顺序

```bash
python3 -B tools/open_annotation/run_portable_successor.py \
  --spec /absolute/private/successor-run.json --spec-sha '<实际SHA256>'
```

默认检查不创建新运行或声明，不调用旧gate、模型或GPU。共同核冻结包全部成员、旧合同和原full索引、原claim、明确共享别名、旧终态链、新旧version和全部其他字段相等、内容账本及目录库、旧队列快照与历史inode。run/v1额外核完整联合报告及计划SQLite；run/v2额外核已完成准备收据和其固定引用，不执行全库审计。新实现的CPU测试、部署和GPU运行结论须分别记录，不能继承旧版本的成功。

只有已授权的正式恢复才加`--execute`。入口先持原语义锁，保持原v2 W2历史模型质量准入命令不变，仍读取原full索引及原合同，不把它替换为remaining来骗过全量门。第二项实际命令是绑定新运行描述及其SHA的`verify_portable_successor_mounts.py`；每次命令前均重新核检查源码、解释器真实二进制及软链接。

原`verify_ultra_cloud_mounts_v2.py`是首次启动检查，明确要求旧run不存在，不能原样用于已经有旧输出的恢复。其脚本、SHA和原admission继续保存，不执行，也不改原件来接收新run。新挂载检查核原用户RW、共享RO的精确GPFS source/target/type/mode，实际控制文件、完整/剩余输入、所选版本证明、26个模型资产的位置和大小、明确共享别名、新run的独立性及执行证据的持久RW位置；只有run/v1要求计划数据库挂载。该门不重新哈希模型内容；原GPU父进程仍会执行完整模型及第三方源码SHA核验。

上述两项实际检查通过后，再取得当前旧队列父锁。核当前锁仍是检查前同一inode，重核控制描述自身SHA、全部新旧代码、合同、解释器、所选版本证明、目录库、原broker及完整completion map。创建新的永久lineage声明和独立run后，在原GPU入口前再核一次。任何异常保留新证据和已创建声明，不自动重试。

默认检查、挂载门、门后和GPU前均拒绝新run或执行证据与旧/新源码、冻结包、完整/剩余输入、控制源、旧声明或共享模型/原音目录相互包含。不能只防止旧run重叠，却允许把新queue或labels写进旧code目录。正式执行证据必须在持久用户`/root`挂载，不能误写容器临时目录。

实际调用的是原23文件中的`gpu_launch.py`，它保留原独占设备锁、模型全SHA检查、空闲双快照、八个worker的物理UUID与context挑战、持续监控和精确清理；输入换成所选版本真实证明绑定的remaining索引，新合同新queue/labels独立。不能同卡添加第二个CUDA context，也不能把显存有余量当共享许可。

原语义锁和旧队列父锁两个FD通过`pass_fds`交给GPU父进程，贯穿计算和清理。控制器收到TERM/INT时只通知本次精确子父进程并等待其既有清理协议；Popen后的证据写入失败也要等待本次子进程退出，不提前放锁。退出0或leader消失都不能单独证明资源归还，最终还须原父进程的八worker、资源归还及输出核验收据。

## 平台启动脚本与现场验收

`launch_portable_successor.sh`需要三个参数：运行描述绝对路径、描述SHA、控制源清单SHA。平台入口先核该脚本自身SHA；脚本再核`controller-files.sha256`及全部控制源、描述、原实际Python二进制，然后执行运行控制器。清单的成员不能在部署后原地修改；修复要建新控制源版本并记录新SHA。

平台任务使用`zhounan_`前缀、优先级6、单机八张A800、原镜像和两项挂载，自动重试关闭。创建后按唯一ID回读配置。实际恢复至少核八worker和八物理GPU一一对应、原持续context监控正常、首批分片完整封账及后续增量、旧原件未改变，并继续只读核PTN日志。机器候选、unknown和原始/FIX边界保留；恢复成功不等于人工完整字质量通过，也不自动释放训练标签。

完整旧侧车不会再执行模型。旧阶段缓存仍按旧合同保存；新合同SHA不同，尚无完整侧车的在途工作可能重做，不能重贴旧缓存并谎称零调用。全库结束后仍需联合complete核验及明确完整字质量审核。

已有v1准备若继承了全库`role_union_counts`，须按[剩余角色元数据定稿](剩余角色元数据定稿.md)另发同目录v2索引、计划和收据，不能原位改旧摘要。联合描述和启动描述使用新真实SHA；分母始终是原11,521,178条。联合CPU检查可显式使用有界旧侧车读并发，但主线程仍执行全部提交校验、SQLite选择和计数；这不是GPU标注提速结论。prepare、union plan和之后的complete仍须在满足历史计划锁device/inode的节点执行；云运行器消费固定数据证明，不在另一节点通过删device重跑旧union。
