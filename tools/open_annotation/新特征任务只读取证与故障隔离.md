## 先分清哪里没有通过

| 已保存的现象 | 能支持的判断 | 下一项有限检查 |
|---|---|---|
| 平台仍排队，resources 尚不存在 | 尚未开始该轨，不能说计算失败 | 核平台原任务身份与队列，不重提 |
| CPU 来源或合同错误，尚无 GPU 子进程 | 前置检查拒绝，不是模型质量结论 | 保存完整错误与源 SHA，核声明和真实依赖 |
| 有 `failure.json`，没有成功父终态 | 该 attempt 未完成 | 保留 child/TERM/资源清理证据，先确认原父排空 |
| GPU 父成功，驱动未生成比较 | 原执行完成，后续有限读回可能仍在进行 | 读驱动原日志/失败文件，不能自行再跑审计器 |
| 比较报告显示实际有效输入不一致 | 批宽受控对照不成立 | 逐项定位 PCM、SDK PCM、mel、mask、prompt，不授速度资格 |
| 有效输入相同，生成文字仍变化 | 前处理差异已排除，解码数值或其它模型状态仍待查 | 固定少量真实差异做新的独立诊断，不改当前任务 |
| ASR 相同，定位异常或 unknown 保留 | 定位/质量条件仍未满足 | 原生/FIX 与错误逐条保留，不自动扩大可用资格 |

## 前处理证明必须读哪些字段

每窗 `asr.native.preprocessing` 要同时有独立 B1 参考和实际 generate 观察。
先核 source/window 的原 PCM、原帧数及 SDK 归一化 PCM，然后核有效 mel 的
shape、float32 dtype、SHA，原有效 feature mask 及其实际 dtype，再核去掉
左侧补齐的完整 prompt token 与音频占位数。实际 feature 补齐宽、文本补齐
宽可以随批宽改变；有效部分不能改变。不能只看
`verified_from_actual_generate_tensors=true` 这一布尔值。

worker 摘要还须保存真实七源路径/SHA和特征配置，与新合同
`asr_preprocessing_sources` 对应。源码、模型配置或 SDK 归一化身份不一致时
停止准入；不能删掉来源守卫、重写冻结清单或把新的 SHA 当作原版本许可。

## 有效输入相同仍有差异时的下一步

只在新的独立诊断里固定最少量差异窗口及不变对照，保留完整 PCM/源 SHA、
已保存有效特征、prompt 和模型合同。逐项检查首次不同 token 前的实际
position IDs、有效 attention mask、cache 长度、真实 decoder 输入和第一处
不同 logits；报告 top 候选及差距，不能仅凭温度为零就宣称所有批次应逐 bit
相同。若要对比注意力具体内核或精度，必须另行显式声明新诊断条件，不能
偷偷修改现试验来消除差异。Ultra 仍按原 FP32/eager 单窗执行。

所有差异保留原报文和原数组。旧 15 源 B4/B8 的速度及质量结果继续留作历史
证据，不把其中已经通过的部分借给新 16 源协议。正式八卡接续只接受新版本
真实的完整质量、恢复、资源和稳态收益证据。

## CPU 封存的独立崩溃与诊断方式

新 B8 主结果的第一次 CPU 封存，在 60.17 秒以 SIGSEGV（退出码 -11）退出，
不是 300 秒预算超时。完整 stderr 先记录首个 60 秒栈转储，正在
`schema._finite_tree` 的有限 JSON 结构检查，随即记录 Python 崩溃。
子进程已经回收，峰值内存约 0.676 GiB，没有产生封存结果。原意图、日志、
进程控制、退出码和源码摘要保留在 `cpu-main-b8-sealed-v1`，不覆盖重试。
这不是转写或定位模型失败，也没有启动 GPU。

目标环境为 Python 3.10.20，二进制 SHA 为
`cdb9592ef64842d7528ac97c2e03c81f226e5d875d5cc9304b59131e7bbcd505`。
系统内存及进程限额的轻量观测没有提供内存不足证据，但单份 Python 栈不能
证明 C 层崩溃的根因。[Python 文档](https://docs.python.org/3.10/library/faulthandler.html)
说明 `dump_traceback_later` 使用 watchdog 线程；[上游问题 116008](https://github.com/python/cpython/issues/116008)
记录过无 GIL 读取活动帧的类似竞态及从 Python 持 GIL 调用的规避方法。
上游案例不是本次现场的因果证明。

维护工具 `diagnose_cpu_stack_capture.py` 仅按固定 SHA 抽取真实 schema 的
`_finite_tree`，循环处理非音频合成 JSON。实际同 Python、nice15、单 CPU、
CUDA 不可见的两组各 10 秒对照，旧 watchdog 与 Python Event 线程均以零
退出，后者实际保存 586 次栈。因此本轮没有复现旧 SIGSEGV，不能写成已经
证明或修好 Python 根因。两组原日志与源码全部保留，不提高测试预算反复碰运气。

新的 CPU 控制器另存 `cpu-sealer-diagnostic-v3`，源码 SHA 为
`403626748e4338e3dcf3cf37ed48441ab4c29ce77d6c5638e3ed43526eb57c98`。
它从 Python Event 线程定期调用 `dump_traceback`，保留栈采集和退出清理，
不改封存器、原审计代码、字节检查、质量条件或 GPU 时限。18 项普通及
`-O` 独立检查通过；同一个 B8 track 在新输出 `cpu-main-b8-sealed-v2`
按原 v1／300 秒预算执行，结果须单独读取，不能借用旧成功声明。

新目录的主 B8 封存随后实际完成：134.762 秒、零退出、未超时、子进程回收，
峰值内存 1676390400 字节。60 秒与 120 秒栈各保存一次，无 Fatal 日志。
输出 `cpu-main-b8-sealed-v2/sealed-readback.json` 为 122738770 字节，SHA 为
`e06e4585cfa19fe1865fcca261439e368a922770d469364a56bf6ada5393dc63`。
主封存结束后才启动 512 来源封存，24.474 秒零退出、未超时、子进程回收，
峰值内存 405692416 字节；输出
`cpu-recovery512-b8-sealed-v1/sealed-readback.json` 为 18528803 字节，SHA 为
`12e8935592e75be48fcbec6c1d3f9dcbd89904d8f6aa6e38fb8d9e819534f126`。

这证明新诊断控制方式下本次完整封存成功，不证明旧 SIGSEGV 的因果根源；
