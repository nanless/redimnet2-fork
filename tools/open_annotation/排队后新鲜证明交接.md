# 排队后取得真实平台新鲜观察，再交给原恢复入口

这是一项可选的排队交接工具。它解决“提交前的观察在长时间排队后超过一小时”的问题，不能代替原标注恢复检查，也不证明标注文字或字界正确。

新任务拿到实例后，外层程序只运行CPU文件检查并发布请求。操作者读取真实平台状态，保存新的观察文件，发布一次回复；外层再执行原冻结恢复入口。原一小时时效、W2历史质量检查、挂载检查、语义锁、旧队列父锁、永久声明、八设备独占监控和23文件计算引擎都保持原样。

**此时实例和八卡已经分配，可能占用资源并产生费用。** “不创建CUDA context”不等于“不占GPU资源”或“免费等待”。程序最多等待1800秒；超时留下失败证据，不重试、不停止平台任务、不删除声明。应由操作者查询实际任务状态后处理，不能盲目重复提交。

## 维护文件与两组固定源码

| 文件 | 用途 |
|---|---|
| `queue_handoff.py` | 默认检查、云内等待、操作者发布、最终交接；只使用Python标准库 |
| `launch_queue_handoff.sh` | 显式Bash入口，核外层清单、蓝图和原Python二进制SHA |
| `tests/test_queue_handoff.py` | 本机真实文件、信号和合成执行反例；不授生产资格 |

外层在独立目录中只包含两个程序文件及`queue-handoff-files.sha256`。原恢复控制器继续放在另一独立目录，清单名称固定为`controller-files.sha256`。正式外层要求原控制器清单完整覆盖已验证的21个成员，不接受只有启动脚本和两个Python入口的薄包。目录内不允许未登记的Python模块、脚本、缓存或子目录遮蔽导入；原控制器保留的`controller-files.json`只是非执行映射文件。

源清单每行使用标准`64位小写SHA  相对文件名`格式，成员不能重复、越界、软链或硬链。外层清单和内层清单分别绑定，不能为加入外层而改写已经冻结的内层。源文件变更后新建部署版本，保留旧版本。

真实Python固定为：

```text
/root/miniforge3/envs/qwen3-asr/bin/python3.10
cdb9592ef64842d7528ac97c2e03c81f226e5d875d5cc9304b59131e7bbcd505
```

平台命令应在调用显式`/bin/bash`之前核外层shell实际SHA，并移除`BASH_ENV`、`ENV`等非交互shell注入来源。shell再核外层源清单和蓝图。Python交接时继续移除`PYTHONPATH`、`PYTHONHOME`、`LD_PRELOAD`、`LD_AUDIT`、`BASH_ENV`和`ENV`。不清空平台原`CUDA_VISIBLE_DEVICES`，也不改写`RANK`、`WORLD_SIZE`或`LOCAL_RANK`来绕过原门。

## 固定蓝图是什么

schema为`annotation-queue-handoff-blueprint/v1`，字段必须恰好如下。蓝图在联合审计真正完成后生成，不能用当前`.consumer-building-*`数据库或空stdout冒充最终结果。

| 字段 | 约束 |
|---|---|
| `schema` | 固定上述版本 |
| `purpose` | `production`或显式`cpu_fixture`；两者不能互相冒充 |
| `task_name` | 必须以`zhounan_`开头，与内层运行描述完全相同 |
| `runtime_base` | 原`annotation-portable-successor-run/v1`运行描述，只缺`current_platform_observation`这一项 |
| `handoff_root` | 原任务ROOT之下的独立持久目录，等待时必须尚不存在，父目录已存在 |
| `outer_controller` | `{root, manifest:{path,sha256}}`，绑定两个外层程序 |
| `runtime_controller` | 同样结构，绑定原内层21成员目录及清单 |
| `python_binary` | 原实际Python二进制路径和SHA |
| `wait_seconds` | 严格整数1至1800 |
| `required_prior_attempt_ids` | 必须逐一重新确认终态的既往恢复尝试ID，非空且无重复 |

`runtime_base`的完整键集如下，缺项或额外字段都会拒绝：

```text
schema, purpose, task_name, model_API_calls_allowed, release_training_labels,
old_control, freeze_receipt, union_spec, union_attestation,
old_broker, old_completion_map, old_queue_identity,
new_run_root, evidence_root, lineage_claim
```

其中`model_API_calls_allowed`必须为严格整数0，`release_training_labels`为false。原运行描述如何绑定最终联合报告、数据库、旧合同和队列，见[跨节点标注接续运行](跨节点标注接续运行.md)。外层只检查联合报告明确为已完成的plan、引用最终数据库，并继续固定其引用；没有再次全读千万行数据库或运行内层`inputs`，输出如实保存`controller_inputs_check_executed=false`、`consumer_database_content_SHA_verified_by_outer=false`。完整数据和运行资格仍由原入口验收。

交接目录必须与旧run、旧源码、模型原音、输入、旧声明、设备锁、两组控制源、新run和新运行证据目录双向互不包含。不能把回复写进冻结源码或原结果目录，也不能让交接目录包住这些目录。所有路径拒绝软链；请求、回复、生成的运行描述及源文件读取拒绝多重硬链。

## 默认只读检查

```bash
python3 -B /absolute/outer/queue_handoff.py check \
  --blueprint /absolute/private/blueprint.json --blueprint-sha '<实际SHA256>'
```

省略`check`也只做相同检查。不创建请求，不执行原控制器、不获取训练或标注锁，不加载模型，不调用平台API，不授GPU资格。`cpu_fixture`只有显式注入的合成执行器才能模拟最后交接；正式模式拒绝假执行器、假时钟和假进程身份。

## 云端请求必须来自实际分配的容器

正式平台入口使用固定蓝图及外层清单SHA：

```bash
/bin/bash /absolute/outer/launch_queue_handoff.sh \
  /absolute/private/blueprint.json '<蓝图实际SHA256>' '<外层清单实际SHA256>'
```

实际等待对应`queue_handoff.py wait ... --execute`。程序从`socket.gethostname()`读取`实际taskID-worker-0`，从本机`/proc/self/stat`读取自身start ticks，从`/proc/sys/kernel/random/boot_id`读取本机boot ID。它不会从预提交蓝图编造未知task ID，也不会把开发机进程表当作云PID核验。

等待只新增：

```text
handoff_root/                          0700
  request-v1/                         0700
    request.json                      0600
```

请求固定蓝图引用、64个十六进制字符的nonce（256位随机数）、实际hostname/task ID/PID/start/boot、创建UTC时间、等待上限及唯一回复路径。stdout在请求完整写入并fsync后给出实际请求路径和SHA。等待使用单调时钟，最后一次sleep不会超过剩余时间；每轮重读同一个请求摘要和自身身份。

已存在交接目录意味着已使用过本次蓝图的交接位置。程序不会覆盖请求或删除目录重新来一遍。超时、信号或稳定校验错误留下`waiter-failure.json`，原请求和已有回复保留。异常期间没有创建原标注永久声明，也不能仅因云实例退出或日志沉默就声称资源已经归还。

## 操作者如何提供真实平台观察

操作者必须先根据stdout中的实际请求，查询当前平台：

1. 原标注任务及唯一worker确实终态，活动worker数为0。
2. `required_prior_attempt_ids`中的旧恢复尝试全部终态，不能漏掉仍在运行或排队的竞争尝试。
3. 除这次请求所属任务外，没有其它竞争接续任务。
4. 请求所属的新task ID、名称和唯一worker确实Running。仅存在一个同名任务或本机request文件，不证明平台认证或实际运行状态。

新的观察沿用`annotation-portable-platform-observation/v1`，保留现有旧终态、`prior_attempts`、`competing_successor_tasks=[]`、`remote_proc_enumeration_performed=false`、`evidence_basis=platform_terminal_and_current_shared_locks`等字段。另增加：

```json
{
  "current_successor_task": {
    "task_id": "实际请求中的新task ID",
    "task_name": "与蓝图一致的zhounan_名称",
    "state": "Running",
    "active_workers": 1,
    "workers": [{"name": "实际taskID-worker-0", "state": "Running"}]
  }
}
```

这段只说明新增字段，不能单独当作完整可执行观察。顶层`observed_utc`必须和`original_terminal.observed_utc`完全相同，不在未来，距离发布及最终交接不超过一小时，而且不得早于本次云请求创建时间。不能修改历史观察时间来制造新鲜证明。真实UI原件或其它实际查询材料保存在受控证据目录，公开仓库不放原始完整日志或业务样本。

把完整观察存为新文件并取得实际SHA，再在能够读到共享用户目录的受控机器上发布：

```bash
python3 -B /absolute/outer/queue_handoff.py publish \
  --blueprint /absolute/private/blueprint.json --blueprint-sha '<蓝图实际SHA256>' \
  --request /absolute/handoff/request-v1/request.json --request-sha '<请求实际SHA256>' \
  --observation /absolute/private/current-platform.json --observation-sha '<观察实际SHA256>'
```

publisher只核文件、引用、时间和字段关系，不查询平台、不查开发机`/proc`来认证云PID，不调用内层`execute`，不取得旧锁，不创建永久声明。返回`platform_authentication_performed=false`和`GPU_admission_granted=false`；操作者保存的外部观察不能变成工具自行认证的结论。

## 回复只能补一个字段

publisher只新增：

```text
request-v1/
  publication-v1/                     0700
    runtime-spec.json                 0600
  reply.json                          0600
```

运行描述必须等于`runtime_base`加上`current_platform_observation`的新路径/SHA，不能修改代码、合同、来源、run、证据或claim。最终比较使用严格的规范JSON，不能让Python的`True == 1`、`False == 0`混淆字段类型。

reply固定实际请求SHA、nonce、全部进程身份、蓝图SHA、运行描述SHA和观察SHA。所有新增文件先写私有`.pending`文件并fsync，再用无覆盖方式发布，最后fsync目录。发布中瞬时nlink2不能被消费；只有本协议同inode的pending过渡允许继续等待，正式读取仍要求nlink1。既有文件、未知硬链或稳定损坏不被当成可用回复。publisher失败保留pending和`publisher-failure.json`，不覆盖修补历史失败。

最终交接会在保存`exec-intent.json`前后分别复核：蓝图、两组源清单和全部成员、解释器、请求、回复、运行描述、观察时效、当前自身身份与单调时钟截止时间。intent写盘期间更换任一固定输入都不能让旧检查结果继续授执行。意图文件不证明GPU已经启动。

然后才用显式Bash执行原固定入口，参数仍是运行描述路径、其实际SHA和原内层清单SHA：

```text
/bin/bash /absolute/runtime-v6/launch_portable_successor.sh
    实际新runtime-spec路径 实际specSHA 实际v6源清单SHA
```

原入口仍独立检查一小时时效、全部数据证明、W2、实际挂载、旧锁、永久声明和GPU身份。外层等到回复、publisher退出0或保存intent，都不能写成八卡标注恢复成功。实际成功仍须八个worker和八物理UUID、独占监控、首批完整封账及后续增量、旧结果保留、PTN正常等现场证据。

## 验证与使用边界

```bash
python3 -B -m unittest discover -s tools/open_annotation/tests -p 'test_queue_handoff.py' -v
bash -n tools/open_annotation/launch_queue_handoff.sh
```

CPU反例覆盖真实私有文件和fsync、只补观察的完整交接、重复请求/回复、旧任务仍Running、漏prior、竞争任务、错误own任务、过期及未来观察、JSON重复键和类型混淆、软硬链、源变更、intent写盘期间置换、超时与真实SIGTERM处理。合成输入、假时钟和执行器都标为fixture；这些不能代替正式云实例请求、平台观察或原GPU验收。

另外有真实的两个操作系统进程检查：独立等待进程先发布请求，另一命令进程读取请求并发布观察引用、运行描述和回复，等待者最后只调用一次合成CPU执行器。两进程使用真实墙时与文件发布，并在任何失败或超时时回收本测试直接创建的子进程。PID是真实的；Linux可读取真实start/boot，Mac上的start/boot和云hostname明确标为合成，不能写成真实云身份或GPU验收。该测试子进程隐藏GPU，只调用假执行器。

本工具不自动查询平台、不创建后台任务、不扩大数据范围、不重启或迁移PTN，也不修改正在执行的联合审计。已有完整标注、旧阶段缓存、严格恢复失败记录、半成品和异常继续保留。
