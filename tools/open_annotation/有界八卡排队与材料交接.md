# 有界八卡排队与材料交接

本入口解决一个具体时序问题：新八卡任务可能长时间排队，而旧标注仍应继续产出。不能在提交新任务时就伪造一份“旧任务已停”的终态，更不能为了等资源提前停止旧标注。现在先完成真实候选选型，再让唯一新八卡实例进入最多 1800 秒的材料等待；操作者读到该实例真实请求、核实际八卡资源后，才受控停止旧标注并发布终态。PTN 从始至终不操作。

现有 `queue_handoff.py` 的 portable `/v1`、`/v2` 入口保持原样。这里使用新 `bounded_speed_queue_handoff.py` 和独立 `annotation-bounded-speed-queue-blueprint/v1`，不会把旧入口改成接受新 schema。真实双卡试验、正式数据或质量材料未通过时，不进入新八卡提交流程。等待发生在**已经分配的八卡实例内，可能占用配额并计费**；1800 秒超时、信号中断或材料不符会保留请求及失败，GPU 不启动，也不自动重提平台任务。

## 一、版本和输入必须先固定

本轮单窗 GPU 运行源码必须从专属 Git 提交 `cf7e8599eedda5a8a61a57cc6c30e1b4c764a2aa` 的 `git archive` 构建。这个版本基于已冻结的 `447c4ae` 单窗双卡试验，只有已经独立审阅的 worker/report 控制接续差异。不能从正在添加原生 batch4/8 的工作目录冻结正式包，再拿旧单窗试验证据授运行资格。若后续原生批处理真实更快，需要另一份明确的新包、新合同和相应真实比较／质量证据。

该v1入口还固定这份Git版本的31个模型、资源和控制关键源码SHA；合同或后端混入未验native字节时，在发布等待请求前拒绝。专用等待脚本使用独立外层控制目录。`build-controller` 从上述独立 GPU 包复制 18 个共同 helper；每个共同文件的 SHA 必须与 GPU bundle 中的对应成员完全相同，仅加入新等待脚本及构建收据。它不往已冻结 GPU 包添加文件，也不改其旧清单。外层控制目录严格拒绝额外导入文件、目录或软链，源码及共同 helper 摘要同时复核。

操作者应先将本仓库新脚本固定为明确 Git 版本，再从该版本的部署副本运行构建。示意命令中路径、文件名及摘要必须改成实际原件，不能直接复制占位符执行：

```text
/root/miniforge3/envs/qwen3-asr/bin/python3.10 -B /root/已固定控制源码/bounded_speed_queue_handoff.py build-controller \
  --gpu-code /root/原任务专属目录/新冻结cf7e859包 \
  --gpu-bundle-sha 实际新GPU包bundle_files.json的SHA256 \
  --controller-output /root/原任务专属目录/独立outer-v1
```

`build-controller` 输出 `root` 和 `manifest`，直接作为 blueprint 的 `outer_controller`。GPU 原件不改，复制后再次核其 bundle，完整构建收据保留在独立 outer 内。

## 二、真实模板与默认顺序

仓库提供三个结构模板，所有 `REPLACE` 均为必填占位符，默认不能通过检查：

- [八卡等待蓝图](templates/bounded-speed-queue-blueprint.example.json)：固定新软件、真实选型材料、前一实际 run、原 Python、原 UUID 锁根、未来输出及等待上限。
- [终态后有界准备](templates/bounded-speed-final-handoff.example.json)：固定最近旧生产者的合同／父索引／旧结果树、独立新 queue／labels 和完整分母。当前模板记录的旧任务与索引是 10 月 28 日该次已知原件，操作前仍要核实际当前任务。不能把“以前已保留的 1,159,534 条”误当最近旧 writer 新完成量；最近旧完成量在终态时按固定槽和最多八片计算。
- [真实平台观察](templates/bounded-speed-queue-observation.example.json)：等待请求出现后才生成，固定实际新 task／worker Running、最近旧任务及其唯一 worker 终态、所有必须核实的先前尝试，以及真实观察时间。

默认顺序如下：

1. 完成真实双卡候选、同输入基线、文字与完整字边界差异复核、512 条零调用恢复、GPU 排空及资源归还。固定所选候选和正式新合同，以及工程控制源码的独立审阅材料；没有这些材料，blueprint 的默认检查就拒绝。
2. 从 `cf7e859` 专属归档构建独立正式 GPU 包，创建独立 outer；固定 blueprint、handoff-spec 和当前生产者的 portable 内容证明规范。其旧合同／索引必须绑定当前生产者，不能重用更早原始生产者的 portable 规范。
3. 新平台任务名称使用 `zhounan_` 前缀，优先级 6，单实例八张 A800，原 `/root` 持久读写和 `/shared/group-shared` 只读挂载，唯一任务查询、自动重试关闭等由操作者按提交技能检查。本工具不提交平台任务。
4. 新实例使用下面的 `wait --execute` 进入等待。它要求父入口只执行一次，拒绝 WORLD_SIZE／RANK／LOCAL_RANK 多进程环境；读取本机实际 hostname、PID、start ticks、boot ID 以及只读 NVML 快照，确认八张 A800、零 compute PID、足够可用显存后，才发布私有请求。0% 利用率不作为空闲依据。
5. 操作者读取该新任务的真实 Running、表单、挂载和请求，并核请求附带的实际八卡快照。只有新任务确已获得资源、候选已通过，才对**明确的旧标注任务**执行受控停止。停止不被描述成“完成当前片再停”；原件、日志、片内侧车、缓存和孤儿均保留，PTN 不动。
6. 从真实平台读取旧 task 和 worker 终态，写新的 terminal 原件及平台观察。task 和 worker 可以是不同的真实终态，例如 Stopped／Failed；二者都必须终态，不能为了让状态相等改写失败。平台观察必须晚于这个新请求，一小时内、非未来、同一真实时间，不能改旧时间戳。
7. 在新八卡 WebShell 的另一个普通 CPU shell 执行 `publish`。它只在真实终态、旧父锁及最多八个 claim 锁可取得后，生成最终薄索引、严格复核新运行协议，再原子发布 reply。尚未领取片只保留元数据，绝不读全部 JSONL、全部侧车或建立数据库。
8. 等待进程绑定 request SHA、nonce、实际 PID/start/boot、blueprint、reply、最终报告及 runtime SHA。所有检查通过且仍在总期限内，才建立独立新 run 并 `exec` 原 `gpu_launch.py`。正式入口继续取得原始祖先锁、最近旧 writer 锁、永久唯一后继声明、原 W2、挂载、UUID 锁、双快照、CUDA 挑战和清理协议。reply 或 exec-intent 都不证明 GPU 已启动或验收通过。

## 三、等待与发布的命令接口

平台入口直接调用独立 outer 的脚本。启动前清理 `PYTHONPATH`、`PYTHONHOME`、`LD_PRELOAD`、`LD_AUDIT`、`BASH_ENV` 和 `ENV`，使用原控制文件固定的 Python 二进制与 `-B`，不要使用另一环境的 `python` 简称。默认 `check` 只读控制，不产生请求、不读旧音频，也不要求旧 writer 已停。

```text
固定Python -B /root/独立outer-v1/bounded_speed_queue_handoff.py check \
  --blueprint /root/固定blueprint.json --blueprint-sha 实际SHA256

固定Python -B /root/独立outer-v1/bounded_speed_queue_handoff.py wait \
  --blueprint /root/固定blueprint.json --blueprint-sha 实际SHA256 --execute
```

请求保存在 blueprint 的 `handoff_root/request-v1/request.json`，同时产生 `resource-snapshot.json`。目录为当前用户 0700、私有协议文件为 0600，文件须为单硬链接常规文件。新任务在请求日志里明确写已经分配、可能计费、外层没有创建 CUDA。

操作者读到请求之后，才能将真实终态材料发布给它：

```text
固定Python -B /root/独立outer-v1/bounded_speed_queue_handoff.py publish \
  --blueprint /root/固定blueprint.json --blueprint-sha 实际SHA256 \
  --request /root/等待根/request-v1/request.json --request-sha 请求实际SHA256 \
  --observation /root/这次真实平台观察.json --observation-sha 观察实际SHA256
```

默认推荐在目标新八卡实例的 WebShell 发布，避免不同机器的 `/root` 实际挂载不一致。**也可以在开发机发布，但仅当所有固定绝对路径确实指向同一持久存储、执行同一独立 outer 和原 Python／共同 helper、且能按原 physical-path 规范访问目标请求时。** 发布工具不读取开发机 `/proc` 来证明云节点进程，不把开发机 hostname 或 GPU 当新实例证明。云任务真实状态必须来自操作者刚读取的平台原件；真正等待进程只在自己的新云实例核 PID/start/boot，正式 GPU 父在目标实例再次检查实际资源及挂载。

## 四、失败、超时和已有结果

任何时间只允许一次私有请求和一次 publication。超时、SIGTERM、SIGINT、来源或控制差异、仍被占用的旧锁、未知 GPU PID、错误新任务、旧任务 Running、未来／过期观察、reply 重放及 nonce 错误都拒绝。部分准备和失败 JSON 保留，不删目录、改旧材料、偷偷延长等待或重置 nonce 继续。

最终材料产生后若发布失败，应先核已保留的最终报告、runtime、失败及是否已经进入原 GPU 父流程；不能直接删除 final 或 publication 重做。需要新的控制版本或平台尝试时，保留历史原件，并重新核唯一任务和永久生产者声明。若旧任务已完成所有来源，发布明确拒绝再启动 GPU，不为零剩余工作提交新推理。

等待外层不修改旧队列或标签，也不持有 GPU context。它会读取固定小控制、源码、有限试验证据及一份 NVML 快照；只有终态发布步骤读取最多八个旧在途片和对应既有结果。正式 worker 后续每次领取一片才检查该片旧结果，已发布结果保留原 producer/job，异常保留，不能用新合同重贴旧标签。详细运行条件见[有界提速正式运行](有界提速正式运行.md)。
