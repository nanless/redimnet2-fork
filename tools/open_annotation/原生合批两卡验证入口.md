# 原生转写合批的两卡验证入口

这两个新入口只准备和执行有限三域试验。原单窗准备器、单窗比较器和运行中冻结包不改；新试验不创建数据库，不遍历当前生产结果，也不能自动切换正式任务。完整方案见仓库`docs/plans/2026-10-28-原生转写批处理独立验证方案.md`，文件缓存及恢复见[整批文件事务](原生转写整批文件事务.md)。

## 准备同批三轨

`prepare_native_batch_validation.py --spec /绝对路径/spec.json --spec-sha 实际SHA --output /独立新目录`生成批次1、4、8的三份独立冻结包、合同、队列、结果和比较描述，不执行模型。先为30条生成一次，再对同一来源全集中的3000条生成一次。准备输入的结构如下，摘要必须由真实文件计算，示例不能直接执行。

```json
{
  "schema": "annotation-native-batch-preparation/v1",
  "source_count": 30,
  "base_contract": {"path": "/absolute/base-contract.json", "sha256": "ACTUAL_BASE_SHA256"},
  "index": {"path": "/absolute/finite-index.json", "sha256": "ACTUAL_INDEX_SHA256"},
  "target_uuids": "auto2",
  "device_lock_root": "/absolute/original-common-device-locks",
  "python": "/absolute/verified/python3.10",
  "protected_roots": ["/absolute/running-annotation", "/absolute/running-PTN"],
  "max_runtime_seconds": 1800
}
```

输入明确限制3—4096条，且来自VoxCeleb2、VoxBlink2和CN-Celeb2三域；每个有限分片都重新核SHA和真实数量。不能把千万条索引改个小分母蒙混通过。默认`auto2`只申请实际两张独立A800，也可给两个明确UUID；本入口拒绝`auto8`，正式八卡是另一项受证据保护的操作。

三个profile名为`native-fp32-sdpa-b1`、`native-fp32-sdpa-b4`和`native-fp32-sdpa-b8`。三轨固定FP32/SDPA、同一模型、源码、输入、窗口、生成上限、质量规则和Ultra逐条FP32/eager；只改变显式`runtime.asr_batching.max_requests`。新track为`redimnet2-annotation-native-batch-track/v1`，不能交给旧单窗比较器。

## 串行真实执行

`run_native_batch_pilot.py --plan /绝对路径/plan.json --plan-sha 实际SHA --output /独立新证据目录`默认只核输入和计划；加`--execute`才运行已固定的命令。计划结构如下。

```json
{
  "schema": "annotation-native-batch-pilot/v1",
  "purpose": "production",
  "model_API_calls_allowed": 0,
  "production_switch_allowed": false,
  "screen_prepared": {"path": "/absolute/screen/prepared.json", "sha256": "ACTUAL_SCREEN_SHA256"},
  "main_prepared": {"path": "/absolute/main/prepared.json", "sha256": "ACTUAL_MAIN_SHA256"},
  "recovery_index": {"path": "/absolute/recovery512/index.json", "sha256": "ACTUAL_RECOVERY_SHA256"},
  "protected_roots": ["/absolute/running-annotation", "/absolute/running-PTN"],
  "wall_budget_seconds": 10800
}
```

这里`purpose=production`表示真实环境执行有限试验，**不表示可以生产标注或自动切换八卡**；实际合同仍为`pilot_validation`。CPU合成测试必须显式用`cpu_fixture`和假执行器，真实用途禁止假执行器。

执行前重新核两份准备收据、全部冻结文件、合同、命令参数和源记录子集关系。每份矩阵内部先检查三轨仅批宽不同；30/3000同profile合同和源码必须一致；512恢复来源须为3000完整记录的子集。输出必须避开真正仓库或部署控制源码、计划文件、有限输入、锁根、两份矩阵和原运行目录，不能把相同父目录错误地当成整个受保护仓库。

每轨只调用固定的`gpu_launch.py`，沿用UUID锁、两次空闲快照、CUDA挑战、模型来源和持续独占检查。真实父进程完成、完整有限侧车读回且CUDA排空归还后才进入下一轨。失败保存完整日志和失败记录，不开始下一轨。取消或超时只通过已绑定PID/start/nonce及pidfd通知本次自有父进程，等待原清理，不按裸PID结束未知进程或PTN。

`audit_native_transformers_batch.py`完整读取有限侧车、提交记录、整批计划/原生包、worker终态和资源证据，核实际请求/PCM/模型/合同及生成行映射、输入mask、原始矩形token、EOS后填充和有效token。所有来源、未知、失败和缺少窗口均保留在分母；批宽上限不能冒充每次实际批宽。审阅文字和字界时要报告文字不同的窗口，不能只展示共同文字子集。

## 恢复和性能数字的含义

主试验三轨各3000条新执行，随后三轨分别以相同labels和合同、新512队列验证完整已发布结果恢复：要求512完整侧车命中、零新ASR、零新定位、零新侧车提交，原文件字节、mtime、inode均不变。比较和计数任一不符合就保留失败，不降低要求。

这项512验证不等于“整批ASR已保存、侧车只发了一部分”之后的真实进程故障恢复；后者的CPU反例和真实GPU证据分别保存。现有完整侧车始终复用；未提交批次只允许原成员、原顺序重做，不宣称未知计算逐位相同。

总墙钟包含加载、模型摘要核验、资源挑战、读写和完整有限读回；纯ASR、Ultra与累计工作进程时间分别计量，不能混作同一分母。三域均衡3000条不代表全量VoxBlink占绝大多数的自然分布，正式剩余时间必须结合上线后的实际新增量。初次30条主要用于揭露配置和输出问题，不能拿首次页缓存差异外推17天。

新GPU源码冻结后不改。若实际试验前后源码再改，要记录新版本、差异和需重做的验收；CPU成功或平台Running不等于真实批处理更快、字界质量通过或正式八卡已接续。
