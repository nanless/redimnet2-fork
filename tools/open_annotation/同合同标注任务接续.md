# 中断后继续原合同标注任务

`resume_existing_annotation.py`只处理已经明确终止的既有标注任务。它保留原冻结代码、合同、全量输入、队列、侧车版本和一次任务声明，另外创建一次接续声明及新的资源证据。它不把旧结果复制成新生产者，不改队列租约，不删除锁，不改资源守卫，也不启动新训练或新转写算法。

默认调用只读取固定原件，并短时独占已有的语义锁、队列父锁和活动片锁；没有创建旧目录或修补文件。只有显式`--execute`才调用原冻结检查和原GPU父入口。这里的接口准备与合成CPU通过，不证明真实平台、显卡、原音或全量结果已经检查完成。

## 为什么不能直接重新执行旧启动脚本

旧正式启动脚本是第一次创建任务的入口。它取得同一合同和原全集对应的语义锁，以不可覆盖方式写`.claim.json`，再用不带`-p`的`mkdir`认领全新运行目录。失败后声明仍然保留，所以直接重复启动会被拒绝。不能删除声明，不能通过改运行目录名绕过它。

接续器核原声明的路径、字节摘要、原admission摘要、合同、索引和原运行目录；原声明始终保留。在同一个语义锁下，新建独立的`.resume-attempt2.claim.json`，再使用原队列和标签继续。当前只实现第一次显式接续，即资源输出`resources-attempt2`。一旦该接续声明存在，无论检查或启动在哪一步失败，都不能隐式重试；须先查明该次任务、进程和证据，再另行审阅下一次接续。

## 两种部署协议不能混用

输入的`protocol`必须明确选择：

- `legacy_frozen_v2`：旧admission为`ultra-eight-three-train-spec/v2`，原检查脚本是`ultra_w8_gate_v2.py`和`verify_ultra_cloud_mounts_v2.py`。旧`gpu_launch.py`没有`--run-root`或`--device-lock-root`，接续器不会传这两个参数。它对已核固定源码做抽象语法树（AST）读取，要求顶层`ROOT=Path('...')`、`GLOBAL_LOCKS=Path('...')`与描述一致，并核该程序实际调用`G.DeviceLocks(GLOBAL_LOCKS,...)`；不导入或执行旧源码来猜常量。
- `explicit_roots_v3`：admission为`ultra-eight-three-train-spec/v3`，检查脚本为`cloud_gate.py`和`verify_cloud_mounts.py`。原admission显式绑定任务根和公共设备锁根，原GPU入口接收对应两个参数。

旧协议兼容只保持实际旧接口，不放宽新协议，也不重新封装旧bundle来伪称同一源码。两种协议都重新核原`bundle_files.json`及其中所有成员的摘要。固定解释器路径沿用原admission；若它是明确的解释器软链接，则保存实际解析目标及字节摘要，并在每次命令调用前重核，不能换解释器。

## 输入描述

描述schema为`annotation-existing-resume/v1`。正式用途是`purpose=production`；合成测试是`cpu_fixture`，后者不能通过CLI调用真实命令。所有文件引用都是`{path,sha256}`，摘要针对相应原件的实际字节，不能写说明字符串或替代原件。必需字段如下：

| 字段 | 含义 |
|---|---|
| `protocol`、`attempt_number` | 原部署协议；当前`attempt_number`严格为整数2 |
| `old_task_id` | 已中断的原平台任务身份 |
| `task_root`、`run_root`、`code_root` | 原任务根、原运行目录和原冻结生产代码目录 |
| `queue_root`、`output_root` | 严格为原`run_root/queue`和`run_root/labels`；后者是版本目录的父目录 |
| `resource_output` | 严格为尚不存在的原`run_root/resources-attempt2` |
| `evidence_root` | 尚不存在的新审阅目录；父目录已存在，与原运行/代码及设备锁树不交叠 |
| `python`、`python_binary`、`device_lock_root` | 原解释器argv路径、同bin目录实际解释器二进制的`{path,sha256}`及原公共设备锁根 |
| `legacy_source_alias` | 仅旧v2的明确共享挂载别名`{alias_path,target_path}`；生产只接受`/root/group-shared`到`/shared/group-shared`这对已核关系 |
| `contract`、`full_index`、`bundle` | 原合同、原全集索引及原`code_root/bundle_files.json`的引用 |
| `admission`、`original_launcher`、`original_claim` | 原正式准入描述、原fresh启动脚本及原一次声明引用 |
| `semantic_lock`、`resume_claim` | 原合同SHA和原索引SHA组合对应的既有`.lock`及新的`.resume-attempt2.claim.json` |
| `terminal_observation`、`writer_absence` | 下述真实外部观察原件及摘要 |
| `checks` | 两项原检查脚本引用和精确参数，顺序先准入、后挂载 |
| `model_API_calls_allowed`、`release_training_labels` | 严格为整数0和false |

正式原分母固定为11,521,178：VoxCeleb2 1,092,009、VoxBlink2 9,904,382、CN-Celeb2 524,787；同合同恢复不创建剩余索引替代原分母。

`checks`的每项为`{script:{path,sha256},args:[...]}`。第一项参数必须严格为`["--live","--spec",原admission路径,"--spec-sha",原admission摘要]`；第二项没有`--live`，其余相同。实际执行命令由接续器构造成`[原python,"-B",固定脚本路径,...args]`，不接受shell命令字符串。脚本名称与所选部署协议对应，不用现行维护脚本假冒旧版本。

`terminal_observation`使用`annotation-writer-terminal-observation/v1`，保存原`task_id`、原`queue_root`、带时区的`observed_utc`、任务终态、整数`active_workers=0`及唯一平台worker的名称与终态。worker名称绑定`task_id + "-worker-0"`。观察必须在一小时内且不在未来。

`writer_absence`使用`annotation-writer-absence-observation/v1`，共同字段是同一`task_id`、原`run_root`、一小时内的`observed_utc`以及`other_successor_tasks=[]`。

- 旧v2使用真实平台任务及实例终态，加本程序取得全部既有稳定锁的证据。原件必须声明`evidence_basis="platform_terminal_and_stable_locks"`、`platform_instance_state`为终态、`remote_proc_enumeration_performed=false`。这不宣称在另一节点枚举了旧容器`/proc`或认出了内核进程号。
- v3使用已明确核实的`active_parent_count=0`、`active_worker_count=0`，二者必须是整数，布尔false不能充数。

这些外部JSON必须依据实际平台或进程观察制作。接续器验证其身份、摘要和时效，**不会认证平台账号或替代真实查询**。单靠手填“终止”和空数组不能作为现场恢复授权。

## 检查与执行

```bash
python3 -B tools/open_annotation/resume_existing_annotation.py \
  --spec /absolute/private/resume-spec.json --spec-sha '<实际SHA256>'
```

默认检查不会调用原gate、挂载脚本或GPU。它要求旧queue的`identity.json`、`broker.json`、`completion_map.bin`、`.parent.lock`及`broker.lock`都存在；标签版本身份也必须存在。因为原队列构造器会初始化缺失文件，接续器必须先拒绝缺失，不能把中断任务误当新任务。

它用轻量槽检查核当前已封账来源下界，并在队列父锁内复核broker不变。最多八个活动片逐条重开已保存侧车和commit，核原source、job key、合同、字节及原音stat；孤儿或损坏保留原件并拒绝，不调用会补commit的`SidecarStore.lookup()`。同时检查已有活动片锁能独占。检查没有扫描所有已完成侧车、全部未领取片或原音，不是千万条完整终验。

旧共享路径的软链接仅由接续器局部读取器处理：显式别名必须在现场仍是指向明确目标的同一关系，后续路径不得再经过未声明软链。原`record.source`及`audio_path`原文不改；仅为stat读取解析该固定别名，完整比较device、inode、bytes、mtime和ctime。跨节点设备号不同也会明确拒绝并给expected/actual，不能删字段掩盖差异。通用`physical`和原准备器的规则没有放宽。

准备具体描述、审阅CPU反例和实际外部证据后，已获恢复授权的维护者才可加`--execute`。执行创建新证据目录，保存`prepared.json`。取得原语义锁后重新检查原件和父锁，创建永久接续声明；任何后续失败都保留该声明和`failure.json`，不自动重试。

随后执行两个原检查，保存命令、返回码及完整日志。两者都通过才允许调用一次原`gpu_launch.py`，固定`auto8`、60000MiB预算、2592000秒保护上限以及原合同/索引/队列/标签。保护时限不是预计完成时间。资源输出只有`resources-attempt2`发生变化。

原检查运行后还会重新读取bundle及其全部成员、原启动脚本、两个检查脚本、实际解释器二进制、明确共享别名和语义锁inode。原GPU入口调用前再次复核，不能在首次检查后改`worker.py`或旧控制脚本而仍启动GPU。broker及部分片完整结果也须与原快照相同。

实际子进程启动后另写带PID及argv的`*.log.process.json`；`gpu-start-intent.json`只代表调用意图。失败记录分开`launch_attempt_count`与已记录的实际`launch_count`，不能把参数检查失败算成已启动GPU。CPU注入假执行器的计数明确带合成标记，不能当真实进程证据。

语义锁的同一文件描述符（FD）贯穿命令并传给子父入口；原队列父锁仅在纯读检查时临时持有，之后交给旧GPU父入口自行重新取得。不能保留一个独立队列锁FD，再让原入口用另一个FD加锁而误以为可重入；竞争出现时必须拒绝。

原入口保留全部双快照、物理设备锁、随机显存挑战、持续compute row检查和精确worker清理，不共享第二个不明CUDA context。原程序输出非零、结果缺失、合同/索引/bundle不符、未归还资源或未完成输出核验，都不能写成成功。接续器保留原`parent_result.json`引用及摘要；原结果成功仍不证明人工文字或完整字质量。

## 为什么旧结果不会重新标注

原队列仍使用原游标和已完成片提交。已封账片不会重新进入模型；活动片重新取得稳定锁后使用新generation，旧generation不能发布。对活动片内完整侧车，原worker先核已有结果并复用，缺失部分才解码和调用模型，阶段缓存也按原合同身份复用。

当前队列优先推进尚未领取的游标，到尾后才回收旧lease；因此八个中断片可能最后补齐。这是原实现的次序，不是丢失。不能手动删除lease、改游标或按领取时间夺锁。完整侧车缺commit的特殊崩溃窗口需要单独封存并审阅修复，不在本接续器默认检查中偷偷补写。

## 本机验证的范围

`tests/test_resume_existing_annotation.py`使用六条合成来源、合成旧合同/准入与假命令执行器，检查默认不写、旧字节和mtime不变、原分母不换、原semantic锁贯穿、旧v2常量及CLI、缺旧元数据拒绝、活动锁拒绝、陈旧/非终态/活动worker拒绝、孤儿保留、gate失败不启动、GPU入口失败无自动重试、已有输出及路径别名拒绝。它不会导入真实模型、运行GPU或查询平台。

真实执行还必须核本次原件、旧部署协议、平台和资源，并继续检查实际八个worker、封账增量、复用、异常及最终完整结果。不能拿CPU假结果或单次退出码冒充真实八卡恢复成功。
