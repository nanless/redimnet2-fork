# 旧结果与新剩余输入怎样联合核验和读取

`union_coverage.py`和`union_consumer.py`提供联合数据检查及唯一读取接口。最初CPU实现使用本机六条合成来源验证，当时没有读取服务器全库、原音、模型或GPU。2026年10月27日后续现场准备及实际全库核验的状态分别以日期报告为准，见[现场故障与后继恢复记录](../../docs/reviews/2026-10-27-WebShell真实试验故障与标注恢复.md)；不能将历史CPU实现范围外推为后续现场未运行。工具不改写正式旧标注结果。工具成功不授GPU运行、云任务提交、人工完整字质量或训练/评测资格。

## 输入描述

联合描述使用`annotation-union-coverage/v1`。以下都是调用者明确提供的实际路径，SHA必须是对应原件的真实摘要。示例中的说明字符串不能直接作为摘要使用。

```json
{
  "schema": "annotation-union-coverage/v1",
  "purpose": "production",
  "expected_full_source_count": 11521178,
  "full_index": {"path": "/absolute/original/index.json", "sha256": "原全量索引SHA"},
  "continuation_plan": {"path": "/absolute/final/coverage-plan.json", "sha256": "最终剩余准备报告SHA"},
  "old_producer": {
    "id": "original-producer",
    "contract": {"path": "/absolute/old/contracts/silver.json", "sha256": "旧合同SHA"},
    "queue_root": "/absolute/old/queue",
    "sidecar_tree": "/absolute/old/labels/old-version"
  },
  "new_producer": {
    "id": "new-producer",
    "contract": {"path": "/absolute/new/contracts/silver.json", "sha256": "新合同SHA"},
    "index": {"path": "/absolute/final/index.json", "sha256": "真正剩余索引SHA"},
    "queue_root": "/absolute/new/queue",
    "sidecar_tree": "/absolute/new/labels/new-version"
  },
  "selection_policy": "old_retained_else_new_remaining",
  "release_training_labels": false,
  "model_API_calls_allowed": 0
}
```

`production`固定原分母11521178和VoxCeleb2、VoxBlink2、CN-Celeb2的原计数，不允许把剩余数量当全量分母。它还核实际逐源数据域和主训练/大间隔训练用途。`cpu_fixture`只用于明确的合成小样本，报告保留该标记，不能当正式全库或旧八卡运行准入。

`continuation_plan`必须由最终准备产生，状态为`final_prepared_not_started`；不接受运行中的provisional报告。旧、新合同均保留自己的SHA及命名空间，不复制记录后修改producer，也不改旧缓存身份。

每个producer合同在入口按SHA读取一次，逐条重开侧车时核对合同版本、原声来源、job key、模型文件provenance以及runtime策略。不能在记录里只填正确合同SHA，却宣称另一版本、另一模型路径/权重或另一执行策略。正式合同必须具有完整的asr/aligner本地模型文件身份和非空runtime；仅`cpu_fixture`允许无models/runtime的最小合成合同，且它不能转成正式准入。消费端也只在打开时加载已pin合同，逐源不反复哈希合同文件。

最终准备会在旧父锁保护下一次流式扫描未领取片，验证其中预先存在的旧侧车/commit，将这些结果写到新的`retained-unclaimed.jsonl`，并在报告中保存`retained_unclaimed_sources_ref={path,sha256,count}`。被保留的来源从真正剩余输入剔除，部分片已有结果也不重复进入新输入。没有预置结果时账本为空，不改变原来无预置结果的接续语义。provisional只声明`unclaimed_sidecars_scanned=false`，不能拿它当最终无预置结果证明。

联合工具按行核账本SHA和数量，使用SQLite辅助表检查每源唯一，核每条确属原broker尚未领取片、原source记录及旧producer不变。错摘要、重复账本行、孤儿或已经发布却未列入账本的来源直接拒绝，不会靠忽略问题重新计算。

## 两种核验方式

`validate_union(spec_path, spec_sha, mode='plan', *, output_index=None)`有两种模式：

- `plan`检查原全量来源集合、旧已保留结果和新剩余输入是否精确互斥、完整覆盖。旧保留结果逐条核提交和字节，不要求新结果已经存在，也不创建新生产队列。此模式要求一小时内的外部旧任务终态观察，以及当前既有旧父锁独占和稳定broker。
- `complete`增加新剩余生产者的完成槽、分片提交、侧车和逐源提交核验。它不要求多天前的真实旧终态观察被重新伪造或刷新，仍核原件摘要、当时终态、当前旧锁与旧broker一致。新结果必须全部完成，没有活动租约。

终态JSON来自外部真实观察，工具不认证火山账号或平台。旧父锁以只读方式打开且不创建；当前writer仍持锁就拒绝。锁只在数据核验期间持有，释放后不等于未来任务获得运行租约。

检查覆盖的是实际每源记录摘要，不只是两个计数相加：

1. 原全量按分片读入磁盘唯一索引，跨片重复来源直接拒绝；同ID改原记录也不能混入。
2. 旧完成片集合须与当前固定旧broker/完成槽完全对应；每源的侧车、commit和片提交保持原摘要。
3. 未封账片的已发布来源核原侧车和commit后保留，不能漏列到新剩余集合。未领取片若存在未被准备报告列出的旧结果或孤儿，也拒绝，不默默重算或修复。
4. 剩余来源须在原全量中，原记录和输出相对路径相同，且此前未被旧生产者选择。多列、重复、少列和与旧结果重叠都会拒绝。
5. 完成核验还重开新片的全部侧车，核决策计数、工作身份、逐源commit及固定完成槽，不拿退出码代替全量结果。

这是一次全域文本和文件元数据检查，**不是轻量运行进度巡检**。大规模会消耗数据库磁盘、旧结果读取和大量路径查询，不应频繁用于运行任务。它不解码或重哈希原音；所谓来源身份是保存字段、原始来源记录和提交链的核对。

## 显式生成消费索引

不给`output_index`时只使用临时SQLite，返回数据核验报告，不留下可复用消费库。给出新外部路径时生成独立消费索引，并返回文件路径和SHA。最终文件只在核验成功后以不覆盖方式发布；失败时不留下貌似成功的最终文件，未完成临时文件保留作故障证据。

```bash
python3 -B tools/open_annotation/union_coverage.py \
  --spec /absolute/union.json --spec-sha '<联合描述SHA>' \
  --mode complete --consumer-index /absolute/new-audit/consumer.sqlite
```

消费索引不能放进原输入、旧/新队列、侧车树或合同目录，不得覆盖已有文件或使用软链接路径。SQLite使用文件临时区和有界缓存，来源ID不整体放入Python集合；完整核验的库另建原顺序索引，逐条消费无需重新排序千万条。索引与准备报告本身、一个分片和少量侧车仍需要内存，不能将“SQLite缓存8MiB”误写成总进程内存上限。

## 唯一读取

```python
from union_consumer import UnionConsumer

with UnionConsumer(spec_path, spec_sha, database_path, database_sha) as consumer:
    selected = consumer.resolve_source(source_id)
    for selected in consumer.iter_selected_sources():
        # selected保留producer_id、原source、原record和原摘要。
        # 训练与正式评测资格始终没有在消费时释放。
        pass
```

也可使用同名模块级`resolve_source(...)`和`iter_selected_sources(...)`，必须显式提供数据库路径与SHA。反复读取建议复用一个上下文，避免每条都重新哈希大型数据库。

消费者只接受与联合描述精确绑定的`complete`消费索引，以只读SQLite方式打开；不会创建新库、重建旧队列或调用可能修复commit的`SidecarStore.lookup`。它按固定原分片位置和来源记录摘要找到原来源，选择已声明生产者，每次重读所选侧车/commit并核摘要，不按mtime或“最新目录”猜。原来源分片缓存至多4片；分片或数据库打开后发生可见改变会重新核验或拒绝。

输出含原始模型内容和来源标识，须保存在私有审阅位置，不能复制到公开Git。`candidate`仍是机器候选，`unknown`仍待复核，读取成功不转为可训练数据。

## 与云端检查的关系

`cloud_gate.py --union-mode plan|complete`是联合数据入口，返回`annotation-union-data-readiness/v1`，使用`data_checks_passed`而不是旧云运行结果的`passed`。它保留原正式分母，且`GPU_execution_admitted`、`cloud_submission_admitted`恒为false。原W2、资源挑战、恢复、人工质量和实际八卡入口条件都保留，数据集合正确不替代它们。

本轮合成测试完整走过：六条原来源→三条旧保留→三条新剩余发布→联合完整核验→逐源返回原producer。反例覆盖旧活动锁、陈旧终态、漏项/重叠、同ID改记录、遗漏已发布来源、旧字节变更、新结果未完成、数据库变更、路径逃逸及CPU夹具误作正式范围。实际测试数量和最终集成记录以本轮统一汇总为准，不能把合成六条说成千万条已完成核验。

另外一条完整文件级反例在原未领取片预置一份已发布结果，实际经过“最终准备→联合数据入口→新剩余发布→完整核验→唯一消费者”得到4份old、2份new，而不是把预置来源再跑一次。既有新侧车树或新队列若身份错误，plan也会拒绝；“允许尚未创建的新树”不能用来忽略已经存在的错误身份。

本描述针对仍有新剩余输入的接续。若准备器返回`all_sources_retained_no_successor_needed`，应停止创建新任务，并使用旧生产者的完整终验；不能人为造一个零分母后继来满足本工具接口。

## 显式跨节点内容后继：保持旧严格恢复不变

2026年10月27日的真实严格恢复在GPU入口前因设备号不同拒绝。新内容协议使用`portable_encoded_sha256/v1`，是另一份明确描述下的新后继数据检查，不能作为旧同输出恢复的`skip_stat`选项。旧侧车、commit、队列、合同、冻结包和所有异常原件保持原字节；新生产者使用新的合同版本、队列和标签树，实际输入只包含真正缺失来源。

这条后继保持旧模型计算方式。联合门逐项要求旧、新合同的`models`、`runtime`、`decoder`、`alignment`、`quality_policy`、`source_files`及`engine_source_files`相同；正式模式还要求FP32/eager、TF32关闭，并保留原推理模块摘要。合同SHA及版本须不同。原13模块及旧时间规则不能被当前14模块、v2时钟、新规范化或更大批次替换后仍称相同计算条件。这里检查的是固定声明的一致性；实际冻结字节、模型文件和运行资源仍须由独立启动入口检查。

联合描述在原有字段之外必须显式增加：

```json
{
  "source_identity_mode": "portable_encoded_sha256/v1",
  "portable_source_spec_ref": {"path": "/absolute/new-preparation/portable.json", "sha256": "实际摘要"},
  "portable_source_ledger_ref": {"path": "/absolute/new-preparation/portable-source-evidence.jsonl", "sha256": "实际摘要", "count": 123},
  "current_terminal_observation": {"path": "/absolute/current-observation.json", "sha256": "实际摘要"}
}
```

`count=123`仅说明字段位置，须替换为实际账本行数；原`expected_full_source_count`始终为11,521,178，不能改成剩余数。上述两个portable引用必须与固定`coverage-plan.json`里的引用完全相同，不能只提供计数或在读取到某个旧报告时自动开启跨节点模式。未显式声明新模式时，出现portable证据会被拒绝，旧严格准备和恢复规则没有改变。

内容规范使用`annotation-portable-source-spec/v1`，明确旧合同、原全库索引、旧队列、旧标签树及唯一共享挂载别名。正式规范只接受已核的`/root/group-shared`到`/shared/group-shared`关系。它只允许`device`不同，其余inode、字节数、mtime和ctime均须相同。新账本保存完整新旧stat、实际编码文件SHA256、原侧车/commit摘要和来源记录摘要；准备器真正读取编码文件，要求读取前后完整stat稳定，实际SHA等于旧发布记录中的文件SHA。它不重解码PCM，不改变原`source.audio_path`、原分片或旧生产者身份。

新准备器仅对**旧活动片和未领取片中已发布且要保留的来源**生成内容证据。已完成片继续通过原完成槽、原片提交和原producer记录保留，不能把115万已封账媒体说成此次重新哈希过。计划须明确：

- `fresh_media_scope="retained_partial_and_unclaimed_only"`；
- `completed_media_scope="original_completed_chunk_reference_not_media_rehashed"`。

联合门按有界行读取固定账本，使用SQLite检查唯一来源，再对每个被选择的partial/unclaimed旧结果重开原侧车和commit，核实际字节摘要及全部内容证据绑定。缺账本、重复账本、账本多列来源、将completed来源冒充fresh来源、允许非device变化或伪造encoded SHA，均拒绝。内容账本不能用于掩盖孤儿、损坏commit或来源重叠。

历史解码失败只能保留为`historical_decode_failure_preserved_not_content_verified`，且原结果必须仍为failed；不得填入虚构的实际SHA或stat，也不能计入fresh内容核验数。成功内容证明单独计为`encoded_content_verified`。联合报告分别给出两类数量，`source_audio_rehashed=false`表示**本次联合门自身**不再读取原音；`upstream_encoded_content_verified_count`才是上游已保存并核绑定的内容证据数量。

### 长扫描后的新鲜平台观察

准备可能超过一小时。计划里的原终态观察作为历史原件保留，不得改时间冒充新查询。portable联合描述另提供`current_terminal_observation`，绑定同一旧任务ID和旧队列、唯一平台worker名称及终态，`active_workers`须为整数0。

`mode=plan`要求这份新观察在一小时内且不在未来；计划里的原观察仍须身份一致、真实终态且非未来，但可早于一小时。`complete`保留当时已固定观察，不要求几天后伪造新时间。旧strict模式的原有一小时时效规则不变。工具只验证外部观察结构、摘要和时间，不认证平台账号，也不能把CPU验证当新鲜平台查询。

原父锁仍须按既有文件以只读方式取得并核当前device/inode；跨节点的内容协议没有放宽锁身份。最终准备与实际联合门若不在同一挂载身份下，需要另行生成正确的新证据，不能静默删除锁device字段。联合门完成后释放自己的旧父锁，启动维护者再取得旧父锁并贯穿新GPU父进程；新GPU只取得新队列的父锁，避免用另一个FD重入同一旧锁。启动前仍须重核旧broker、原语义锁、唯一永久后继声明和实际空闲八卡。

本轮新增CPU集成实际走过：六个合成文件→原活动片device差及真实encoded SHA→真正准备器内容账本→保留原未领取片预置结果→6=4旧+2新→新生产者发布→完整联合核验→原顺序唯一消费者。旧字节及mtime不变。该小文件集成不代表真实千万条已核完，也不授八卡运行、模型文字、完整字或训练资格。

### 大库目录项索引与两阶段证明

新版portable准备器在旧父锁下对旧标签树做一次目录扫描，生成新的`portable-sidecar-inventory.sqlite`，不是逐个对一千多万条缺失来源调用PFS的`exists/stat`。它拒绝未知文件、软链、孤儿、未映射到原全集的标签路径；只跳过已知根`.stage_cache`，不遍历缓存内容。原已完成片只登记来源与目录项，不在准备期重读其百万份内容或媒体。

有目录项库时，plan与union spec还须提供相同的`portable_sidecar_inventory_ref={path,sha256}`；plan保存`portable_sidecar_inventory_summary`。联合门按SHA核文件，以SQLite `mode=ro`附加读取，核其中policy、旧producer、原全集、每个路径的source ID和completed/partial/unclaimed类别，以及全分母计账。未被旧结果选择的来源只查固定目录项库，不再逐条访问缺失PFS路径。库SHA、来源、类别或数量不符均拒绝；核验不更新目录项库，不修复原目录。`portable_sidecar_inventory_verified`独立报告实际使用情况；没有该库的受控输入仍走原逐路径检查，不能声称获得目录扫描的性能收益。

联合数据核验本身仍会重开旧已保留侧车、逐源commit及原片提交；“准备器未重读已完成内容”不能扩写成“联合完整核验只做计数”。没有重哈希已完成音频，也没有重新推理旧结果。

在开发节点完成prepare与union后，跨节点启动可消费固定的数据准备证明，明确绑定plan、union spec、消费SQLite、原全集、旧/新producer和剩余索引的实际SHA。该证明只说明当时数据分区正确，plan模式SQLite不是完整新结果已完成的消费证明。旧broker和completion map应固定全文件SHA，实际启动在新节点取得当前原语义锁和旧父锁后重核这些固定原件，再贯穿新GPU父进程。历史准备锁与当前运行锁是两个观察，不能拿历史FD当现在的租约，也不能在另一节点假称重新通过了原device绑定的union检查。当前节点的FD与路径须互相核dev/inode；跨节点文件系统身份及历史inode对照由明确的新启动协议检查，不能在旧strict工具里加跳过选项。

本地测试另用断言禁止对缺失旧路径调用`Path.exists()`，实际验证固定目录项库分支仍能完成联合数据核对，且库原字节不变。篡改库SHA或来源绑定会被拒绝。它不证明PFS吞吐、真实全库耗时或新云端锁已取得。

## 旧完成片纯读并发：显式选择，缺省串行

联合描述可增加整数`retained_read_workers`，当前支持1至4，缺省为1。布尔值、浮点数、字符串、空值及越界值均拒绝；CPU夹具和production使用同一规则。这个字段只决定数据核验的读取容量，不修改模型、计算精度、音频、侧车、角色或选择结果，也不授GPU资格。已部署的旧工具不会被热改；启用须使用另一个固定源码版本及新的描述SHA。

只有**旧生产者已完成片**内的`read_result`进入全局`ThreadPoolExecutor`。每次读取使用独立文件描述符和JSON对象，schema及规范化检查使用局部变量，共享合同只读。线程内不访问SQLite，不改选择集合或决策计数；返回值只含侧车SHA、commit SHA和决策三个小字段，不把整份record长时间排队保存在主线程。

每批最多提交256条；大片也分成至多256条的批次，上一批全部返回后才提交下一批，不跨片预取。`executor.map`按原来源顺序返回。主线程仍执行原来的逐源片收据、job key、相对路径、字节数、决策和SQLite写入，片级完成槽、片提交、来源ID摘要及最终决策计数全部保留。partial、unclaimed的内容证据及新生产者complete核验继续串行。

线程内失败时，主线程在仍持旧父锁的范围内执行`shutdown(wait=True,cancel_futures=True)`，取消未开始的读取并等待在途纯读结束，然后抛出原异常。已失败的临时消费数据库保留，不发布最终消费数据库。这里的“有界”指线程数及待处理记录数，不承诺PFS文件I/O一定在若干秒内返回。

报告新增以下计账字段，完整保存到消费数据库的metadata：

- `retained_read_workers`：实际配置的线程池容量上限，不是测得的平均活跃线程数；
- `retained_read_executor`：`serial`或`thread_pool`；
- `retained_read_scope="old_completed_chunks_only"`；
- `retained_read_submission_limit`：串行1，并发256；
- `retained_read_max_submitted_batch`：本次实际提交过的最大批大小；
- `retained_completed_source_reads`：在主线程通过逐源片收据检查的旧completed来源数量，不包括partial/unclaimed。

不能把这些容量字段当速度收益。现场应在同一已固定完成片上分别用1、2、4读取，比较实际墙钟时间和按原序返回的来源/SHA/决策摘要，并观察共享存储压力及主训练速度。收益不稳定或无收益时保持1；不根据理论线程数宣称两倍或四倍加速。

小型CPU测试强制第二条先完成，核返回顺序和串行证明完全相同；对SQLite加主线程守卫；用600条合成元数据验证提交批次为256、256、88；注入并发异常，验证旧父锁保持到在途读取结束且最终库不发布。测试不读取媒体，也不构造模型。

## 可选的spawn进程纯读与有界对照（2026-10-27）

显式设置`retained_read_backend="process"`和整数`retained_read_workers=2`或`4`，才能让旧completed片的独立文件解析进入`ProcessPoolExecutor`。缺省backend仍为`thread`，缺省workers仍为1；即使显式写process而workers为1，也仍然串行执行，不启动子进程。新字段不改变模型、精度、窗口、时间规则、旧来源或结果选择。正在运行的旧版本不能热改；现场应保留旧审计，新版本先做少量来源的对照。

进程入口位于模块顶层，固定使用`multiprocessing.get_context("spawn")`；不使用fork，不继承父进程已经加载的模型或CUDA上下文。入口及依赖是标准库代码。父进程和initializer拒绝已加载的`torch`、`qwen_asr`、`vllm`；父进程在spawn导入`__main__`前隐藏CUDA/NVIDIA/HIP/ROCR设备，整个独立CPU审计pool结束或失败后精确还原原环境。子进程之后也拒绝导入这些推理库。该限制仅作用于此CPU审计进程，不修改其他任务的环境或设备。

每个子进程initializer仅接收一次已固定的producer和contract字典，核本机验证器及直接依赖的文件SHA，保存小型初始化收据到stderr。每个job只携带一条来源元数据和期望侧车/commit SHA，返回侧车SHA、commit SHA及决策三个小字段。侧车记录不进入长期结果队列，不能把音频、模型或大record对象当进程间传输数据。SQLite、进度、计数、逐源片收据检查仍只在主进程。

Linux initializer读取父PID及`/proc/<pid>/stat`启动ticks，在设置前后均核父身份，再用`PR_SET_PDEATHSIG`设置不可忽略的SIGKILL并用`PR_GET_PDEATHSIG`回读。父进程已在设置前死亡的情况必须被前后身份检查拒绝，不能只相信prctl返回0。每个job前再次核父PID/start。这个机制跟随创建子进程的父线程生命周期；审计主流程在主线程创建pool，不在GPU或后台推理线程中创建。参见[Linux man-pages原始说明](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html)。

本机为macOS，无法验证Linux内核行为；只有显式`purpose="cpu_fixture"`可在非Linux启动process reader，worker收据必须写`unsupported_nonlinux_cpu_fixture`、`linux_parent_death_signal_verified=false`。production的多进程读在非Linux直接拒绝。Mac上实际spawn通过和prctl竞态mock通过，不能写成Linux生命周期已实测；真实Linux启动收据须另行保留。启动收据包含实际worker PID、父PID/start及源码身份，不能把配置容量当实际活跃进程数。

无论线程或进程，每批仍最多256条，`map`结果全部收齐后才按原source顺序交给主进程；本批结束前不提交下一批。pool在旧父锁退出前统一`shutdown(wait=True,cancel_futures=True)`，覆盖正常结束、worker错误及主进程的SQLite/进度/片收据错误。关闭是幂等的；外层异常处理不能在放锁后留下未排空的reader。失败仍保留临时SQLite，不能发布最终消费库。不承诺文件系统I/O在固定秒数内返回；SIGKILL父死亡保护也不是文件I/O超时算法。

联合报告增加`retained_read_backend`、`retained_read_process_start_method`及`retained_read_process_lifecycle_platform`，原`retained_read_executor`扩展为`serial|thread_pool|process_pool`。`linux_prctl_in_initializer`表示该平台采用该机制，实际worker设置和回读事实在stderr逐进程收据中；没有启动worker时不能从报告字段推断已有内核实证。所有GPU/模型准入字段仍为false。

### 同片有序证明及墙钟对照

`benchmark_retained_reads.py`复用联合门的`retained_read_pool`和`_complete_chunk`，不能独立复制另一套进程生命周期实现。它要求固定的final plan及SHA，只读取选中的旧completed片：默认第一片、serial1，显式上限8片及2048条来源，默认来源上限1024；超限拒绝。它不创建或领取旧队列，不取旧父执行锁（可与既有只读审计并存），不授执行租约或联合全库通过证明。若现场可能仍有旧writer，必须先确认平台终态；该小基准自身不认证平台，也不提供写者排斥。

例如，在另一个固定源码目录中使用实际路径和摘要：

```bash
python benchmark_retained_reads.py \
  --plan /absolute/prepared/coverage-plan-metadata-finalized.json \
  --plan-sha 实际计划SHA256 \
  --positions 0,1,2 \
  --modes serial1,thread4,process2,process4,serial1 \
  --max-sources 1024 --purpose production \
  > /absolute/private/retained-benchmark.json \
  2> /absolute/private/retained-benchmark.stderr.jsonl
```

每种模式只创建一次pool并在多个所选片之间复用。每条原序证明保存source ID、source元数据SHA、侧车SHA、commit SHA与决策；所有模式的完整有序证明摘要必须相同。程序重开原片提交、完成槽、producer合同、原全集索引及固定broker，结束后再核plan/index/contract和broker没有变化。出现未知模式、超限、同源重复、任何绑定或返回证明不同均报错，不能输出最终成功JSON。

stdout只有最后一份原生JSON，worker收据在stderr。`wall_seconds`是真实墙钟，`main_process_cpu_seconds`取`process_time()`，`reaped_children_cpu_seconds`取pool退出后`RUSAGE_CHILDREN`增量；它们包括本次启动成本，并非单条模型耗时或仅任务函数CPU。文件系统缓存及模式顺序会影响结果，所以允许末尾再跑serial1以观察顺序变化，不自动给出加速倍数或GPU收益。只有现场同一批500条以上来源实测有序证明完全相同、耗时显著改善且PTN未受影响，才考虑另启新版本CPU审计；原在跑版本继续保留。

新增CPU测试真实启动spawn，用相同小文件比较串行、线程及2/4进程有序证明；覆盖worker读错误、initializer源码身份变化、pool构造失败、父进程读后进度异常、环境恢复、临时库保留及锁内排空。Linux父身份设置竞态与GET不一致用模拟调用检查，macOS结果明确不充当Linux内核或GPU实证。进程池必须从可导入的`__main__`文件启动，不从交互stdin启动；见[Python官方ProcessPoolExecutor说明](https://docs.python.org/3.10/library/concurrent.futures.html#processpoolexecutor)。
