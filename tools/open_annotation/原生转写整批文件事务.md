# 原生转写整批文件事务

`native_transformers_batch.py`只负责原生Transformers批处理的输入身份、固定批次、整批文件保存和恢复。它不加载模型，不停止现有任务，不建数据库，不给自动字界发训练／评测资格。真正多行模型调用仍必须由独立新数值合同、实际Qwen模型、资源准入和有限GPU验证证明。

设计背景与实际模型接入条件见[原生转写批处理独立验证方案](../../docs/plans/2026-10-28-原生转写批处理独立验证方案.md)。旧`single_window_independent`合同、原23文件冻结包以及正在运行的三轨pilot不变。新增的`asr_fixed_cohort_fa_single/v1`明确表示转写可以固定批处理，但Ultra仍按FP32、eager、每次一个窗口执行。当前只用于新建的独立pilot，不能靠新增字段放宽正式silver准入。

## 为什么不能直接使用逐窗缓存

同一窗口与不同长短邻居一起padding后，生成文字和终止位置可能改变。因此，固定数值方式、窗口PCM和模型仍不足以证明批次身份相同；同批有哪些窗口、它们的原顺序也要保存。旧`StageCache`按逐窗输入查找，不能代替完整原批次提交。`ASRStageStore`使用SQLite，本实现不导入或构造它，也不使用其它数据库。

逐窗缓存仍可在原单窗路径继续使用；新ASR批处理分支必须由整批文件事务接管。Ultra的单窗定位缓存可以继续使用原检查。ASR整批结果尚未完整提交时，不能发布其中一行作为已经可以复用的缓存，更不能将错误批次缩小后声称恢复成功。

## 接口和输入

```python
store = NativeTransformersBatchStore(
    stable_group_root,
    producer_sha256,
    synthetic_fixture=False,
    contract_sha256=contract_sha256,
    model_sha256=asr_model_identity_sha256,
    max_batch_rows=4,  # 新代码同条件基线用1，候选用4或8
    policy='asr_fixed_cohort_fa_single/v1',
)
results = store.run_batch(
    original_rows,
    infer_batch=actual_native_inference,
)
```

`stable_group_root`必须是本claim／来源组的稳定专属目录，不得由当前剩余cache-miss集合、attempt nonce或时间戳计算。建议以真实已领取片ID和原完整sources组的摘要定位，由父输入及实际claim互斥保护。不能把它放入旧生产者树，也不能为了绕过坏计划换一个目录重试。

每行包含以下字段：

|字段|约束|
|---|---|
|`row_id`|必须严格等于`source_id + ':' + window_id`|
|`source_id`、`window_id`|非空、稳定的来源和窗口编号|
|`source_record_sha256`|完整source记录摘要；若有`context.source`还会直接重核|
|`input_pcm_sha256`|真正16k单声道模型输入PCM的SHA256|
|`model_input_frames`|正整数，不超过480000帧，即30秒|
|`model_sample_rate`|必须为16000|
|`audio`|本次要推理时必须提供一维有限float32 numpy PCM；缓存命中可以不再提供|

一次有限计划最多256行。调用者先排除已经通过原producer／本producer严格检查的完整侧车，再按新合同固定顺序组织未发布窗口。首次计划发布后，不能因部分结果已完成而给未提交批次换成员。实际传入PCM会在调用模型前核大小、dtype、有限值和摘要；缓存恢复若也提供PCM，同样检查，不能用不相干波形配一个旧摘要。

`producer_sha256`、合同SHA、ASR模型身份SHA、批宽和新policy写入store identity；任一改变都不能复用同一目录。Ultra的FP32/eager/单窗约束也显式写入身份。这些SHA须由调用层从冻结合同和模型原件生成；仅有SHA字符串不替代GPU启动前的实际文件守卫。

## 保存和恢复的顺序

1. 首次将整个有限计划原子发布为`plan.json`，固定全部行的完整身份与按1／4／8划分的批次。最后不足整批时保存其真实宽度，不补假音频、不复制窗口凑满。
2. 在store现有锁内，按计划处理每个涉及的批次。先检查整批结果是否已存在；存在则完整读回并核计划、模型、合同、批次及原生行覆盖。
3. 未提交批次必须提供原批全部行和原顺序。缺一个窗口、换顺序、改PCM或加入新窗口均拒绝；不自动重排，不单行补推理。
4. 真模型回调只能返回以原row_id为键的完整JSON结果。每行必须声明真实`native.actual_generate_rows`和`native.actual_generate_row_index`；宽度必须等于本批行数，位置必须与原顺序一致。多次generate、官方内部split／merge、padding、早EOS与token证据还须由实际Qwen回调独立观测和严格校验。
5. 将含完整原生输出、原输入计划、模型与合同身份的**整批单个JSON**原子发布到`batches/<cohort_sha256>.json`，再完整读回验证。文件内容摘要写在同一原子包内，不能出现“逐行缓存已经发布、其余批次还没有”的中间结果。
6. 所有本次所需批次完成后才返回逐行副本。每行附`durable_native_batch`，固定plan SHA、cohort SHA、原生包路径及文件SHA、该行在原批的位置，并附本次是否从旧完整包复用的`cache_hit`。这个运行标志不写回原始包。

恢复时可以只请求一个已经完整提交批次中的部分行，而且不需要重新提供音频，模型回调不会执行。未提交批次仍要求全部原输入。如果发生错误，`attempts/`保存完整异常、已返回的整批／部分原生JSON和“整批是否已经提交”状态，异常继续抛出。回调因第二次generate或映射异常而抛出时，它在异常属性`native_batch_evidence`携带的已捕获token、padding和预期行ID也完整保存。已提交后的中断不会擦掉原包；再次执行只复用原包。部分回调结果不会成为逐位成功缓存。

本模块只读已知identity、plan和被请求批次；没有遍历全库、媒体目录或已有标注目录。它本身不知道真实sidecar是否已发布，所以调用层仍必须在模型与新阶段执行前严格检查原producer／本producer结果，并在新旧树都有同源结果时拒绝。不能把完整侧车检查替换成这个store的存在性判断。

## 测试与当前限制

最初14项合成CPU反例覆盖：新代码batch1基线、batch4／8、整批保存、任意已提交子集零模型复用、未提交缺行／乱序拒绝、提交后中断恢复、部分原生输出保留而不发布、宽度／位置／外来行拒绝、实际PCM／完整source／30秒时钟检查、模型或合同或profile改变拒绝、新来源不能借旧计划执行、包与plan损坏拒绝、symlink和未知目录保留，以及数据库连接禁止。另一代理独立审阅并执行普通／`-O`各14项也通过。新增异常属性保存测试后，当前15项普通／`-O`测试通过。有限完整文件审计另见[原生批处理有限比较与恢复](原生批处理有限比较与恢复.md)。

这些CPU检查不说明batch4或8已经更快，也不证明Qwen在真实不同长度音频上的文字和完整字边界正确。新模型路径还须同代码batch1／4／8实测，记录实际generate宽度、padding、早EOS、真实吞吐和峰值、逐源原生差异、整批恢复及资源归还。只有真实原件通过才讨论正式全量接续；当前旧八卡和PTN不因这个新模块而重启。
