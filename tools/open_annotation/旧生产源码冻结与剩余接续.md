# 旧生产源码冻结与剩余接续

`freeze_legacy_successor.py` 用于恢复原FP32八卡标注。它只准备新的源码包和合同配置，不启动GPU、不提交任务、不改旧队列、旧标签或旧声明。新vLLM试验仍关闭，不能把此次恢复当成模型或速度试验。

## 原字节保留什么

仓库内 `legacy_snapshots/production_20261025/` 保存实际旧生产源码。固定 `bundle_files.json` 的文件摘要是：

```text
54cd49b77ce3c82bbd61bc4ca3cc9389016e908e976ef2574fb953b3249554b0
```

清单含23个原文件，**其中包括 `contracts.py` 源码**；加上清单文件本身共24个文件。不在此清单里的是生产 `contract.json` 配置。因此，复制23个原文件和原清单后，清单文件摘要仍为54cd，不能为新版本重新排列或重写它。

冻结器核每个成员的实际字节、文件名和摘要，拒绝缺失、额外文件或符号链接；再从旧 `contracts.py` 的抽象语法树提取13个模型相关模块，核清单及生产合同中的每个摘要。这里只使用旧13模块，不能混入当前14模块或新的时间换算方式。

新生产合同只改 `version`。模型路径和文件摘要、外部Qwen源码身份、decoder、Ultra无head、FP32/eager、TF32=false、单窗口独立计算、batch=1、512 tokens、旧窗口和旧时间换算规则都保留。原合同中的 `parent_contract_sha256`、`parent_bundle_sha256` 也不改；这次接续关系放在外部冻结回执，不能通过加减合同字段伪造谱系。

冻结器会使用已核原字节的旧合同校验器检查新旧格式；载入时显式compile/exec，避免Python给冻结副本写 `__pycache__`。这一步不导入torch、Qwen或vLLM，也不读取真实模型权重。

## 入口和输出

Python接口：

```python
from tools.open_annotation.freeze_legacy_successor import freeze

receipt = freeze(
    base_contract_path="/实际绝对路径/旧生产合同.json",
    base_sha="旧合同文件SHA256",
    output="/实际绝对路径/新的冻结目录",
    version="新的安全单层版本名",
)
```

命令行：

```bash
python -B tools/open_annotation/freeze_legacy_successor.py \
  --base-contract /实际绝对路径/旧生产合同.json \
  --base-sha 旧合同文件SHA256 \
  --output /实际绝对路径/新的冻结目录 \
  --version 新的安全单层版本名
```

输出目录必须全新，父目录已经存在，位于Git工作树及 `.git` 外，不得与源码副本相交，也不能是 `/` 或 `/root`。禁止覆盖已有结果。输出包含：

- `code/`：23个原源码文件及原 `bundle_files.json`，逐文件再次核SHA。
- `production-contract.json`：只修改版本的新合同，使用新的合同SHA。
- `freeze-receipt.json`：固定旧合同、新合同、原程序包、13模块、未验新GPU等事实。`base_contract`、`new_contract`、`bundle` 都是严格的path/sha256引用，版本另记为 `new_version`。

中断后留下的新目录作为证据保留，下次不能覆盖这个目录。应先检查失败材料，再使用新的明确目录；不能自动删除后假装首次生成。

## 冻结不是运行准入

冻结器只能证明给定旧合同的文件摘要、旧源码副本完整、新合同只改版本及固定FP32计算配置。它没有在本机重读远端模型权重或外部运行库，也没有重新核历史两卡验收原件，更没有验证新任务的八张卡。

真正恢复前，外部运行门仍须把 `base_contract` 绑定到原本已验收的旧生产合同及历史两卡证据。随后检查模型和decoder实际字节、原设备锁、资源双快照、持续独占监控、新任务唯一声明及平台状态。历史模型配置可沿用，**新任务GPU启动、吞吐或成功不能继承**。回执固定 `runtime_admission_granted=false`、`new_GPU_execution_verified=false`、`new_task_submitted=false`。

新生产任务必须用新的合同、新的剩余输入索引、新queue和新labels；旧生产者保持原字节。原始三训练域总分母仍需等于11521178，不能为了恢复把剩余数冒充全库数。旧保留结果与新剩余必须逐源互斥且合起来覆盖原库。缺少完整提交的异常材料单独保留，不得重贴到新合同。

## 哪些工作不会重复

已完整发布的旧侧车结果，包括未完成分片内已发布并完成提交的来源，必须从新remaining中排除。旧结果继续绑定旧合同、旧程序包和旧来源身份；跨节点的文件系统设备号变化由独立可移植内容账本记录和核验，不能改旧侧车里的stat字段。

旧ASR/aligner阶段缓存的key含旧合同SHA。新version改变合同SHA，保持13模块不变时，新生产者不能直接命中旧key。冻结器不改key、不复制后重贴生产者，原缓存仍保留。没有完整侧车的在途或阶段工作可能有界重做，不能承诺所有阶段零重复。是否跨合同复用阶段结果需要另外明确的协议，本次恢复不扩展此范围。

CPU测试使用实际23文件副本和格式样本合同，覆盖原字节保持、仅版本变化、计算配置变更拒绝、源码损坏、重复或不安全版本、现存/Git/符号链接输出拒绝以及不导GPU库。格式样本没有真实模型权重，不能作为生产质量或实际GPU验收证据。

## 历史质量门和新挂载门分别检查什么

恢复入口保留原 `ultra_w8_gate_v2.py` 及原admission文件，继续核原两卡验收、质量材料、模型计算语义和原三域全库分母。该历史门没有取得当前语义锁，不要求旧run全新；文件stat只是同一次读取前后比较，不把历史设备号强加给当前节点，也不把新节点当作原两卡验收机器。

原 `verify_ultra_cloud_mounts_v2.py` 包含“旧admission里的run必须不存在”的初次提交条件，而旧run在恢复时本来就已经存在。因此，恢复入口保留其原文件及SHA作为历史谱系，**不再执行这个旧fresh-run命令，不改它或原admission里的run_root**。

第二道实际命令改为 `verify_portable_successor_mounts.py`，直接绑定新的后继spec文件及SHA。它要求新run全新、仍在原独立ROOT内；原 `/root` 用户挂载必须RW、共享挂载必须RO，两者的GPFS来源、目标、类型和模式逐项保持原配置。检查会读取实际新code、旧queue/labels、新run父目录、原全库与新剩余索引、计划数据库及其他固定引用的findmnt结果；模型的实际路径、文件大小也必须位于原共享RO挂载中。这里只核路径和大小，模型内容SHA仍由原GPU父进程在CUDA之前完整检查。

共享别名仅接受已声明的 `/root/group-shared` 到 `/shared/group-shared`。报告保留当前别名的链接身份、解析目标和实际挂载行。两道门均不新建run、不启动GPU；全部通过后，恢复控制器才在旧锁保护下创建一次性声明及新run。云端控制源清单必须固定新增挂载检查器的实际源码SHA，不能部署仍引用旧控制目录的半套脚本。

新run和运行证据还必须避开专用冻结包、旧源码、旧控制脚本、全库/剩余索引及语义声明目录。仅重绑定计划数据库和输出字段，不能把新queue/labels写进旧code目录；证据目录也不能占用旧输入或永久claim的命名空间。控制器与新挂载门使用同一份目录隔离检查，门后再核一次。单个JSON若放在通用base或其通用父目录，不会导致整个base及所有合法兄弟输出都被禁止；这些固定叶子文件仍由SHA和全新目录要求保护。实际专用目录中的新run/evidence一律拒绝。

共享输入/模型整棵只读树同样禁止作为运行证据写入位置。生产证据必须位于持久用户 `/root` 挂载，不能误用容器的 `/tmp`。新挂载门会对证据目录（尚未创建时为最近存在的父目录）实际核同一用户RW GPFS来源，不把“路径看起来在某处”代替真实挂载证明。
