# 转写计算提速、容量估算与保留旧结果

本页按版本保存 10 月 27—28 日的方案、失败和实测。只查进度时，读末节“正式B8已真实运行后的查询口径”和[任务状态](task-status-and-readonly-progress.md)，这两处不会触发恢复或新模型任务。要解释当前合批方案，先读“真实合批差异与逐条声学特征修复”一节，再看它的前置条件。旧联合数据库交接、BF16/SDPA 探索和 vLLM 失败各有各的证据：它们不是当前 B8 的执行命令，后续 B8 通过也不说明这些路线取得了运行验收。

维护实现位于仓库`tools/open_annotation/`。本参考讲的是转写阶段的优化，不改既有 PTN 训练，也不改运行中已冻结的标注。

用户此刻要的是“实际GPU验证”还是“仅依据已有机器信息估算”，先分清。后者不授权新增 GPU 进程，也不授权按未测的倍数上线。2026年10月27日早期转写提速阶段，用户曾要求“GPU先不测了”，当时只完成 CPU 实现和八卡信息测算；之后用户授权八卡 WebShell 实测，并在事故后明确要求恢复八卡标注。所以早期那句限制不等于现在禁止恢复。

独立恢复按本页末节和`docs/reviews/2026-10-27-跨节点标注恢复实测.md`记录的真实数据、互斥条件与运行条件执行。恢复授权不扩展到再次在同卡上构造 vLLM；已暂停的 heartbeat 不自动重开。

## 选择转写计算方式

新合同可以显式设置`runtime.asr_compute={dtype:float32|bfloat16, attention:eager|sdpa}`，`freeze_contract.py`有对应的成对 CLI 参数。旧的缺省配置不改子模型配置，legacy 基准走它自己实际的默认行为；显式 FP32eager 与旧默认可能不同，两者不是同一基线。Ultra 保持原精度、单窗和原生/FIX 观察，转写提速不靠换定位模型取得。

实际加载时核对 dtype 参数；显式 profile 还要核对所有相关子配置。首个成功的 ASR 调用里观察实际 attention forward、逐模块 SDPA 调用、Q/K/Vdtype、配置是否稳定以及哪些模块没有执行。显式设置没有兑现就停止这次试验，不能把结果伪装成单条音频 unknown。上游有报告指出顶层 attention 参数没有传入子配置，因此请求标签不能作为依据。这类观察不是 CUDA 内核 profiler，也不保证模型质量。

完整的首窗观测只在终态保留；周期性的`chunk_committed.performance`用当前进程的轻量累计与增量，把转写、定位、源审核、窗口、缓存和发布分开记。首窗观察那次调用本身就含真实推理时间，整段不能都算成钩子带来的额外耗时。新进程恢复后重新计时，不接上一次 attempt 的累计值。

## 有限实际对照的准备与读取

`prepare_speed_validation.py`的 schema 是`annotation-speed-matrix-preparation/v1`。显式给出 base 合同、三域 30/3000/512 索引及 SHA、两个目标 UUID、协作锁根和解释器，它生成 legacy/FP32SDPA/BF16SDPA 三组独立的源码、合同和命令。这个工具只生成，不执行命令，也不授予资源或八卡资格。输出不落在仓库和旧合同/代码/索引树里；输入与锁目录是软链时直接拒绝。定位原因先用短样本，对选中的候选再做代表性完整流程；十小时的长跑本身不算验收。

`audit_speed_comparison.py`要求两份 SHA 固定的`redimnet2-annotation-speed-track/v1`描述和完整有限结果。speed 模式下只有 ASR 计算配置可以不同，模型、第三方代码、解码器、工程源码、质量规则和其他 runtime 保持一致。它逐项核对已保存的原声身份字段及其侧车/提交绑定（不重读、不重新哈希媒体）、窗口、文字、语言、token/EOS、原生与 FIX 字界和决策。目标文字不同的窗口不强行配边界；失败样本缺失时，不给出完整总体的结论。

全冷速度比要满足几个条件：两轨都是真实的新 ASR 执行，没有复用完整侧车或阶段缓存，音频与窗口相同，并且实际计算观察已核对。旧结果复用照旧保留，但消费缓存得到的数字不能当作新模型速度。legacy 按真实子模块行为核对，不必声称全是 eager；没有实际观测，就不能下配置已兑现的结论。recovery 模式用同一合同，逐来源和原生结果严格一致，只忽略两项缓存标记；不一致时照样保存差异，退出 2。报告始终不授予人工质量、训练/评测或自动八卡准入。

## 仅根据现有八卡信息估算

`estimate_speed_capacity.py`读取`annotation-existing-monitor-capacity/v1`监控摘要及其 SHA，输入是观察吞吐、剩余来源和显式余量假设。NVML 的`total-used-free`可能不为 0，驱动保留和非实例占用要扣掉。只有每卡一个已绑定计算进程时，才能据此估算单实例。显存短窗峰值不是历史最坏情况，GPU 利用率也不是 SM 占用率；用 100/util 推不出必然的倍数，也推不出理论上限。

10月27日11:34的实测数据：八张 80GiB A800 各一个进程，最重一张 14570MiB；不可用和非实例占用 701MiB。按静态 5 份/卡算，再留 8192MiB 且每份乘 1.15，预算降到 4 份/卡。这些是当时的机器信息和明确假设，不构成将来启动的许可。现维护的启动器仍是每个 UUID 一个 worker；多副本资源组没有实现也没有验证，32 进程的显存表不代表实际支持 32 进程。展示 1.5/2/2.5 倍 ETA 时标成假设，并说明它与进程数无关。BF16/SDPA 没有实际测速，就不写提速成立。

## 去重接续

`prepare_speed_continuation.py`不构造旧的 WorkQueue/SidecarStore。默认的 provisional 模式只读固定索引、一个完成槽快照和最多 8 个未封账片；已封账片保留旧 producer 引用，部分片里已有完整侧车/commit 时也要核对身份再排除。孤儿文件保留并拒绝，不悄悄修复，也不重新推理。旧 cache 含合同身份，改动合同 SHA、重贴标签或拿旧 ASR 结果声称新 profile 已测都不成立。

`--execute-final`要求有真实的旧 writer 终态观察及其 SHA/任务绑定、时间有效；先取得既有`.parent.lock`的只读 FD 独占锁，在持锁状态下核对索引和 broker 稳定，才把尚缺文本分片复制到新目录并生成 remaining index。最终准备还会流式扫描未领取片里已有的旧侧车/commit，核身份后排除，写出新的`retained-unclaimed.jsonl`及其 SHA/count 引用。孤儿或损坏的分片保留并拒绝；provisional 明确没有扫描，不能当最终证据。终态 JSON 来自外部观察，工具本身不是认证平台；准备锁释放后也不构成未来启动的租约。旧结果加新剩余的数量应严格等于原11521178；保留完整片的固定索引/完成槽证据，不等于重开百万侧车做全量审查。

新八卡准入还要验证原任务的真实终态、资源互斥和实际质量，不能直接放宽原来固定的全量分母。新`cloud_gate --union-mode`只做联合数据检查，和原运行门分别返回结果；剩余准备或数据检查通过，不等于可以执行新任务。新旧 writer 不共写同一队列，旧结果不复制成新 producer 的结果，这一过程也不操作 PTN。

本轮 713 项 CPU 检查实际通过、0 skip；这是 CPU 结果，不是 GPU 速度或人工完整字的证据。具体的新鲜快照、代码、已修反例和仍缺的条件见仓库`docs/reviews/2026-10-27-转写提速实现与八卡容量测算.md`，命令接口见模块 README 和`转写提速对照验收.md`。后续每次执行都重新核对用户指示、源码和现场资源；本页数字不是实时状态。

## 方案选择与已经实现的范围

新规划在仓库`docs/plans/2026-10-27-转写提速方案反思与执行优先级.md`。长期方向优先研究 Qwen1.7B BF16 加官方 vLLM 的单卡共享请求引擎，八卡各自独立来源，Ultra 先保留。后续补了最小 adapter，但没有真实性能和质量证明。已有单窗 BF16/SDPA 是新增代码最少的实际对照候选；同参数双副本对模型数值方式的改动更小，但需要新的资源组，所以不能说它的实施成本更低。4 份/卡的静态容量不决定哪个方案最优，也不能把复制 4 份权重当默认终态；7ASR+1FA 的配比和小模型直接上 TP8 都没有定下来。

现有算子审计要求同一份工程源码、batch1，且每次运行内各 worker 的 UUID 互不重复（基线和候选可以先后使用同两张卡）。这套检查不适合直接评价 vLLM 或同卡多副本；新架构改用独立协议，旧的严格检查保留。恢复时把几件事分开：已发布字节是否不变、来源是否不重不漏、未发布的重新计算差异，以及质量。固定 cohort 并不能自动解决半批发布的问题，新 ASR 阶段库先把完整批次持久化，再逐源消费。旧缓存键和 producer 不能直接改；这个阶段库也不是 ASR/FA 的完整异步调度器。

质量要同时比较固定文字的 FA 结果和各自文字的端到端结果；只看共同文字子集会有选择偏差。人工允许区间、削首/削尾/邻字和分层文字错误，比小数点后的位数更重要。旧原生时间格点实际是 80ms，FIX 给出的小数不构成新增的真实精度。没有人审金标时，不报完整字准确率；候选吞吐和人工抽检质量分开统计。

vLLM 的批次不变特性仍是 beta；文档写硬件 CC>=8.0，不等于 Qwen3-ASR 已在这样的卡上验证过，旧的 CC>=9.0 结论不能沿用，只设 seed 也保证不了恢复后逐位相同。vLLM 的内存包含 KV 和工作区，套不上旧 14.23GiB/实例的容量。做 CPU 实现那次，用户要求先不测 GPU；之后明确要求八卡 WebShell 实测。真实尝试和事故见本页末节；最小适配不等于实际资源组，也不等于 GPU 证明。

## 联合全库的数据检查与唯一读取

仓库`tools/open_annotation/联合覆盖与唯一读取.md`说明`annotation-union-coverage/v1`的实际格式。`union_coverage.validate_union(spec_path,spec_sha,mode='plan',output_index=...)`用 SQLite 逐源核对原全集、旧完整片/部分片/未领取预置结果、新剩余输入和侧车提交。生产用途固定11521178及三域原计数，CPU 小样本显式隔离。检查内容包括 source 完整记录、合同版本、runtime 和模型来源，不限于两个数量是否相等。它不构造旧的 WorkQueue 或 SidecarStore，也不修旧 commit。

plan 模式要求终态是新鲜的、旧父锁与 broker 稳定，然后核对分工和旧保留结果；complete 再核对全部新旧结果以及新队列没有租约。complete 可以使用已经固定的历史真实终态，不必在几天后伪造一次新旧观察，但当前锁和 broker 仍要核对。`cloud_gate.check_union_data`使用独立的`annotation-union-data-readiness/v1`和`data_checks_passed`，没有旧门里的`passed`；GPU、云提交和训练/评测资格恒为 false。这个结果替代不了 W2、实际模型、资源或质量条件。

显式的新外部消费索引以不覆盖的方式发布，并给出 SHA。`UnionConsumer(spec_path,spec_sha,database_path,database_sha)`上下文只读数据库，核对 complete/spec 绑定，按原分片与 source 摘要选定原 producer，再重开原侧车/commit。批量读取复用一个上下文，避免每个来源都重新哈希整库；不按 mtime 猜版本，资格恒为 false。数据库或来源发生变化时拒绝，或重新核验。全部旧结果都保留时不造后继，走旧的全量终验。

最终准备、联合 plan 和 complete 都不是轻量的进度巡检：它们要读全库文本和元数据、读旧结果，还会在磁盘上建数据库，开销明显。只在真实的交接或终验边界执行。该工具最初的 CPU 实现记录没有扫描真实全库，不能由此推出真实音频的 SHA。10月27日之后的现场准备与联合检查见`docs/reviews/2026-10-27-跨节点标注恢复实测.md`，那里逐项区分了来源文本、侧车内容和媒体内容的证明。正在运行的进度用 readonly_progress 查。

真实联合库构建时，逐片 FULL 提交、随机来源主键和小缓存会造成明显的共享盘同步与读取等待；阶段性的抖动不等于进程卡死。目前没有安全的 CPU 审计断点续建协议：事务已提交，或旧结果阶段计数到位，都不能把隐藏的临时 SQLite 当最终证明。先查实际 PID/start、CPU/IO 和日志时刻，再决定下一步；不热改运行中的源码，不伪造完成报告，也不在`/tmp`只剩少量空间时盲目搬迁。实际云启动仍要有独立的新鲜平台观察；联合审计的启动观察只在启动时核对时效，不改写历史时间。

本次把恢复用的 SQLite 中间索引放在共享盘，是维护执行时自行选定的架构，不是实验合同或模型标注的必要步骤。以后选构建位置前，先实测代表性的随机读写、事务同步成本和预计库大小，并核对本地实际可用容量。旧结果核对和中间索引构建要单独计时，它们的耗时不能算进模型标注的速度。调整构建方案时，当前已验证的结果和唯一审计继续保留：不打热补丁，不另起全库重扫，不降低验证强度，也不把还没实现的内存方案或迁库方案写成已经可用。

run/v1 启动控制器对最终的千万行计划库做一次全表精确条件计数，避开`GROUP BY`的临时排序开销。计数里要保留两个非空生产者、各自精确数量、总数守恒和`COLLATE BINARY`；未知/NULL、第三组，以及大小写或尾部空格造成的别名都拒绝。只把两项 SUM 和报告比一下、忽略额外来源，这种做法不成立。实际 SQL 计划和反例另行验证；CPU 检查通过不等于八卡已经启动。

恢复原标注还可以用显式的`annotation-portable-successor-run/v2`，用`preparation_attestation`替代 v1 的`union_attestation`。它复用真实准备时遍历原 11,521,178 来源的分工，以及角色定稿已完成的 10,361,644 剩余记录的父片／互斥检查和 816 份内容证明；核对固定完成收据、原／新计划与索引及必要摘要，不重开 115 万旧侧车，不重新逐条扫描全库，也不读取联合计划库。`union_spec`只保留布局引用，不执行审计；原 23 文件引擎直接消费剩余索引。v1 对完整联合库的要求仍然有效，停止审计的原件和半成品保留，但不算 v1 成功。v2 实现另封新源码，仍要独立 review、CPU 测试和实际八卡验收；W2、挂载、旧锁、context 守卫以及最终联合消费／完整结果终验不变，机器边界不自动放行。

可能长时间排队时，可以用独立的`queue_handoff.py`和`launch_queue_handoff.sh`，格式与接口见仓库`tools/open_annotation/排队后新鲜证明交接.md`。蓝图 schema 仍是 v1，内部runtime_base显式选 run/v1 或 run/v2：前者要有最终联合报告和数据库，后者要有真实的完成准备收据，两者都不接受隐藏的半成品。默认 check 不写请求，不运行内层 inputs 或 GPU；外层不全读 v1 计划库 SHA，v2 也不使用联合库，因此两者的结果如实标为 false，替代不了内层门。真实实例生成唯一请求后，操作者再按实际平台提供新鲜观察；开发机上的 publisher 只核共享文件，不声称查过云 PID，也不声称代表平台认证。

内层 21 成员清单和外层 2 程序清单分别固定，拒绝额外导入、软硬链、FIFO 和置换。读取时先用 lstat 拒非普通文件，再用 NONBLOCK 防止打开前被置换造成永久阻塞。发布用私有目录和无覆盖文件；已有的请求、回复、声明和失败记录都不删除。最终 exec-intent 保存后，再完整复核源、蓝图、请求、回复、只补观察的运行描述、实际自身身份与截止时间。生产环境不使用假的执行器、时钟或进程钩子；CPU 双进程 fixture 成功，不等于真实云或 GPU 成功。

## 跨引擎审计与新阶段恢复

仓库`tools/open_annotation/跨引擎对照协议.md`对应`engine_protocol.py`和`audit_engine_comparison.py`。原声/PCM、模型、窗口、prompt/语言、generation、质量和定位都固定，允许变化的只有显式给出的 backend/code/precision/batching。vLLM 轨要引用实际的适配 spec，核对所有控制项以及源码/版本/模型文件，不能只写一个散列。每个来源的完整侧车/commit 和新 vLLM native 引用都要核，包括 request identity、原生 ID、cohort SHA 形状、EOS、终止、规范化、状态和冻结包绑定；失败的来源不从分母里去掉。

固定文字的定位和各自文字的端到端结果分开算；目标不同的不强配时间，也不报 0 误差。计时按 new/cache/reused/not_run 分别统计；只有非合成的完整新执行才计算声明的墙钟比例，报告里仍然写`GPU_runtime_verified=false`、`validated_GPU_speedup=null`。已发布的结果按原字节恢复，未提交的跨引擎计算不给逐位保证。

`vllm_backend.py`的普通导入和 help 不加载真实的 torch/qwen_asr/vllm。CPU 入口`VLLMBackend.from_fake_engine`只接受 cpu_fixture；真实构造`build_real_engine(...,execute=True)`这条低层路径需要 pilot、离线环境、实际的完整权重与处理器输入、固定依赖和关键实际源码，构造前还要核对 enqueue/wait 公开 API，当前不调用它。映射按实际原生 ID 做，不按位置或数字猜；EOS token 的观察和引擎自身的 EOS 停止分别留证，出现矛盾或未知时不把状态升为 completed。

## 10月28日真实合批差异与逐条声学特征修复
