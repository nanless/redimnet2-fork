# 训练巡检与恢复范围

## 证据采集

先核对任务ID、run root、启动身份、阶段和数据集。持久 train.log、外层 reproduction.log 和云stdout 分别读，因为同一个异常会在三处重复出现，混在一起会把次数累计错。取一个完整统计快照，其后的最新行只作补充复核，各自的时间与时区都注明。实际GPU状态从精确任务的 worker 采样，开发机的数据代替不了它；浏览器登录失效时请用户自己完成登录，认证材料不读。

检查项：多rank是否对齐、日志是否推进、loss/LR/margin/Acc是否有限、Traceback 是否被捕获后继续、OOM/NCCL/子进程退出、短音频限频打印、检查点稳定性和磁盘可用性。WARNING 训练行属于常规输出，不按日志级别算异常。只转录或保存必要的白名单运行字段；整份环境变量和凭证不进证据。

异常按独立发生登记：轮次、前后批号、音频和原文。同一次发生在 stdout/reproduction中的副本可去重；不同轮批再次发生，即使key和归一化块SHA相同，也分别计数。原始字节SHA，和换行规范化之后再比较的SHA，两个值分别保存。异常被捕获、日志继续写，不等于未来的阶段门禁已经接受它，还要按专用阶段规则另核；音频复查成功，也不说明历史根因已经消失。整段及首中末成功，不排除生产裁剪或近文件末端seek/read失败；这里要区分当次加载的soundfile.py与原生libsndfile路径、摘要、版本和探测位置。巡检只记录失败与推进，不改事件许可，也不改解码环境。开发机私有库的对照通过，和真实worker的验收分开算；没有记录的历史随机起点，不能写成已经完整重放。

## 指标解释

当前计量器在 rank0 每16批采样1批，累计的是本轮，每25批打印一次，没有跨卡归约。所以 loss/Acc不是最近25批瞬时均值；分类Acc 也不是验证准确率。日志里的批次是数据批次/更新尝试，AMP 可能跳过更新，所以不能把它叫作已经证明成功的 optimizer step。

本次已核实的计划是120轮、每轮15001批，PTN 的累计进度按 `(epoch-1)*15001+batch` 除以 `120*15001` 算。其他配方或后继任务要先从实际有效配置里核实轮数和每轮批数，不能套用这两个常数。新任务不继承被停止旧任务的累计计数。只有监控协议相同，EER 趋势才可比较。百分数、百分点和相对变化分别算；快速8秒验证和最终整段LM协议分别报告。数值有限不等于质量改善；与LR同时变化不证明因果，仅凭几轮回升也判不了过拟合或发散。

GPU 至少记录采样时刻、卡号、利用率、MiB显存/总显存、温度和功耗；短时间多次采样仍然不是全程均值/峰值。rank PID、WORLD_SIZE、cwd、worker子进程数能证明当前的运行结构，证明不了每个训练batch都成功更新。

## 检查点

先 stat，再用 CPU、单线程、mmap 逐份读取可信的本项目 checkpoint；读完之后复核 size/mtime稳定。正在写的 TMP 不能当完整的恢复点。核对 epoch 与文件名是否对应、model/optimizer/scaler 是否齐全、head 形状、浮点数是否有限，以及 optimizer/scaler状态；最后给出最新点和最佳验证点两个身份。检查点读取成功，不证明加载入口、源码冻结或未来阶段可用。

现行做法按整轮原子保存，不含完整的RNG、loader游标和轮内状态。恢复通常要重做当前轮，所以不能承诺逐批/逐位复现。原PTN续训恢复 model、optimizer、scaler 与 epoch；PTN→新LM 只初始化模型，optimizer/scaler 全部新建，两者不能混同。执行恢复前先读阶段门禁的引用。

## CPU 恢复演练（2026-11-06）

对 `model_120.pt` 做过一次纯 CPU、单线程、mmap 的只读恢复演练，结论是文件本身自洽：

- 四键齐全（`model`/`epoch`/`optimizer`/`scaler`）：823 张量、81,422,833 元素（含 78 个 int64）；584 份 SGD 动量；`scaler=16384.0`；`lr` 与 `val_log.csv` 第 120 轮逐位一致；1,329 个浮点张量里 0 个非有限；体积闭合，0 字节误差。
- 能加载不等于能续训：检查点里没有 per-rank RNG，也没有 48—120 段的 dataloader 游标。恢复只能重做“已保存的完整状态 + 绝对时钟”，所以不能承诺与不中断训练逐位相同。PTN→LM 更是只取模型参数，动量与 scaler 一律新建。

有两个看起来通过了、实际没验到的情形，都出现过：

1. `torch.cuda.amp.GradScaler` 在没有 GPU 的机器上会静默 Disabled：`load_state_dict` 成了空操作，`get_scale()` 恒返回 1.0，于是“scaler 恢复成功”是假的。CPU 演练要用 `torch.amp.GradScaler("cpu")`，并显式断言 `get_scale()` 等于检查点里的值。
2. `read_bytes=0` 不等于没读：页缓存命中与 mmap 访问都不计入 `/proc/<pid>/io` 的 rchar。拿 rchar 判断“是否真的读过权重”，结论正好相反；要证明读过，看读到内容之后的校验结果（张量数、非有限计数、体积闭合），不看 IO 计数。

演练本身不授权任何 GPU 或新阶段，它只说明这份文件能被人读懂。

## ETA

同时给出短窗口的批耗时和近期完整轮周期。批耗时只取同一轮内的窗口，轮间开销另算一次；完整轮周期已经含保存、验证和重建，不能再加一次。端点要说清：`WARNING 15000→下轮25` 与 `INFO15001→下轮25` 不一样，两者都包含下一轮的前25批，所以不能叫纯验证耗时。

报告里写清估算锚点、剩余批数、方法差异和阶段边界。PTN与LM帧数/batch不同，32批LM短测不足以可靠外推整个阶段；还没执行的导出和完整评测不算进PTN ETA。方法范围不是置信区间；门禁已知会失败时，不承诺无人值守跑完整流程。
