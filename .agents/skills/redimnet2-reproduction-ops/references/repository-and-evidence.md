# 仓库、部署和证据

代码、脚本、可公开配置、测试和文档的持续维护源都在本仓库，技能源也在 `.agents/skills/`。安装副本只做同步，改完记录源提交和逐文件摘要。2026-11-05 只读核对的结果：该目录和 `docs/16-实验维护与验收边界.md` 只在本机工作副本 `/Users/zhounan/Documents/声纹降噪/redimnet2-fork`，服务器检出 `0a3f6dd` 没有这两项。

外部运行证据至少要写清观测日期、程序摘要、模型与输入摘要、用途和实际输出。公开仓库里可以放证据字段说明和合成夹具；业务原件、完整日志、诊断名单、密钥和访问令牌不放。旧文件就在本机，也不等于有公开发布的授权。

新仓库版本只要有依赖路径、异常规则、身份读取或输出作用域的变化，就按新源码验证。历史冻结清单保留原文；重算旧清单再宣称新旧相同，会抹掉两者的差别。部署副本要能追溯到仓库提交，不能把仓库外的实验目录当作唯一现行实现。

写文档时检查相对链接和代码入口，并把“规划”“合成 CPU 通过”“真实模型通过”“GPU 恢复通过”“人工边界审核”分开写。平台表单提交成功只证明提交这一刻的结果；任务是否唯一、挂载、rank、日志和检查点还要回读。结果未知时先查有没有重复任务，不自动再提交一次。

未来云任务名称统一带 `zhounan_` 前缀。`make_admission_spec.py`把名称写入新描述的`cloud.platform_task_name`，`make_cloud_launcher.py`输出同一个名称；合法的自定义名不能和已固定的新描述冲突。旧描述缺这个字段时，只把它当作未来表单的建议，不写回旧原件。`tools.ptn_resume.build`只在构建收据里给建议名称，不改运行合同。平台侧仍要验证字符、长度、唯一性和名称回读；这两个前缀工具落实的是用户约束，不是平台校验。10月27日已在平台原地给本轮查到的13个ReDimNet2任务补了前缀，任务ID和运行配置不变，历史提交时的名称继续保留。

仓库静态检查的入口是 `scripts/check_repository.py`，CPU 分组检查的入口是 `scripts/run_cpu_checks.py`；先看 `--help`，结果写到本次新建的 `.audit-local` 文件或目录（此前不存在）。静态检查不跟随受控软链、不覆盖已有文件，并拒绝非有限 JSON 和重复键。CPU 汇总里只要出现跳过、预期失败、零用例、超时或失败，就不能记成完整通过。用例数量随版本变化，以本次实际记录为准，不拿历史报告的数字当验收目标。

自2026-10-28的用户全局铁律及本次明确补充起：本机对GitHub只读／只下载。从本机上传任何文件、代码、文档、数据、提交对象或分支，都违反这条规则——本机git push、网页／API／gh上传和自动同步都在排除之列；改URL、remote、端口、代理或隧道给本机上传换出口，同样在排除之内。本机保留`disabled://github-push-blocked-by-policy`，已删的远端`codex/repository-audit-20261025`不恢复，26个其他仓库不再重审。

明确允许的GitHub写入方式是：把任务需要的仓库同步／拷贝到`dev_a800_2gpus`，在服务器自己的工作目录和进程里连GitHub，执行该任务需要的提交和推送；本机可以通过SSH发起远程服务器命令。服务器上的实际上传，和把本机push透传过去，是两回事，后者仍然禁止。服务器要配自己的remote或既有认证，只作用于服务器副本，不把这套推送配置反向恢复到Mac。此前“服务器中转也禁止”的笼统说法，已由这次明确许可替代；本机永不上传这一条不变。本地编辑和commit照旧，作者／提交者nanless；其他协作目的地按用户指示。规则更新本身不代表仓库迁移或推送已经完成。

服务器交付前核 `git rev-parse --is-shallow-repository`。浅历史仓库生成的bundle即使在本机verify成功，也证明不了服务器空仓库拥有浅边界之前的祖先；服务器应该按原来的真实边界，从指定GitHub仓库只读获取所需提交，再实际导入并核HEAD，而不是伪造祖先或重建已删分支。服务器还要分别核对配置里的原始remote和 `git remote get-url` 得到的实际URL，已有的insteadOf可能指向第三方代理；向这种代理上传，不能算直接交付到GitHub。只使用用户指定的目的地和服务器既有认证，不把Mac凭据或本机push流透传过去。HTTPS缺认证和网络超时分别记录；没有回读到远端SHA，就不报推送完成。

持久作业声明是去重协议的一部分。新任务在取得声明之后失败时，要准备显式的恢复入口和新鲜的资源证明；删掉声明或锁文件再强行重跑，等于绕过去重。文档维护请求也不构成启动、停止或迁移现训的授权。

用户明确要求控制台工作期间不锁屏时，可以用本轮拥有的临时电源保活，并用 `pmset -g assertions` 实读确认。`caffeinate -u` 不给时间时的用户活动断言默认很短，进程还在不等于一直在防空闲锁屏；防熄屏、休眠和用户活动这三项的实际期限要同时核对。永久锁屏和登录安全设置不改。把PID、启动时间和完整命令记在本仓库被忽略的本地证据目录里；下次继续工作前先读已有记录，结束时只撤销身份仍然匹配的本轮进程，不按名称杀掉别的保活。保活不是后台巡检或训练启动的授权。


## 本轮构建和复验中已证实的失效方式

新恢复包的配置要用真实YAML，并做逐类型的回读断言；只验证JSON语法不够，YAML里的类型和结构错了照样读得进去。模块既有脚本又有包消费者时，用显式的 `if __package__` 选择相对导入还是脚本导入；宽泛的 `except ImportError` 会把依赖内部的错误一起吞掉。只有在独立的临时cwd、清掉PYTHONPATH之后实际导入，才能发现被“测试进程已插入源码目录”掩盖的路径问题。

包里每个必需文件都要存在，缺一个就立即失败；写成 `if exists` 会静默漏包，装出来的包直到导入时才报错。仓库的相对目录要保留：工程器在 `tools/ptn_resume/`，资源模块是仓库根的 `word_ft_v3/`。部署目录错了，改正确源码去迎合错误包，等于把错误固化进源码。归档时逐成员核regular/safe相对路径/字节/SHA，再在脱离仓库的cwd里验证实际导入。旧失败包、父日志和未初始化CUDA这些事实都保留。

本轮 619 项完整运行（2026-10-26 前后）曾真实失败在完整字组的包导入上；修好之后的局部通过不能替代新的全量汇总。下面这些条数都是历史记录，不是当前状态：较早549项通过、后来的619失败、修后624项无跳过通过，各自记录；退出信号、二进制和NFKC配组反例完成后的上次633项也曾实际0跳过通过。以后新增审计时，最终数量只从实际总结里读，不能按预期用例数提前宣布全部通过。真实CPU恢复、双卡finite/injected和正式八卡是不同源码及资源上的验收；同一个source190，也不会让不同的父入口自动继承运行成功。

项目技能先在仓库维护源里更新，再统一同步到安装副本并记录摘要；安装目录里不另养一份唯一实现：两份实现分叉后，说不清哪份是现用版本。安装目录里额外的历史参考保留，删除式同步会把它们清掉。源里还有未提交修改时，同步记录要同时保存基准HEAD和实际逐文件SHA；工作区的字节不是那个HEAD的原件。

10月27日加了联合接续/跨引擎/最小适配后，首轮796项实际通过；补上原生ID和cohort形状反例后，798项单元测试实际通过。同期静态组失败过一次，原因是报告还没写完、链接断了；失败日志保留，文档写完后再单独重跑静态检查。把整个失败汇总直接改成passed，会让这次失败从记录里消失。最终收据分别引用单元运行和最后一次静态报告的SHA，绑定本次全部维护文件；安装同步保留原副本和逐文件摘要。后续只改文档不用重跑真实模型，也不拿重复测试顶替尚缺的GPU或人工证据。

## 启动时效失败与真实接续的记录

10月26日的公开记录在仓库内 `docs/reviews/2026-10-26-PTN启动时效修复与八卡接续巡检.md`。jvhrd的真实失败发生在CUDA之前：旧的control观测过期，1800秒内没有取得新材料，所以没有创建run。这次失败和原control都保留；把它改写成NaN复发，或者覆盖成后继成功，都会改变事实。ctjsk的八rank恢复和首次真实SGD已经实读；截至那次观测，完整的第48轮和新检查点还各自待验，以后再汇报要重新获取状态。

`refresh_terminal_refs.py`是仓库维护工具，不追加进旧的冻结候选包。它默认dryrun，不改规范control；要执行时先封存原字节，再以原子单文件发布的方式写入真实的新观测，并记录输入SHA、before、after和部分完成的情况。原件里的平台状态来自实际观测，文件检查不是平台认证；工具不检查平台当前的writer，也不会因为run不存在就授予启动许可。外部无并发writer这个前提、固定候选包的CPU恢复、唯一后继和实际首次更新，都要分别有证据。

文档同步、或者已经存在的监控提示，都不会重新启用已暂停的heartbeat，也不等于新的持久调度授权。技能内部的references保留相对链接；仓库路径写成明确的代码字面，因为安装之后，跨出技能目录的Markdown相对路径找不到仓库。安装副本仍由维护者从最终已核版本同步。
