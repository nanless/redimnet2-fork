## 前向非有限值与隔离诊断

2026-10-25 的接续任务在 48 轮 1773 批 rank4 出现真实故障：增强后的 FP32 输入是有限的，FP16 向量先出现 NaN，FP32 损失随后 NaN。没有故障时刻的权重/RNG，所以 model47 加原波形重放正常，不等于故障已经修复。此前的 1772 个训练迭代也不能一律算成 1772 次实际 SGD 更新：GradScaler 可能跳过更新，而本批失败发生在其反向缩放之前，降低 scale 解决不了本批的前向问题。判断状态要读最新带日期的审查报告，不沿用“八卡正常”的旧结论。

CPU 入口是`tools/ptn_diagnostics/inspect_numeric_cpu.py`，只读 SHA 固定的可信张量/检查点；CUDA 隐藏，线程数和读带宽都限住，模型和动量分开统计。输出一律用新文件，写到现场目录之外；摘要不对或输出不安全的，在反序列化之前拒绝。原 JSON、原 wave、完整 rank 日志和原 SHA 都保留；截图手抄的形状或缺字符的摘要不能当最终身份。

`tools/ptn_forward_probe.py`只用于指定空闲双卡上的单批故障诊断。起点是一组固定条件：全新进程、`python -B`、UUID 绑定、共享协作锁、5 秒双快照、冻结源与输入摘要；每个 case 用独立进程，并重新取一次空闲证明。驱动的 host PID 如果在容器内证明不了归属，不能放宽成“当作自己的 PID”。普通模块核对文件来源与 SHA，namespace 包核对唯一冻结目录，每个 case 都做导入核验。原模型、原配置和完整批保持不动，不再做数据增强。train 前向会更新 BN，所有对照都要重新加载状态。

模块探针会改变同步方式和运行开销，只能用来定位模块边界。CPU 上直接做 half 的溢出，不等于 CUDA autocast 的实际 dtype 策略。`--no-grad`的 FP32 对照要写明没有梯度图，不能写成训练验收。这个工具不做反向、优化器或调度器，不授予生产接续资格。当前同一完整批上 model47 的 AMP 和 FP32 诊断都得到有限值，现场第一个坏掉的算子仍未确认。

## 故障原件和双卡工程的证明范围

新取证在裸模型的前钩子、DDP buffer 广播之后保存真实输入、小 RNG 和全部 buffer。出现非有限值或捕获失败时，各 rank 在反向/更新之前保存完整的当前模型/SGD/scaler、前后 buffer/RNG、标签和输入。各 rank 先发布完整文件和摘要，再交换状态、写协调记录并同步，最后才打印那段会触发父监控的 fatal 文本。某个 rank 写失败时，其他 rank 也要一起停，并记录为不完整；声称全 rank 都能重放，与事实不符。故障包不是训练检查点，不当成完整的 model48。

`engineering_two_gpu.py`的有限路径要完成真实的 SGD 更新；GradScaler 的跳步尝试不能算作更新。测试分两种：一是连续第二次实际更新，二是重新构造模型/SGD/DDP 后加载第一步再做第二步；两者都比较完整的模型、BN、RNG、优化器、scaler 和尝试时钟。注入非有限值另做一轮，核对两个 rank 的完整协调取证和更新前停止。真实完成的数据以当次报告和原件为准。同进程重构不是进程重启，WORLD2 不是正式的 WORLD8，工程的 deterministic/CUBLAS 策略也不等同于生产轨迹。这一结果不能用来宣布原故障根因已解。

本轮真实双卡机器的记录已完成：每个 rank 连续两次 SGD，以及从第一步重构后的一次重放更新；注入非有限值时，也记录了两个 rank 的共同取证和更新前停止。完整的二进制 SHA/mmap 等独立复核以当次最终报告为准，JSON 里的成功字段替代不了它。之后八卡任务 jvhrd 曾排队，启动时两份终态观测已旧了约 2 小时 23 分钟；实际日志显示它在 CUDA 之前等满 1800 秒后退出，未认领新 run，也没有新的数值故障。当时的排队截图不能继续用来声称任务未启动或仍正常。

## Torchrun独立会话与资源锁

torchrun 退出不代表 rank 也退出了：各 rank 可能各有独立的 PG/SID。正式 worker 在任何 CUDA 之前，原子登记 PID/PPID/PG/SID/start/nonce、合同/包 SHA 和本卡 GPU 共享锁的 FD；父进程实读`/proc`和实际环境，用 FD/inode 验证八份登记，并重新核对设备空闲，之后才 ACK。没拿到完整 ACK 的 worker 不进入 CUDA。

父进程持八 GPU 独占锁，在统一准入的独占锁保护下转成共享并把 FD 传下去；每个 rank 另外独立持本卡的共享锁，原逻辑链和旧的四把稳定共享锁保留。只依赖父进程存活是不够的。清理覆盖已确认的 launcher 和独立 rank 组：先按已知 PG 或真实 PPID 关系筛选，不遍历无关进程的环境去猜归属。nonce 或权限未知时，只保持锁并查询原组是否已经消失；重复同一个异常后逃出锁上下文、或猜着杀进程，都不行。清理和归还期间要防 TERM/INT 重入，完成后恢复处理器；SIGKILL 屏蔽不了。只在新鲜的双快照确认资源已归还后释放；本轮的执行预算不代表保守清理一定按时结束。

每轮在验证/保存之前，核对实际的八个 rank 各 15001 批；日志里的轮次和最终 checkpoint 的轮次不能用截断小数冒充整数。第一迭代 705047 和第一次实际 SGD 更新分开记录；AMP 跳步时，后者不能写成第一迭代。“未来 LM 三段协议”读仓库内`tools/ptn_resume/三段LM准备协议.md`，115/120 要来自真实的新第三段，LM 的优化器/scaler 冷启动。
