## 平台终态怎么查（2026-11-06 实测）

- 查终态用 `volc ml_task get -i <task_id>`。`volc ml_task list` 只列 `排队中`、`部署中`、`运行中`、`停止中` 的任务，已结束的任务不在列表里，所以“list 里没有”不等于任务不存在或没跑过。
- 服务器有官方 CLI：`/root/.volc/bin/volc`（v1.2.55）+ 同目录 `mlp`，它们不在 PATH 里，要先 `export PATH=/root/.volc/bin:$PATH`；不加这一步，报的是 `exec: "mlp": executable file not found`。
- CLI 目前不可用：任何认证查询都报 `AccessKeyId or SecretAccessKey is empty`。`~/.volc/credentials` 不存在，只有实例自带的 `access_token`，而 CLI 不认它。这条通道不用凭据，也不必为此去读或搬运它们。
- 所以当前唯一可用的通道是控制台浏览器：任务详情页可读到镜像/队列/优先级/规格/挂载/框架/时限/重试/实例信息与实例终态。抄录时把“控制台目视、非 CLI 复核”写进证据。CLI 字段不伪造：实例列表没展开，就不填 `worker_states`，并写明 basis。
- 用 CUA 操作控制台的经验：任务列表页目标行用 `复制` 会打开预填表单（`/customTask/create?Id=<task>`）。填字段用 AX 元素动作（`AXPress` / `set_value`）；坐标点击不可靠，顶部大菜单展开时会整体遮挡，点击偏移到相邻行。AX 快照 60 秒过期，重采之后索引还会移位，所以采完要立刻动作。数字输入框（`AXIncrementor`）不吃 `set_value`/合成键入；“最长运行时间”留空，平台仍然接受。

平台Running、日志在写、优化步实际推进和检查点完整是四种不同的证据。终态说明里，主动停止、准入失败和程序失败要分开写。开发机挂载能读云端文件，不表示开发机的PID或GPU就是云任务的PID或GPU。读取时记录主机角色、任务ID和观测时间，展示时使用同一时区。

正式新薄索引使用仓库`tools/open_annotation/bounded_metadata_progress.py`，详细接口读`tools/open_annotation/仅元数据的标注进度.md`。先核工具本身及其`readonly_progress.py`依赖的部署字节身份；再读已发布index、report、queue与contract，用它们实际的SHA，不从旧笔记里猜值。只读一次broker与已完成非leased固定槽，按实际来源数统计，不乘固定片长。旧`readonly_progress --bounded`会进一步读取来源JSONL、partial和旧commit，因此不能作为纯元数据接口使用。

保持工具返回的来源闭包、人工质量和运行资格未授予标志。历史保留量、新生产者发布量、在途片和实际模型调用数分开报。总完成量是快照下界；新队列旧生产者计数0不代表旧的历史结果丢失。`candidate`不是人工真值，`unknown`不是程序崩溃数，`failed=0`不是文字或字界全对。原因调查按用户要求另做有限样本；进度查询不重开全库审查、数据库或百万侧车读取。

ETA需要至少两个同口径且有意义间隔的完成量。优先报告较长窗口，同时可给最近短窗，说明语言、时长、在途片和输入分布的不确定性。历史保留量不计入新增速度。分母变了，速率就不能直接拼接。每次查询取到足以回答问题的有限快照就停；上一轮说的“三份快照”只对那次成立，之后仍可再查。

## 遥测与阶段耗时

先读现有`resources-attemptN/GPU_utilization.jsonl`和`GPU_samples.jsonl`的有限尾部，再读8个明确worker日志的有限尾部；共享卡上不另建模型或CUDA上下文。解析时只取完整的JSON行，并保存实际读取范围。利用率要报告时间区间、时间点数、卡数、缺测和均值；瞬时值冒充不了区间均值，0%不是空闲证明。

设备即时used、计算PID占用、框架allocated峰值和reserved峰值分开记，字节与MiB／GiB换算写清。容器中NVML进程名Not Found不能认定进程消失，也不能据此杀PID。设备利用率也不能用100/util直接换算提速倍数：利用率是时间占比，不是耗时倍数。

`chunk_committed.decision_counts`和`performance.cumulative`均为该worker本次进程的累计值：每个worker只选最新完整记录，把日志各行相加会重复计数。阶段占比使用相应累计时长与同一进程elapsed的比值，并说明不是CUDA内核占用分析。末次提交与日志mtime分别记录；租约领取时间不是心跳，运行中缺parent_result也不自动判故障。

## PTN与后续训练

从有限的日志尾部读取最新轮次、步数和同一步的八rank指标。先按`[defaultN]:`分块，再匹配各块表格；进度条和下一rank表格粘连时，直接匹配会归错rank。训练loss和分类准确率不能当验证等错误率；未读到最新验证就明确写成缺项。

检查点使用实际日志／配方定位的数字轮次路径，至少核size、mtime和两次稳定stat。文件存在、元数据稳定、完整内容加载和断点恢复是四种不同结论，前一种不自动推出后一种。只读stat后不能声称已重验恢复。近期尾部错误计数0只证明该读取范围，不覆盖历史FLAC或NaN。过去192个数据worker存活的证据，不能冒充本次完整进程树实证。

以真实目标轮数、剩余批数和有代表性的进度增量估计训练剩余时间，并把验证和保存开销的不确定性算进去。PTN有新检查点，不等于 LM 可以启动；LM仍须核1—35、36—47、48—120三段记录与最终检查点。2026-11-06 起三段记录已齐：`tools/ptn_resume/three_segment_lm_check.py` 对真实数据 `build` 17/17、`check` 18/18，均 exit 0，但 `ready_for_lm_execution` 恒 false——CPU 证据齐全不等于执行许可。官方模型完整字自然变长微调是另一条实验，自动标签不授正式训练或评测资格。
